# DRAFT for the owner: wording for Google Consent Mode "advanced" (2026-10-16)

**Status: DRAFT, not adopted.** Written by the agent (job session `quick/google-advanced-consent`, quick task
261016-ov1) after the owner's decision of 2026-10-16 ~16:30 CET: Google switches to Consent Mode v2 "advanced";
Meta stays after consent only; Tag Manager stays off. No lawyer has read it. Nothing here is on the site. No code
changes until the owner adopts this text (all of it, or with the edits he names) in the question form.

On adoption the build copies each "Proposed" cell byte for byte into `app/vamos-meta-texts.js`,
`apps/web/i18n/messages/{en,de,fr,ar}.json`, `app/vamos-i18n-dict.js` and the `content_strings` seed, and
`apps/web/lib/consent/owner-texts.test.ts` moves its pins from the 2026-10-09 / 2026-10-11 sections to this file.

## Read this first: the Swiss guide recommends the opposite

The EDÖB guide (FDPIC, "Guidelines on data processing using cookies and similar technologies", v1.1, 06.10.2025,
https://www.edoeb.admin.ch/en/cookie-guidelines-updated-version) says, §3.13.1: "data processing must not be
activated by default when the website is accessed", and recommends a two-click solution for third-party services
and tracking pixels so their JavaScript does not run before consent. §1.1 counts "pixels" and "browser
fingerprinting" as "similar technologies", with no exception for signals sent without cookies. §3.12.2: the
information "must always be provided before the data subject gives their consent". The guide is not binding law,
and it does not mention Google's cookieless pings by name. But advanced mode does what §3.13.1 advises against:
Google's script runs, and Google gets the IP address, for every visitor before any choice. **The agent advises one
read by counsel before the ship.** The texts below make the behaviour transparent. They do not make it consent-based.

## What changes for the visitor

| | Today ("basic") | After ("advanced") |
|---|---|---|
| Before a choice, and after "Necessary only" | No request to Google | gtag.js loads on the listed pages with every consent signal denied. It sets **no cookie** and sends cookieless pings |
| What a cookieless ping holds (Google, consent-mode overview, updated 2026-07-30) | — | timestamp, user agent (browser), referrer and page, consent state, whether an ad-click id is in the address, a random number per page load. Google: "While consent is denied, the Google tags send measurements without cookies"; GA4 denied events "are not associated with a persistent user identifier" |
| Google receives the IP address | only after consent | for every visitor, when its script loads (Ads "truncate IP addresses at collection" while ad_storage is denied) |
| Accept | script loads, consent granted | same script, `consent update` granted, read from `/api/consent/state` as today |
| Google may estimate | no | GA4 behavioural modelling and Ads conversion modelling fill gaps from the pings (thresholds: GA4 ≥1,000 denied events/day for 7 days and ≥1,000 granted daily users on 7 of 28 days, support.google.com/analytics/answer/11161109; Ads 700 ad clicks per 7 days per country and domain, support.google.com/google-ads/answer/10548233). Below those thresholds Google models nothing |
| Meta | after consent only | **unchanged** |
| Tag Manager | off | **off** |

## Open choices the texts depend on (agent's recommendation first)

1. **A paid booking while denied.** (a, recommended) A cookieless conversion ping (Ads) and purchase ping (GA4)
   with the amount and CHF, **without the booking reference**. Google's Ads help says conversion modelling "is most
   accurate when these cookieless pings are fired". The booking reference identifies a booking and a person, so it
   is not sent without consent. (b) Today's rule: no conversion or purchase until granted, so no modelling for
   people who refuse. The texts below are written for (a). For (b), delete the clauses marked ⟦1a⟧.
2. **GA4 button and booking-step events while denied.** (a, recommended) Sent as cookieless pings: the same fixed
   list, event name and contact kind only. (b) Only when granted. For (b), delete the clauses marked ⟦2a⟧.
3. **`ads_data_redaction` = true** (recommended, today's value). While ad_storage is denied, Google Ads removes the
   advert click code from its requests, so only "came from a Google advert: yes/no" is left. That is why the texts
   say "not the advert click code". (Google's own reference page for this setting returned 404 on 2026-10-16. The
   behaviour comes from Google's consent overview, "Google Ads will delete the stored information", plus the
   headless proof in the plan. The build re-checks it.)
4. **`url_passthrough` = false** (recommended). Setting it to true would add `gclid` / `_gl` to every internal link
   and form address. That breaks our "path only, never a query" rule, and the texts would have to mention it.
5. **Region**: the denied default applies to every visitor, with no region list. One behaviour, one text.

## Facts the texts rely on (the build must make them true; the headless run proves them)

| Fact | Build must |
|---|---|
| Same pages as today | the loader's address list does not change: never a pay link, manage-booking, review, sign-in confirm, reset-password, dashboard or ops |
| No cookie and no local storage key from Google while denied | headless run with Google's real gtag.js: no `_ga*`, `_gcl*`, `_gac*`, `FPLC` cookie and no `_gcl_ls` (or other Google) local-storage key before Accept and after "Necessary only" |
| Ping contents | every denied request recorded. Page address = origin + path, booking reference replaced by `:ref`, no query, no hash. Referrer = bare origin. No `gclid` value. No booking reference ⟦1a⟧ |
| Hosts | the policy covers every host the denied run reaches. Google's CSP guide (updated 2026-09-18) lists `*.google.com`, `*.g.doubleclick.net` and `*.google.<TLD>` for GA4. The policy gains only the hosts the run actually hits |
| Accept / withdraw | as today: granted only from the server's answer. Withdraw denies, deletes Google's cookies on every domain form, and the tag goes back to cookieless pings |
| GTM | stays off. Its adopted texts stay hidden |

## Consent version

`CONSENT_POLICY_VERSION` moves from `2026-10-13` to the ship day (Zurich date), with its pin in `legal-gate.test.ts`.

What that does to visitors who already chose:
- `/api/consent/state` reads choices under the current version only, so on their next page load **everyone** gets
  `chosen: false` and sees the banner again, including people who accepted and people who refused.
- Until they choose again: Google runs denied (cookieless pings, no cookies). Meta does not load. Anyone who had
  accepted gets no Google cookies and no Meta until they accept again. Google cookies already in their browser stay
  until the next withdraw or until they expire, but they are not read or written while consent is denied.
- Meta's server-side events read consent as of the paid time under the current version. A booking paid after the
  bump by someone who has not chosen again sends no Meta server event.
- Their old choices stay in `consent_log` as proof of what they agreed to and when. No migration, no deletion.
- Why bump at all: the information shown before the choice changes (EDÖB §3.12.2: information before consent).
  A visitor who chose under the old text never saw that Google runs before the choice.
