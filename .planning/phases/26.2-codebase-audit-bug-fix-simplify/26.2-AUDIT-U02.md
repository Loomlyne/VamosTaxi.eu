## U02-1 · correctness · A failed customer cancellation e-mail is saved as "sent" when the ops copy went out

`apps/web/lib/lifecycle/notify-lifecycle.ts:147-153`

```ts
const customer = await sendCancellation(mail, { ...trip, urgent: false }, trip.customerEmail);
const ops = await sendCancellation(mail, { ...trip, urgent: assigned }, BOOKINGS_OPS_EMAIL);
...
return customer.ok ? customer : ops;
```

`claimThenSend` (lines 109-127) settles the claim from that one outcome. When it is `ok`, it calls
`notification_settle(claimId, providerMessageId, null)`, which records the claim as delivered.

**Failure scenario:** a booking is cancelled and the customer's address is rejected by Resend (a mistyped
domain at checkout, or a suppressed address). `customer.ok` is false, the copy to bookings@ succeeds, and the
callback returns `ops`. The claim is settled with the ops message id as a success. The dedupe key
`{bookingId}:cancellation:` is spent, so no retry or sweep ever tries again. The customer is never told their
booking was cancelled, and the notification row says the mail went out.

The test (notify-lifecycle.test.ts) only checks the source text. No test covers a failed customer send.

**Smallest fix:** return the customer outcome on its own (`return customer;`), the way notifyReminder24h does
at line 201. The ops copy stays best effort.

## U02-2 · correctness · A siteverify 5xx counts as a failed challenge, not as degraded

`apps/web/lib/abuse/turnstile.ts:100-123`

```ts
const res = await fetchImpl(SITEVERIFY_URL, { ... });
let json: unknown = null;
try { json = await res.json(); } catch { json = null; }
if (json && ... success === true) return { configured: true, success: true };
if (readErrorCodes(json).includes("timeout-or-duplicate")) return { ..., timeoutOrDuplicate: true };
return { configured: true, success: false };
```

`res.status` is never read. The file header says "Absence and degradation both fail OPEN below the threshold
and fall back to Layer 1's edge managed_challenge at or above it". `challengeDecision` fails open only on
`degraded` (line 201-203).

**Failure scenario:** Cloudflare siteverify answers 502 or 503 with an HTML body. `res.json()` throws, `json`
is null, and the result is `{configured:true, success:false}` with no `degraded`. From the 3rd quote in the
60-second window, `challengeDecision` returns `{enforce:true, passed:false}`, and `turnstileGuard` answers
`turnstile_required` (guards.ts:94). A real customer who solves the widget again gets the same 5xx, so the
quote funnel is blocked for as long as siteverify is down. That is exactly what the header says must not
happen.

The test (turnstile.test.ts) covers timeouts and throws as degraded. It has no case for a non-200 response.

**Smallest fix:** in `postSiteverify`, after the fetch, add
`if (res.status >= 500) return { configured: true, success: false, degraded: true };`.

## U02-3 · correctness · Two or more records that cannot be mapped answer `ok: true` with an empty list

`apps/web/lib/flight/aerodatabox.ts:333-345`

```ts
if (matching.length > 1) {
  const candidates: FlightRecord[] = [];
  for (const rec of matching) { const mapped = mapRecord(rec, number, date); if (mapped) candidates.push(mapped); }
  return { ok: true, action: "disambiguate", candidates, i18n_key: "quote.flight.pick_one" };
}
```

The one-record path refuses a record that cannot be mapped (`if (!single) return fail("not_found")`,
line 351). The two-or-more path does not.

**Failure scenario:** AeroDataBox returns two records for `LX318` on the day, and neither `arrival` has a
`runwayTime`, `revisedTime` or `scheduledTime` utc (for example cancelled legs). `mapRecord` returns null for
both. The answer is `ok: true`, "pick one", with `candidates: []`, so the widget asks the customer to choose
from nothing instead of falling back to manual time entry. Also, when exactly one of two records maps, the
customer is asked to "pick one" from a list of one.

The test (aerodatabox.test.ts:150) only covers two records that both map.

**Smallest fix:** after the loop, `if (candidates.length === 0) return fail("not_found"); if (candidates.length === 1) return { ok: true, flight: candidates[0] };`.

## U02-4 · polish · "Fail-open when the binding is missing" is false

`apps/web/lib/abuse/account-write.ts:3-6, 13-19`

The header says "Fail-open when the Workers binding is missing (local next)". But the code passes
`limiter: env.QUOTE_RATE_LIMITER_BARE` straight through. When that binding is undefined,
`checkWriteRateLimit` throws `TypeError` on `input.limiter.limit`. It catches that itself and returns
`rate_limited` (rate-limit.ts:172-176, fail-closed by design), so the outer `try/catch` never runs.

**Failure scenario:** in any environment where `getCloudflareContext()` works but the rate-limit binding is
not bound, every POST to `/api/manage/{cancel,time-change,flight,resend}` and `/api/account/prefs` answers
429. Two examples: `next dev` under initOpenNextCloudflareForDev, whose top-level wrangler config has no
ratelimits, and the `front` or `ops-changes` envs. The live `staging` and `production` envs do bind it
(wrangler.jsonc:152-160, 300-308), so live is not affected. `actions.ts:66-81` (`authWriteAllowed`) has the
same wrong comment and the same behaviour. `guards.ts:166-167` gets it right with `?? passLimiter()`.

**Smallest fix:** `if (!env.QUOTE_RATE_LIMITER_BARE) return null;` before the call, in both files. Or correct
both comments to say they fail closed.

## U02-5 · polish · A missing SUPABASE_URL or anon key quietly points session refresh at 127.0.0.1

`apps/web/lib/supabase/middleware.ts:11-18`

```ts
if (typeof url === "string" && url.length > 0 && ...) return { url, anonKey };
return { url: "http://127.0.0.1:54321", anonKey: "anon-placeholder" };
```

`server.ts:66-68` throws on the same misconfiguration. The middleware swaps in a local placeholder instead,
and logs nothing.

**Failure scenario:** a deploy where the `SUPABASE_URL` secret is missing or misspelled. Every request's
`updateSession` calls `auth.getUser()` against 127.0.0.1 from the Worker. That call fails, sessions are never
refreshed, and signed-in customers drop out when their access token expires. The logs carry no line naming
the cause.

**Smallest fix:** keep the placeholder only when `NODE_ENV !== "production"`. Otherwise emit one `log("error",
…, { reason: "supabase-env-missing" })` and return the response unchanged.

## U02-6 · polish · The magic-link sign-up server action drops the phone number

`apps/web/lib/auth/actions.ts:162-175`

`otpRequestSchema` accepts `phone` on the sign-up branch (schemas.ts:68, `signUpMagicSchema.phone`). The
`runOtp` input built here passes `firstName` and `lastName`, but not `body.data.phone`. `runOtp` stores the
phone only when it is given (run.ts:145).

**Failure scenario:** a magic-link sign-up through `SignInClient` → `requestOtpAction` with a mobile number.
The number never reaches `user_metadata.phone`, so `syncSignupPhone` has nothing to copy onto the customer
row. The live `/sign-in` is the DC mock posting `/api/auth` (middleware.ts:43-44), so this server-action
surface is a second, mostly unused auth path that has drifted from the route.

**Smallest fix:** add `phone: body.data.phone` to the sign-up branch. Or retire the server actions that
duplicate `/api/auth`.

## U02-7 · simplify · Dead "use server" module, with a weaker redirect check than the live one

`apps/web/lib/auth/staff-ops.ts` (whole file)

`staffListVerifiedFactor`, `staffMfaChallenge` and `staffMfaVerify` have no importer. The only reference is
`staff-ops-no-password.test.ts`, which reads the source text. The live MFA path is `staff-mfa.ts` behind
`/api/auth`.

It is still a "use server" module, so it should not linger. Its `next` check (line 90:
`next.startsWith("/") && !next.startsWith("//") && !next.includes("://")`) lets `/\evil.com` through. URL
parsers read a backslash as a slash in special schemes, so that becomes a protocol-relative open redirect.
redirect-target.ts:44 guards `/\` for exactly this reason.

**Smallest fix:** delete the file and its source-grep test. If it is kept, reuse `validateAuthRedirectTarget`.
