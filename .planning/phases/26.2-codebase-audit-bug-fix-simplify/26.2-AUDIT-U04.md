## U04-1 · money · A fixed coupon worth more than the fare charges the checkout extras the coupon should have covered

**Where.** The kernel caps a fixed coupon at the pre-coupon total:

```ts
// lib/pricing/policy.ts:235-238
if (coupon.amount_rappen !== null && preCouponTotal !== null) {
  if (coupon.amount_rappen > preCouponTotal) {
    amount = preCouponTotal;
    clamped = true;
```

So the lock's `class_totals[].total_rappen` is 0. Checkout then rebuilds the pre-coupon figure by adding the
coupon's full face value back on:

```ts
// lib/checkout/price-route.ts:155-156   (and lib/checkout/intent.ts:477-478, the charge)
} else if (coupon.amountRappen != null) {
  preCouponRappen = netRappen + coupon.amountRappen;
```

`checkoutCharge` (lib/checkout/checkout-charge.ts:94-109) then charges `max(0, fare + extras − fixed)` using
that inflated fare.

**How it fails.** Fare CHF 30.00, fixed coupon CHF 50.00, child seat CHF 10.00 ticked on /checkout.
- Kernel: coupon is capped at 3000, lock total = 0.
- Gross-up: pre-coupon = 0 + 5000 = 5000.
- Charge: max(0, 5000 + 1000 − 5000) = **CHF 10.00 + VAT**.
- D-34 says the coupon comes off fare plus extras: max(0, 3000 + 1000 − 5000) = **CHF 0**.

The customer pays CHF 10.81 they do not owe. The Fare row also reads CHF 50.00 for a CHF 30.00 ride.

The percent gross-up (`roundHalfUp(net*10000, 10000-p)`, price-route.ts:154, intent.ts:234-237,
ops/booking-change-price.ts:178-181) cannot undo a rounded discount exactly either. With a 10 % coupon, 4,500 of
the 45,000 pre-coupon figures from CHF 50.00 to CHF 499.99 come back one rappen out. Example: 5005 → 4504 → 5004.
The Fare row then shows CHF 50.04 instead of 50.05. With extras, the charge can be one rappen out too.

**Test cover.** No test in `lib/checkout/*.test.ts` covers a fixed coupon larger than the fare.

**Smallest fix.** Stop grossing up. In `classTotals` (pipeline.ts:491-498), pin `pre_coupon_rappen` for each
class in the lock. That is `sumPreCouponTotal` over the class lines without the coupon line, and it is already
HMAC-signed. Then read that figure in price-route.ts, intent.ts and booking-change-price.ts instead of
rebuilding it. A lock from before this change has no `pre_coupon_rappen`: refuse it with `price_changed` so
the browser asks for a new quote.

## U04-2 · security · A `coords` place lets the browser's own place text decide the airport fee and the city pair

**Where.** For `kind: "coords"` the server keeps the text the browser sent. It never looks the coordinates
up, so it has no airport flag, no city id and no canton:

```ts
// lib/quote/pipeline.ts:255-262
if (place.kind === "coords") {
  return { lng: place.lng, lat: place.lat, text: place.text, place_id: place.place_id };
}
```

`toQuoteInput` then sets `origin_is_airport: origin.isAirport === true` (false) and `origin_place: origin.text`
(pipeline.ts:361, 367). The kernel picks the zone from that text (`attachPlaceZones` → `zoneIdMatchingPlace`,
lines.ts:179-194: a substring match on IATA code or zone slug). The city-pair label fallback matches on the
same text (lines.ts:318-339). The airport fee fires only on `origin_is_airport` or an airport `zone_type`
(lines.ts:520-528).

The only gate is `coordsAllowed` (pipeline.ts:240-248, 541-546). It passes with a verified `vamos_qs` or any
suggest session the visitor has already opened, and every booking card opens one.

**How it fails.** POST `/api/quote` with pickup `{kind:"coords", lng:8.5492, lat:47.4502, text:"Kloten"}`
(Zurich airport) and a city drop-off sent the same way with text that matches no pair label.
- Directions bills the real metres, so the distance fare is correct.
- "Kloten" contains no `zrh` and no airport zone slug, so there is no zone, no airport fee line and no pair extra.
- The lock pins that text (pipeline.ts:725), and the intent re-run uses the same lock, so `recompute_pin` agrees.

The card is charged the fare without the airport pickup fee and without the route extra. The `retrieve` and
`pin` paths get these facts from Mapbox, so only `coords` is open. The only in-repo sender is the
BookingBoard fallback (components/home/BookingBoard.tsx:292-293, `lng: 0, lat: 0`). The Europe box refuses
that request, so closing the path breaks no real flow.

**Smallest fix.** In `defaultResolvePlace`, handle `coords` like `pin`: run `reverse` (count the Mapbox unit),
take `canton`, `cityId`, `cityName` and `isAirport` from Mapbox, and replace `text` with Mapbox's name. Or
refuse `coords` on `/api/quote` with `untrusted_input`. Better still, `attachPlaceZones` should never match on
text the client typed. Add a pipeline test: coords at ZRH with neutral text must still carry `airport_fee`.

## U04-3 · correctness · Confirmed (a): the airport fee and the route pair are folded into one "Fare" line

**What the kernel makes (correct).** `buildClassLines` (pricing/priceQuote.ts:197-242) emits separate lines
for each leg:
- `distance_fare` (`price.line.transfer`, start + per-km × all metres; lines.ts:473-516)
- `airport_fee` (kind `surcharge`, `price.line.airport_fee`, amount `airport_start_rappen`; lines.ts:549-582)
- `fixed_route` (kind `extra`, the one city or canton pair; lines.ts:398-462)
- any leg surcharges

Then the return discount and the coupon. The quote response carries all of these in `classes[].lines`.

**What the customer sees.** The checkout price comes from `/api/checkout/price` → `checkoutCharge`, which
builds one fare line from the lock's class total:

```ts
// lib/checkout/checkout-charge.ts:118-126
const lines: ChargeLine[] = [
  { kind: "fare", code: "distance_fare", i18n_key: "price.line.transfer",
    params: { vehicleClass: input.vehicleClassSlug }, amount_rappen: fareRappen },
];
```

`fareRappen` is `classNetRappen`, which is distance fare + airport fee + pair extra + automatic surcharges −
return discount. SummaryRail renders that line as `t("fareExVat")`, which reads "Fare" in English
(app/[locale]/checkout/sections/SummaryRail.tsx:78-79). Only the extras ticked on /checkout, the coupon and VAT
get rows of their own.

The same single line goes into `price_snapshots.lines` through `snapshotLinesFromCharge`
(lock-to-rpc.ts:196-233). The confirmation receipt and the stored audit row therefore lose the airport fee
and the pair extra as well. The legacy `snapshotFareLines` (lock-to-rpc.ts:132-176) and the staff test
booking (test-unpaid/route.ts:74) do the same.

**Built but not wired.** pipeline.ts:454-489 signs `price_rows` (airport_fee + fixed_route per class) into the
lock "so checkout can show them as their own rows". lib/checkout/price-rows.ts has `breakdownRows`,
`breakdownRappen` and `peekLockPriceRows` for exactly that. Grep finds no caller outside price-rows.test.ts.

**How it fails.** Pickup ZRH → Zurich city, Business. The quote has `distance_fare` X, `airport_fee` Y and
maybe `fixed_route` Z. Checkout shows "Fare CHF (X+Y+Z)", then VAT, then Total. That breaks UI-SPEC §8, cited
in price-rows.ts:1-3: "every component of the charge is a labelled line the customer can point to". The
amount charged is correct.

**Smallest fix.** In `checkoutCharge`, accept the lock's `price_rows` for the chosen class (or the kernel
lines) and emit each as its own `surcharge` line with its i18n key. Subtract their sum from the fare line, as
`breakdownRappen` was written to do. The coupon and VAT arithmetic stay the same. `snapshotLinesFromCharge`
then stores them unchanged. The "Airport pickup fee" key already exists in four languages (seed.sql:2754),
and the pair label keys are in price-rows.ts.

## U04-4 · correctness · The generic rule writer still double-encodes

**Where.**

```ts
// (ops)/api/staff/rate-book/route.ts:1041, 1062-1065
const payloadObj = rec(recBody.payload) ?? recBody;
const payload = JSON.stringify({ hours: ..., ...payloadObj });
// :1087            payload = ${payload}::jsonb
// :1093            values (${versionId}, ${ruleKind}, ${payload}::jsonb)
```

The same file states the mechanism at :935-938, and lib/checkout/stripe-event-record.ts:6-10 states it too.
Through the Worker client (`fetch_types: false`, prepared statements), `${JSON.stringify(x)}::jsonb` stores a
JSON **string**. The parent fixed the `city_pair` branch of this route, but this branch writes every other
rule kind (`quote_lock`, `lock`, anything typed).

**How it fails.** You save a quote-lock rule on /pricing. `rate_version_rules.payload` becomes
`"{\"hours\":2}"` (`jsonb_typeof` = `string`). Today's readers cope: `rulePayload` (:297-307) and `mockRules`
(:395-405) parse strings, and no SQL function reads the column. But `payload->>'hours'` in any future SQL
returns NULL. The completeness gate `r.payload = '{}'::jsonb` (lib/ops/pricing.ts:166) can never match a
string either, and `{hours: null}` makes the payload non-empty anyway.

When the body has no `payload` key, :1041 also stores the whole request body (`kind`, `id`, `ruleKind`, ...)
as the payload.

**Smallest fix.** Build the payload as an object, `{ hours, ...rec(recBody.payload) }` with no `recBody`
fallback. Send it as `tx.json(obj)` and drop the `::jsonb` casts at :1087 and :1093, the same pattern as
:902 and :939. Rows already stored as strings need a one-off
`update ... set payload = (payload #>> '{}')::jsonb where jsonb_typeof(payload) = 'string'`. That needs a
migration number from the controller and is the owner's call.

## U04-5 · correctness · Mapbox Directions down plus an airport pickup gives a 500, not the CHF 000 board

**Where.** On a Directions failure the pipeline carries on with no metres on purpose:

```ts
// lib/quote/pipeline.ts:637-652
if (!routed.ok) {
  // Mapbox down / no token: no metres. Do not invent km.
  state.routed = inputs.map(... distance_m: 0, duration_s: 0, ... road: false);
  return { ok: true };
}
```

With 0 metres the fare line's amount is null (lines.ts:479-485). The airport fee still carries
`distance_rate.airport_start_rappen` (lines.ts:580), and a matched pair still carries `price_rappen`
(lines.ts:460). `assembleTotals` treats null mixed with priced amounts as `partially_priced`
(priceQuote.ts:93-101). Then `loadAndPrice` returns `partially_priced_class` (engine.ts:232-234), which is
HTTP 500 "quote.error" (errors.ts:164-167).

**How it fails.** The pickup is Zurich airport (the main product route), `airport_start_rappen` is set on the
live book, and Mapbox Directions times out or the token is missing. The customer gets a 500 toast, where
D-26 intends a CHF 000 board.

The test that pins D-26 (pipeline.test.ts:306) uses a book with no airport and no pair, so it passes. Any
active `always` or night `amount` surcharge with a figure causes the same 500 on any route.

**Smallest fix.** In `buildClassLines` (priceQuote.ts:197-242), when `fare.amount_rappen === null`, set every
leg line built after it to `amount_rappen: null`: the airport fee, the pair extra and the amount surcharges.
The class then reads all-null (CHF 000), not mixed. Add the airport case to pipeline.test.ts:306.

## U04-6 · polish · A whole number means rappen and a decimal means francs

**Where.**

```ts
// lib/ops/rappen.ts:14
return Number.isInteger(value) ? value : Math.round(value * 100);
// :18
const n = Number(value.trim().replace(",", "."));
```

**How it fails.**
- `rappenFromMoneySet({CHF: 25})` gives 25 (CHF 0.25), while `{CHF: 25.5}` gives 2550 and `{CHF: "25"}` gives 2500.
- The string `"1,250"` gives 125 (CHF 1.25), because the comma is read as the decimal mark.

Today the /pricing mock sends form strings (app/ops/OpsPricing.dc.html:1474 `{ CHF: rec.baseFare }`), so the
number branch is not reached from the UI. It is reached by any API caller or future form that sends a JSON
number. rappen.test.ts pins only the string forms.

**Smallest fix.** Rappen enter only through the `*Rappen` fields (integers). The money-set path always reads
francs, with numbers too: `Math.round(value * 100)`. Refuse a string with more than one separator, or a
comma followed by exactly three digits, rather than guessing.

## U04-7 · polish · The test unpaid booking is priced from the draft but its snapshot names the live price book

**Where.** The amounts come from `priceDraftPreview`, which reads the draft book
(test-unpaid/route.ts:44 → lib/ops/draft-preview.ts:284). The snapshot sets `rate_version_id: live.id`
(:56, :68).

**How it fails.** A test booking made while the draft has a different per-km rate is stored as "priced by
price book row <live id>" at a figure that row never produces. The header (:5-6) says this is deliberate
because the charge gate needs a live id. The booking is `is_test`, so no customer is charged. The cost is
an audit row that misstates which book priced it.

**Smallest fix.** Add `draft_rate_version_id` to the snapshot policy (or `params`) so the row names both, or
leave it and note it in the ops docs. This is the owner's call.

## Paths found clean

- **Integer kernel** (pricing/round.ts). Integer ratio half-up, safe-integer guards, percent parsed by regex
  into hundredths. Metres throughout, and `perKm` divides by 1,000. No float, no cents/francs mix, no km/m
  mix in the kernel.
- **Exactly one pair extra.** lines.ts:418-441: `fixed = city ?? canton`, and the zone-id fallback runs only
  when neither matched. Same-place guards are at :303, :326, :362 and :428. At most one pair extra per leg,
  matching in both directions, and nothing when there is no match.
- **No surcharge applied twice.** Leg surcharges skip quantity rows (lines.ts:667). Extras skip non-quantity
  rows (:816). `manual` never applies in the quote (predicates.ts:188-195). Legacy string predicates map to
  manual (rateBook.ts:181-184). A percent surcharge comes off its own leg's fare line only.
- **Coupon order and sign.** The coupon comes after the return discount and after extras
  (priceQuote.ts:256-273), and is capped at the pre-coupon total (policy.ts:219-238). Checkout takes it off
  before VAT. Every percent is bounded 0-100 in the database (rate_versions.sql:194, coupons.sql:15,
  settings.sql:73), so the return discount cannot exceed the fare sum and no total can go negative. U04-1 is
  the one failure.
- **The server sets the price** (apart from U04-2). The schema refuses client price and airport fields
  (schema.ts `FORBIDDEN_CLIENT_PRICE_FIELDS`). `fare_kind` is never read for money. The lock is HMAC-signed
  and the reprice keeps metres from the lock (pipeline.ts:813-870). The intent compares the re-run with the
  pin (quote/intent.ts:215-240). Extras are codes only, priced from the live catalogue
  (checkout-charge.ts:74-88).
- **Eligibility** (pricing/eligibility.ts), **public board** (public-board.ts) and **rateBook mapping**:
  nothing wrong found.
- **Staff routes**: `rate-versions` (list and create), `[id]`, `[id]/clone`, `[id]/discard`,
  `rate-book/preview`. Admin and staff wrapping is in place, the SQLSTATE mapping is in place, and none of
  them do money arithmetic.
