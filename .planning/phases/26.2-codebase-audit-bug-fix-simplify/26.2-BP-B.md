## Database notes (words only, no migration written)

- **B1, remainder.** The Worker fix closes an already open Stripe payment page. It does not close a sent pay link: `checkout_pay_link_by_hash`, `checkout_pay_link_state` and `checkout_pay_link_lines` (20260928140000, 20260930170000) select on `status in ('pending','quote')` and never on `erased_at`, so the customer can open the link again and get a new payment page for an erased booking until the 24 hour hold ends. `checkout_payment_settle` (20260930100000) also confirms an erased booking. A full fix is a new migration that adds `and b.erased_at is null` to the three pay-link functions (and decides what settle does with a payment for an erased booking: today it would confirm it). That is a database change and a behaviour choice, so it is not done here.
- **B9, check on a database.** The five new lookups in `draftRowId` (`rate-book/route.ts`) were only run against the stand-in. They need one run on a real database before the fix ships. Read-only check on live, with `<id>` the id of the extra in price book row 18 and `<draft>` the id of the open draft (skip if there is none): `select n.id from public.surcharges n join public.surcharges o on o.code = n.code where o.id = <id> and n.rate_version_id = <draft> order by (n.id = o.id) desc, n.id limit 1;` It must return the id of the same extra in the draft. The other four have the same shape on `distance_bands` (class and `from_km`), `rate_version_rules` (`kind` and `payload`), `fixed_routes` (both ends and class) and `distance_rates` (class).

## Seen on the way, not part of a row (no change made)

- `edit-request.ts:104-116` `resolveBookingId` reads `public.bookings` directly as the system role (`:145-146`). That role has no table rights on live (`lib/db/system-reads.ts:3-7`), so this would answer 42501. It is only reached when `edit-accept` is called without `requestId`; the dashboard always sends one.

If Stripe refuses, the cancel still answers OK; the booking's refund is marked failed in the database by `applyStripeRefund` itself, so the board shows it. Not changed (not the reported row, and the answer of a cancel is a choice).
- B9, page side: after a single-row answer the page keeps the ids it loaded and adds the saved row next to the old one until the next full load (`app/vamos-ops-data.js:366-383`). The page is read only for this group. With the route fix both ids write the same draft row.
