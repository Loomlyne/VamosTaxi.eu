# 26.2 audit, unit 06: React components (`apps/web/components/**`)

Scope: every file under `apps/web/components/**` except `forms/TimePicker.tsx`, which another session owns. This was a read-only audit: I edited no file, started no server and ran no git write. Line numbers refer to the `audit-26-2` worktree.

**Which code customers actually reach.** The public-host middleware (`apps/web/middleware.ts:32-51, 665`) always serves the DC mock for `/`, `/about`, `/faq`, `/contact`, the legal pages, `/sign-in`, `/sign-up`, `/reset-password`, `/account` and `/bookings`. The React home page returns `null`. Customers only see the React components on `/checkout*`, `/confirmation*`, `/checkout/pay/*`, `/review` and 404 pages, plus the shell on those pages (header, footer, cookie banner and the contact button, `ContactFab`). Each finding below is tagged **live** or **dormant**. A dormant finding is a real bug in code that no customer reaches today.

**Folders with no findings:** `data`, `feedback`, `marketing`, `navigation`.
The other ten folders have findings: `auth`, `booking`, `checkout`, `consent`, `core`, `forms`, `home`, `legal`, `shell`, `transfer`.

## Correctness

### U06-1 · correctness · live: the receipt drops or mislabels owner-added extras
`booking/BookingVoucher.tsx:153-158, 189-259`, which calls helpers in `lib/checkout/confirmation-receipt.ts:6-10, 110-122, 126-160`.

**What is wrong.** The voucher builds its money lines from `extrasOnReceipt`, `extraRappenByCode` and `receiptPriceSplit`. All three keep only `EXTRA_CODES = { child_seat, oversized_luggage, extra_stop }`, and all three are marked `@deprecated 26.3 D-35 — use receiptRows; removed by plan 26.3-14`. The project's rule is that extras are generic dashboard surcharges, and no behaviour may depend on an extra's name.
- **Split branch** (a total exists): `fareRappen = gross − vat − extraSum(known only) + discount`. A surcharge with any other code is folded into "Fare ex VAT".
- **Fallback branch** (no total): an unknown line falls through to line 247-248 and is labelled `t("transferClass", { class })`, so it reads like a second "Economy transfer".

**Failure scenario.** The owner adds an extra `meet_greet` at CHF 20 on the dashboard. A customer books with it. The trip later completes, is refunded or is cancelled, so the confirmation page renders `BookingVoucher`. (`ConfirmationClient.tsx:641-651` uses it whenever the booking is not `booked`.) The receipt then shows no "Meet and greet" line, and the fare is CHF 20 higher than the class price. On the fallback path it shows two "Transfer · Economy" lines instead. The two equal labels also collide as React keys (see U06-17).

**Smallest fix.** Build the lines from `booking.receipt.rows` (`receiptRows`), as `BookedCard` already does. Then delete the four deprecated helpers.

### U06-2 · correctness · live: flight lookup stays pinned to the wrong day
`booking/FlightField.tsx:52-57, 64`. The host is `checkout/sections/ContactSection.tsx:128-133`, and `checkout/CheckoutPage.tsx:303-346` keeps that section mounted while the trip editor is open.

**What is wrong.**
```ts
const [choice, setChoice] = useState<"today"|"tomorrow"|"trip">(
  tripDate === tomorrow ? "tomorrow" : tripDate === today ? "today" : "trip");
const lookupDate = choice === "tomorrow" ? tomorrow : choice === "today" ? today : tripDate;
```
`choice` is computed once, at mount. If the trip date later changes, `choice` stays `"today"` or `"tomorrow"`, so `lookupDate` ignores the new date.

**Failure scenario.**
1. A customer opens /checkout with tomorrow's trip. `choice` is set to "tomorrow".
2. The customer types LX 318.
3. They reopen the trip editor at the top of the page and change the date to next Friday. `ContactSection` stays mounted.
4. When they retype the flight, the lookup still asks for tomorrow. The card shows tomorrow's status ("already departed" or "cancelled") and tomorrow's landing time, and "Use" fills that in for a Friday trip.

**Smallest fix.** Add `useEffect(() => setChoice(tripDate === tomorrow ? "tomorrow" : tripDate === today ? "today" : "trip"), [tripDate])`. Alternatively, keep only an override that resets when `tripDate` changes.

### U06-3 · correctness · dormant: the sign-in form's messages are label words and raw codes
`auth/AuthForm.tsx:56, 123-125, 140-149, 192-204`. This is dormant because the middleware serves the DC mock at `/sign-in`.

**What is wrong.**
- `if (!password) next.password = tCommon("password");` The error message is just the word "Password".
- `banner === "credentials"`: the Alert title is "Check the email address" and its body is `{tCommon("password")}`, which is "Password". The `"registered"` banner is titled "Create an account", with the body "Sign in".
- `<p className="sr-only" aria-live="polite">{banner ?? stage}</p>` announces the raw values `credentials`, `registered`, `form` or `sent` in every language (Law 03 and a11y).
- The method toggle (line 197) and the forgot-password link (line 202) are both labelled `tAuth("send-a-new-link")`, but they do different things.

**Failure scenario.** A user enters a wrong password. A screen reader says "credentials". The page shows a red box titled "Check the email address" with the single word "Password" underneath. Two adjacent buttons both say "Send a new link".

**Smallest fix.** Use real message keys for the credentials and registered banners and for the empty-password error. Map the banner and stage values to translated sentences, or leave the live region empty. Give the method toggle its own key, for example "Email me a sign-in link".

### U06-4 · correctness · dormant: "Sign in" after a password reset drops the locale
`auth/ResetForm.tsx:43, 59`.

**What is wrong.** `<Button … href="/sign-in">` renders a plain `<a href="/sign-in">`, not the next-intl `Link`.

**Failure scenario.** A German user finishes the reset at `/de/reset-password`, presses "Anmelden", and lands on the English `/sign-in`.

**Smallest fix.** Build the href with `getPathname({ href: "/sign-in", locale })`, as `ContactForm.tsx:106` does, or render the next-intl `Link`.

## Accessibility

### U06-5 · a11y · live: the mobile menu sheet traps nothing and loses focus
`shell/SiteHeader.tsx:205-213` (`finishClose`), `245-280` (effects) and `408-419` (the sheet).

**What is wrong.** The sheet is `role="dialog" aria-modal="true"`, and focus moves to its close button (line 279). But there is no Tab or Shift+Tab containment. Closing it (`finishClose`) never puts focus back on `[data-hd-menu-btn]`. Compare `SiteHeaderAccount.tsx:118`, which does restore focus, and `BookingCard.tsx:57-88`, which has a working trap.

**Failure scenario.** At 390 px on /checkout, a keyboard or switch user opens the menu. Pressing Tab past "WhatsApp" moves focus into the page under the scrim, where it is invisible because body scroll is locked. Pressing Escape closes the sheet and drops focus to `<body>`.

**Smallest fix.** Add the same Tab/Shift+Tab wrap as `BookingCard` inside the existing `[menuOpen]` effect, and focus the menu button in `finishClose`. The shared hook in U06-26 would cover this.

### U06-6 · a11y · live: the cookie preferences dialog has no Tab trap
`consent/CookieBanner.tsx:181-189, 395-414`.

**What is wrong.** The dialog is `aria-modal="true"`. Focus moves into it and Escape closes it, but Tab walks out to the page behind the veil. Separately, after a choice on the banner card (lines 381-389), the button that had focus unmounts. `closeSheet()` then has no opener to return to, so focus falls to `<body>`.

**Failure scenario.** On /checkout, a keyboard user opens "Manage preferences" and tabs past "Accept all". Focus lands on the hidden checkout form behind the veil. A user who instead presses "Necessary only" on the card is left with focus on `<body>` at the top of the page.

**Smallest fix.** Add a Tab wrap in the `[sheetOpen]` effect. After a successful card choice, focus the page's `<main>` or the element that had focus before the card appeared.

### U06-7 · a11y · live: field errors and hints are not tied to their inputs
`forms/Input.tsx:40, 95, 100-108, 123-130`; `forms/Select.tsx:85-98, 125-132`; `forms/Textarea.tsx:73-90`; `forms/PhoneField.tsx:34, 64-89`.

**What is wrong.**
- No field sets `aria-describedby` on the control. The error or hint `<span>` has no id. A grep finds `aria-describedby` only in `AccountChoice`.
- `Input` takes `required` out of the props, renders a visible " *" that is not `aria-hidden`, and never passes `required` or `aria-required` to the `<input>`. `PhoneField` also takes `required` out and never passes it on.

**Failure scenario.** At checkout (`ContactFields` → `Input`/`PhoneField`), a customer presses PAY with a bad email. Tabbing back to the field, the screen reader says "Email, invalid entry" but never reads the message ("Check the email address") or the hint. Required fields are announced as "First name star" and not as required.

**Smallest fix.** Give the error and hint spans `id={`${fid}-msg`}`, and set `aria-describedby` on the control. Pass `required` (or `aria-required`) through to the input, and mark the asterisk `aria-hidden`. That is about four lines per control.

### U06-8 · a11y · live: the flight result is not announced, and its radiogroup is misnamed
`booking/FlightField.tsx:165-175`.

**What is wrong.** "Checking…", "not found" and the match sentence appear inside `role="group"` with no live region. The day choice is `role="radiogroup" aria-label={t("today")}`, so the group is named "Today".

**Failure scenario.** A screen-reader user types a flight number and waits. Nothing is announced while the lookup runs or when the card appears. When the user reaches the day choice, it is introduced as "Today, radio group".

**Smallest fix.** Put `aria-live="polite"` on the status paragraph's container. Use a proper group label key, for example "Which day does it land".

### U06-9 · a11y · dormant: the contact form loses focus while sending
`forms/ContactForm.tsx:386-398`.

**What is wrong.** While `sending`, the submit `<Button>` is replaced by a plain `<span>` that is not a live region. The focused element is removed from the page.

**Failure scenario.** A keyboard user presses "Send message". Focus drops to `<body>` and nothing is announced. On the `unavailable` or `challenge-failed` outcomes, focus stays lost.

**Smallest fix.** Keep the button mounted with `disabled` and `aria-busy`, and swap only its label. This is the pattern `PayBar.tsx:95-116` already uses.

### U06-10 · a11y · dormant: the date picker's month arrows do nothing and have no name
`forms/DatePicker.tsx:176-190`. The `BookingBoard.tsx:186-194` refusal view passes `prevMonthLabel=""` and `nextMonthLabel=""`.

**What is wrong.** Both arrow buttons have no `onClick`, and their `aria-label` is `undefined` or `""`. The refusal view also renders an operable calendar with a made-up month (31 days, `firstDow=5`) and eight hard-coded times.

**Failure scenario.** Any consumer opens the popover. A screen reader announces two unnamed buttons that do nothing. Today the only consumers are the dead `BookingBoard` and dev galleries (U06-23 and U06-24).

**Smallest fix.** Delete `DatePicker` together with `BookingBoard`. If it is kept, wire `onPrevMonth`/`onNextMonth` and require the labels.

### U06-12 · law (icon law + RTL) · dormant: `→` used as an icon
`home/BookingCard.tsx:93` (`` `${pickup} → ${destination}` ``) and `forms/WhenPicker.tsx:288` (`<span className="vt-when__arrow">→</span>`, range mode only).

**What is wrong.** CLAUDE.md says to never use `→` as an icon. In Arabic, the arrow points against the reading direction. The `BookingCard` string is also not wrapped in `vt-dir-keep`, so bidi reorders it.

**Reach.** `BookingCard` renders only in `/dev/home/hero`, and range mode is unused because V1 is one-way.

**Fix.** Use `<Icon name="arrow-right" />` with a logical-direction flip, or the `arrow-left-right` glyph.

### U06-13 · law (Law 03) · dormant: WhenPicker defaults to visible English
`forms/WhenPicker.tsx:93-101`.

**What is wrong.** The defaults are `groups = ["Morning","Afternoon","Evening"]`, `legLabels = ["Pickup","Return"]`, `timeTitle = "Pickup time"`, `timeTitle2 = "Return time"`, `savedLabel = "Saved"`, `clearLabel = "Clear"`, `saveLabel = "Save"`, `prevMonthLabel = "Previous month"` and `nextMonthLabel = "Next month"`. `DatePicker`, `Counter`, `Dialog` and `Toast` deliberately have no English fallbacks. Today both live callers (`TripEditor.tsx:324-343` and `BookingCard`) pass every non-range label. `legLabels` and `timeTitle2` would leak the first time range mode is used.

**Fix.** Remove the English defaults and make the props required, or default them to `""`.

### U06-14 · law (Law 03) · dormant: other hard-coded English names

**Fix.** Turn these into required label props, or translation keys with no default.

### U06-15 · law (owner rule) · dormant: the legal page has a Language row

## Polish

### U06-16 · polish · live: hand-built locale hrefs cost English customers a redirect
`checkout/AccountChoice.tsx:133, 138` (`` `/${locale}/terms` ``, `` `/${locale}/privacy` ``) and `checkout/CheckoutSignIn.tsx:210` (`` `/${locale}/sign-in?returnTo=…` ``).

**What is wrong.** Routing uses `localePrefix: "as-needed"`, and `i18n/routing.ts` itself says `/en/...` answers 308. So English customers always take one redirect hop, and links that open in a new tab get a non-canonical URL.

**Fix.** Use `getPathname({ href, locale })`, as `ContactForm.tsx:106` does.

### U06-17 · polish · live: list keys built from label strings collide
`transfer/PriceSummary.tsx:101`, `transfer/RouteSummary.tsx:109` and `transfer/VehicleCard.tsx:116` all use `key={typeof label === "string" ? label : i}`.

**What is wrong.** Two lines with the same text get the same key. The U06-1 fallback branch produces exactly that ("Transfer · Economy" twice), and React then warns and may reuse the wrong row.

**Fix.** Key by index plus kind, or have callers pass a `key`/`id` on each line.

### U06-18 · polish · live: block content inside the class-card button
`transfer/VehicleCard.tsx:75-99`.

**What is wrong.** `<button>` contains `<h4 className="vt-veh__name">` and `<p className="vt-veh__examples">`. A button may only contain phrasing content, so heading navigation lands inside a button. This is used by the checkout `ClassSection`.

**Fix.** Use `<span>` with the same classes. A screen reader then reads the name as the button text.

### U06-19 · polish · live: the refund line on the voucher is not localised
`booking/BookingVoucher.tsx:92-96, 288-294, 459`.

**What is wrong.** `payoutDate()` returns the raw ISO date `2026-10-05` into `stripePayoutOn`. The refund copy is then joined with a literal `". "`. The date is not wrapped in `vt-dir-keep`, so it reorders in Arabic, and the full stop is outside the translation.

**Fix.** Format the date with `Intl.DateTimeFormat` for the locale, as `formatPaidAt` does. Move the joiner into the message.

### U06-20 · polish · live: a computed-style read on every icon render
`core/Icon.tsx:89-94`, `core/Logo.tsx:14-19` and `core/CheckerMark.tsx:13-18`.

**What is wrong.** Every render calls `getComputedStyle(document.documentElement).getPropertyValue("--vt-icon-base")`, and likewise for the logo and pattern variables. Only test harnesses set these variables. The app never does, so the result is always the fallback, at the cost of a computed-style read for every icon on checkout.

**Fix.** Use the constant base path, or read the variable once at module level.

### U06-21 · polish · live: the account choice shows one value while the host holds another
`checkout/AccountChoice.tsx:68`.

**What is wrong.** When `createAvailable` becomes false while `value === "create"`, the component draws "guest" as checked but never calls `onChange("guest")`. `ContactSection.tsx:55` derives `createAvailable` from `f.createHidden`, which can flip at runtime. The host's PAY rules (`CheckoutForm.tsx:806-808`) receive both values, so this is a display/state split, not a proven wrong charge.

**Fix.** Have the host normalise the value (`if (!createAvailable && choice === "create") setAccountChoice("guest")`), and drop the masking in the component.

## Checked and not reported
- **Locale/event subscriptions.** Every listener, observer, interval and timeout has its cleanup. (`HowItWorks.tsx:93` leaves an unchecked 120 ms resize timeout, which is harmless and dev-only.) There is no `VamosLocale` subscription in this unit; `locale-shim` handles that.
- **Laws 01 and 02.** No `--vt-shadow-accent`, no yellow-50 to 300 or 600/700, and no coloured `box-shadow`. The three `outline: 3px solid rgb(253 194 11 / .45)` rules (`WhyVamos.css:188`, `SiteFooter.css:63`, `CookieBanner.css:138`) copy the `--vt-ring` colour exactly; they are not invented.
- **Scrolling.** No scroll library. `WhyVamos` and `WhenPicker` scroll handlers write no custom property on `<html>`. `CookieBanner` writes `--vt-ck-reserve` from resize and `ResizeObserver` only.
- **Pickup time slots.** `WhenPicker` offers ten fixed pickup times on live checkout. These match the home DC mock's own `slots` list (`home.dc.html:2282`), so this is the signed design, not a component bug. Whether it should change is the owner's call.
- **Sign-out and the header.** Signing out redirects to `/`, which is served by the DC mock, so the browser does a full navigation and the header's cached session snapshot cannot go stale.
