## U07-1 · correctness · Dashboard redirects that depend on sign-in state are 308 with no Cache-Control

**File:**
- `apps/web/middleware.ts:396`: signed out, any console path redirects to `/login` with `NextResponse.redirect(loginUrl, 308)`
- `:379`: signed in, `/` redirects to `/dashboard` with 308
- `:328`: the same redirect on ops-changes
- `:317`: `/ops/*` redirects with 308

None of these get a `Cache-Control` header. `applyStagingNoindex` adds the security pairs and `X-Robots-Tag` only (`lib/security/headers.ts:17-27`). `applyPublicCacheHeaders` is never applied on the dashboard host. `worker.ts` and `dashboard-gateway.ts` add nothing either.

**What is wrong:** 308 is a permanent redirect and is cacheable by default. Browsers keep it with no expiry and never ask the server again. Here the target depends on whether the visitor is signed in, so one URL gives different answers at different times, and the browser remembers only the first.

**Failure scenario:**
1. The owner, signed out, opens a bookmark to `https://dashboard.vamostaxi.site/dashboard`.
2. He gets a 308 to `/login`, and the browser caches it.
3. He signs in. `ops-login` navigates to `/dashboard` only after `result.ok`.
4. The browser answers `/dashboard` from its cache with `/login` again, without asking the Worker. He is back on the sign-in page.
5. The same happens to `https://dashboard.vamostaxi.site/`: the first visit was signed out (308 to `/login`), so every later visit to `/` goes to `/login` even with a session.

The only fix on his side is clearing the browser cache for the site.

**Tests:** `tests/unit/ops-dashboard-host.test.ts:24-27` checks that the source says `308`. It does not check whether 308 is correct, so it does not contradict this finding.

**Smallest fix:**
- Use 302 (or 307) for the two redirects that depend on state: `:379` and `:396`, plus `:328` for symmetry.
- Set `Cache-Control: private, no-store` on all four dashboard redirects.
- Keep 308 only for a fact that never changes, if one is wanted (for example `/ops/*` → `/login`, but that also needs `no-store`).
- Update the regex in the test.

## U05-1 · security (low) · Review photo upload: no rate limit, public before publication, 500 on a bad body

**File:** `apps/web/app/api/reviews/photo/route.ts`
- `:57-60`: no rate limit runs before the body is read.
- `:60`: `await request.formData()` is not wrapped in a try/catch.
- `:117-120`: each POST writes a new R2 object `reviews/<bookingId>/<uuid>.<ext>`.

`apps/web/app/photos/[...key]/route.ts` serves any key that `isReadablePhotoKey` accepts (`lib/ops/photos.ts:141-146`, which checks only the prefix). Nothing checks that a review exists or has been published.

**What is wrong:**
- Every sibling account and manage write runs `accountWriteForbidden` (`lib/abuse/account-write.ts`), and `reviews/submit` runs `checkWriteRateLimit`. This route runs neither.
- An uploaded photo can be read at `/photos/<key>` as soon as it is stored. That holds even if the review is never submitted, or is rejected or deleted on the dashboard.

**Failure scenarios:**
1. A customer with one paid booking, or anyone holding its manage token, loops `POST /api/reviews/photo` with a 5 MB JPEG. Each request stores another 5 MB in R2 under a new UUID, without limit. Each response returns the key, which is then a public, Vamos-hosted image URL.
2. A photo the owner rejects on the dashboard stays reachable at its URL.
3. A request with `content-type: multipart/form-data` and a truncated body makes `formData()` throw, so the route answers 500 instead of 400.

The UUID keys cannot be guessed, so this is abuse and cost, not a data leak.

**Smallest fix:**
- Call `const limited = await accountWriteForbidden(request); if (limited) return limited;` after the CSRF check.
- Wrap `request.formData()` and return `jsonErr("invalid-input", 400)` when it throws.
- Optionally, add a later job: `/photos/reviews/*` serves only keys referenced by a published review, or orphaned uploads are swept.

## U07-2 · polish (legal / i18n) · Internal "Client input" notes are live on the public imprint

**File:**
- `app/pages/imprint.dc.html:222-246`: three `data-slot="1"` blocks, for licence, dispute body, and content and links.
- `:352`: `slotNotes: (this.props.showSlotNotes ?? true) !== false`, so the notes are on by default.

This mock is the live `/imprint` (`middleware.ts:44`, `DC_PAGES`). The Next twin is `apps/web/app/[locale]/imprint/page.tsx:169-210`, which never renders (see U07-4).

**What is wrong:** The kicker ("Client input · licence") and the reviewer notes appear on the public page. One example: "Carrying passengers in the Canton of Zurich requires a licence … Both are missing from the previous site." They exist only as `de` and `en` spans inside `data-vt-no-i18n`. The page declares `data-vt-legal="en de fr ar"`, so `/fr/imprint` and `/ar/imprint` (indexable, listed in the sitemap with hreflang) show Latin-script reviewer copy inside an RTL page.

The rule that client-input notes stay English is meant for review scaffolds. These notes are on a public, indexed legal page, and that is the problem.

**Failure scenario:** A visitor or Googlebot opens `https://vamostaxi.site/ar/imprint`. They see the internal note saying the licence number is missing from the previous site.

**Smallest fix:** Default `showSlotNotes` to `false` on the public page, or replace each block with the standard `data-tok` TBC pill ("licence number TBC"). Make the same change in `imprint/page.tsx`.

Note: another session has uncommitted edits to `imprint/page.tsx` and `PendingSlot.tsx` in this worktree (U11). Coordinate before fixing.

## U05-2 · polish (latent) · Cancel route accepts only 4-digit references

**File:**
- `apps/web/app/api/account/bookings/cancel/route.ts:32`: `/^VT-\d{2}-\d{4}$/i`

- `reviews/submit/route.ts:19` and `reviews/photo/route.ts:21` both use `\d{4,5}`.

**Failure scenario:** Once five-digit references exist, `VT-26-10001` passes the database check. `POST /api/account/bookings/cancel {"ref":"VT-26-10001"}` then answers 400 for the customer's own booking. Today the generator cannot produce five digits (see "Outside scope"), so this is latent.

**Smallest fix:** Use `\d{4,5}`, or better, one shared `BOOKING_REF` constant used by all three routes.

## U07-4 · simplify · Most public Next pages never render on the live site

**File:** `apps/web/middleware.ts:33-53` (`DC_PAGES`) and `:665-678`.

`dcMockPath()` matches `/`, about, faq, contact, terms, privacy, cookies, cancellation, imprint, sign-in, sign-up and reset-password in every locale before `handleI18nRouting`, then serves the `.dc.html` mock. As a result:
- Each of those Next pages' `generateMetadata` is dead on the public host.
- `buildAlternates()` (`lib/metadata.ts:76-81`, which also emits four identical alternates for routes that are not indexable) is dead there too.
- So is the FAQ JSON-LD at `faq/page.tsx:316-331`.

The live head and hreflang come only from `lib/seo/head.ts` `applySeoToHtml`. Only `/review`, `[...rest]`, `not-found` and `error` reach Next. Memory already records this ("Live home and legal pages are DC mocks"), but the code does not say it.

**Consequence:** A fix made in these Next pages has no effect on the live site. U07-2 is an example: its Next twin is also wrong but invisible.

**Fix:** Either delete the shadowed Next pages, or put a one-line header in each saying "shadowed by DC_PAGES; edit app/pages/<name>.dc.html". Separately, drop `languages` from `buildAlternates` when `seoPageFor(path)?.indexable` is false.

## Outside scope (for the database owner): the reference generator truncates at 10,000

**File:** `packages/db/supabase/migrations/20260823000010_bookings.sql:65`. `format('VT-%s-%s', …, lpad(n::text, 4, '0'))`.

Postgres `lpad` cuts a longer string down to the given length. `lpad('10000', 4, '0')` is `'1000'`. The function allows `n` up to 99999 (`:59`), but the 10,000th booking of a year gets `VT-26-1000`, the same reference as booking 1,000. That insert then fails on the reference unique key.

**Fix:** In a new migration, use `lpad(n::text, greatest(4, length(n::text)), '0')`. Ask the controller for the migration number.

## Checked and rejected

- **`rate-versions/[id]/publish`, `JSON.stringify(service_area)::jsonb` (23514 on publish).** This was real at `3978fda9`. It was fixed during this audit by `3045c044`, which now uses `tx.json`. It is not carried as a finding.
- **`PATCH /api/staff/profile` with a password or e-mail drops the cookies from `updateUser`** (`profile/route.ts:87-96`; `ops/profile/actions.ts:100,118` build the client without a sink). The code does take this path. But GoTrue keeps the current access and refresh tokens on a password or e-mail change, and the cookie that would be lost only refreshes the cached user object. I found no user-visible failure, so it is rejected. It is still worth threading the sink through for consistency with `/api/auth` `update-password`.
- **Possible authorisation holes on staff routes.** Every route under `(ops)/api/staff/**` in scope is gated:
  - most use `withStaff` or `withAdmin`, which run `requireStaffClaims` / `requireAdminClaims` and then an Origin check on any method other than GET or HEAD (`lib/ops/staff-json.ts:68-101`);
  - `invite` uses `requireAdminClaims`;
  - `claim-invite` is self-only through `staff_claim_invite()` behind `staffOriginAllowed`.
  All 48 re-exports under `app/api/staff/**` point at the matching file and export the same verbs.
- **The manage cookie reaching another booking.** `flight`, `time-change` and `resend` go through `asGuest`, so the row lookup (`lib/ops/edit-request.ts:359-383`) returns nothing for any booking other than the token's, and the answer is 404. `cancel` refuses with 409 `wrong-booking`.
- **Review `photoKey` from another booking.** Keys contain `crypto.randomUUID()` (`lib/ops/photos.ts:102-110`) and cannot be guessed.
- **The flight cache key and the lookup normalising differently.** Both use `normaliseFlightNumber` (`lib/flight/aerodatabox.ts:90,267`).
- **Open redirect through `next` / `nextb` on the auth callback.** `validateAuthRedirectTarget` accepts only `PUBLIC_ROUTES` or `safeReturnTo` checkout paths, and rejects `//` and `/\` (`lib/auth/redirect-target.ts:37-72`). `nextb` is base64url, which follows the Worker rule for carrying a URL in a query value.

## Found clean

**OpenNext cookie trap.** Every route that sets a cookie copies it onto the response by hand:
- `api/auth` (`json`, `sessionJson`, `staffJson`)
- `auth/callback` GET and POST (`authSetCookieHeader`; POST keeps only the last write per cookie name)
- `consent` (Set-Cookie header)
- `staff/claim-invite`
- the middleware's `copyCookies`

`auth/session`, `auth/confirm/preview` and `consent/state` set no cookies.

**postgres.js traps:**
- No `JSON.stringify(x)::jsonb` remains in scope. The customer time change uses `sql.json` (`lib/ops/edit-request.ts:426-433`).
- No JS arrays are passed as parameters.
- No try/catch sits inside an `asSystem` or `asStaff` callback. `account/bookings` GET runs the guest claim in its own transaction for exactly this reason.

**Routes:**
- `api/auth` (every action branch): CSRF, IP limit plus per-address limit, dashboard refusal of non-staff, re-auth gates for staff password, e-mail and passkey changes, the per-account code limit before every code or password check.
- `auth/callback`, `auth/session`, `auth/confirm/preview`, `auth/email-hook` (signature verified before parsing, JSON content type on every answer).
- `account/bookings` GET (row-level security plus an e-mail filter, 500 on a failed read), `account/prefs`, `account/bookings/{cancel,flight,paid-cancel,resend,time-change}`.
- `manage/{cancel,flight,resend,time-change}`.
- `consent`, `consent/state`, `contact` (Turnstile before parsing, delivery is idempotent), `reviews`, `reviews/submit`.
- `geo/{suggest,retrieve,reverse}` (rate limit plus breaker, retrieve gated on an earlier suggest, no upstream body echoed).
- `flight/[no]`, `fx`, `internal/health` (empty 404 on every verb without the key), `dev/db-smoke` (always 404), `webhooks/resend` (svix signature verified on the raw body).
- Every staff route in scope, plus `(ops)/api/photos/upload`.

**Middleware:**
- The host split: the public host rewrites `/ops` to `/__vamos_gone`, and the dashboard runs its own branch.
- The manage token is moved to an HttpOnly cookie with a 302.
- Public redirects get `private, no-store`, because `applyPublicCacheHeaders` makes every non-200 response no-store.
- `vamos_qs` is minted on page responses.

**Other files:**
- `dashboard-gateway.ts`: rejects a mismatched SNI, closes robots for the console, routes `/app/ops/*` to Dashboard.
- `robots.ts`, and `sitemap.ts`, which matches the nine indexable rows of `lib/seo/pages.json` (enforced by `head.test.ts`).
- `i18n/routing.ts` and `i18n/request.ts`: unknown locale goes to `notFound`, missing leaves fall back to English one at a time, `$meta` is stripped, a missing key renders as empty.
- **Key parity:** en/de/fr/ar have the same keys. The only gaps are `$meta` and the intentional `quote.error.service_area_undefined` (`$meta.nonTranslatableKeys`).
- **RTL:** the public page CSS (`about`, `contact`, `imprint`, `review`, `home`, `error-pages`, `auth-page`, `PageHero`) has no physical left or right properties.
