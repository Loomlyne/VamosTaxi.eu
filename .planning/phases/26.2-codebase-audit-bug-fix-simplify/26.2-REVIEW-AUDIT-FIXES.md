## Blocking item

**B1. A Turnstile 4xx now fails open, but the commit only claims 5xx.** `apps/web/lib/abuse/turnstile.ts:113`:

```ts
if (!res.ok) return { configured: true, success: false, degraded: true };
```

`!res.ok` covers every 4xx, not only 5xx. The commit message and the U02-2 finding say "a siteverify 5xx or non-JSON body". Before this change, a 4xx body was parsed and came back as a failed challenge.

Why a stranger can use it:
- The quote guard reads the token from the request header `cf-turnstile-response` (`apps/web/lib/abuse/guards.ts:175`) and checks only `length > 0` (`guards.ts:68`). There is no 2048-character cap, which is the documented maximum token length.
- Siteverify documents `bad-request` ("Request is malformed") and `invalid-input-response`. The docs do not say which HTTP status those come back with.
- If any input the caller controls (an oversized or malformed token) makes siteverify answer with a 4xx, then from the 3rd attempt on `challengeDecision` returns `{ enforce: false, fellBackToEdge: true }` (`turnstile.ts:191-194`), and `turnstileGuard` lets the request through (`guards.ts:91`).
- So on every quote request, the challenge drops to the per-IP rate limiter and the edge rule only.

Is the fail-open bounded the way the header says? Only partly. Inside the app, "degraded" never enforces at any attempt count. The only bound is the Layer 1 edge rule plus the 8/60 and 4/60 Worker limiters. That is acceptable for a real Cloudflare outage, but not for a status code the caller can trigger.

The test `turnstile.test.ts` ("a 502 with an HTML body is degraded") pins 5xx only. Nothing pins what a 4xx does.

Fix:
1. Use `if (res.status >= 500) return …degraded`.
2. Let a 4xx fall through to the JSON parse, so it reads as a failed challenge.
3. Optionally treat a token longer than 2048 characters as a failed challenge before calling siteverify.
4. Add one test: a 400 answer is `{ configured: true, success: false }`, not degraded.

## (1) Can an input change the charged amount, or break the fare rule?

- **f68799bb (voucher in lock): clean.**
  - The price call and PAY send the same lock: `lockForVoucher` is used at `CheckoutForm.tsx` in both the price effect and `pay`.
  - PAY with no signed voucher lock announces "updating price" and sends nothing.
  - Reprice does not re-resolve places, Directions or metres (`pipeline.ts:851-889`). It only rebuilds lines from the lock with the new coupon, so a voucher cannot move the route.
  - The intent rule "body coupon must equal lock coupon" stays (`intent.ts:445`).
  - After a flight re-sign the base lock changes, so `held.base !== base` and the voucher is signed again on the new base.
- **0b5f930d (pinned pre-coupon): clean, and it fixes a real overcharge.**
  - Price route (`price-route.ts:153-157`), PAY (`intent.ts:457-461`) and the staff change price (`booking-change-price.ts:245-249`) all start `checkoutCharge` from the server-signed pre-coupon total, then apply fare + extras − coupon with a floor of 0 (`checkout-charge.ts:94-110`). That matches the owner's fare rule.
  - The screen and the charge evaluate the coupon live the same way, so they agree even if the owner edits the coupon between quote and PAY.
  - `netRappen` at PAY comes from `repriceFromLock`, which echoes `class_totals` (`reprice.ts:68-81`). The pinned total is compared with `total_rappen` only (`quote/intent.ts:236-243`).
  - `pre_coupon_rappen` itself is HMAC-covered and not re-derived. That is fine because only the server mints it.
- **U04-5 (null fare): clean.** It only nulls lines in a class whose total was already null (`sumPreCouponTotal` returns null on any null amount). No priced class changes.
- **U04-2 (coords reverse): clean.** No live page sends `kind: "coords"`: `home.dc.html:692/697` and `OpsNewTrip.dc.html:101/105` send `retrieve`/`pin`, and only the unused React `BookingBoard.tsx:292` uses coords. So only a direct API caller is affected, and that caller can no longer pick the airport fee or city pair through `text`.
- **U11-5 (VAT fail-closed): clean.** An unreadable flag refuses `pricing_not_live` (`intent.ts:436`). It no longer charges 8.1 %.

- **New page JS on an old Worker during the minute of the deploy:** the voucher reprice works (old reprice already accepts `coupon`). It mints a lock without the field, and the first new-Worker price call re-quotes. This clears itself.
