### U11-1 · money · A voucher typed on /checkout lowers the total on screen, but PAY always refuses it

**What is wrong.** The one-page checkout never puts the voucher into the signed quote lock. Two server routes then disagree about a voucher the lock does not carry:

- `/api/checkout/price` accepts it. `price-route.ts:133` reads `const couponCode = lockCoupon ?? bodyCoupon;`. With no coupon in the lock, the body voucher is evaluated and taken off the total.
- `/api/checkout/intent` refuses it. `intent.ts:460-462`:
  ```ts
  const lockCoupon = payload.coupon?.trim().toUpperCase() || null;
  const bodyCoupon = body.coupon?.trim().toUpperCase() || null;
  if (bodyCoupon !== null && bodyCoupon !== lockCoupon) return refuse("coupon_no_longer_valid");
  ```
- No client call ever sends `coupon`. `CheckoutPage.tsx:204-211` builds the `/api/quote/reprice` body from `quote_id, lock, locale, display_currency, preferred_class, legs` only. `fetchQuote` (`checkout-quote.ts:225`) posts the trip only. The reprice pipeline itself can pin a coupon into the lock (`lib/quote/pipeline.ts:836-841`), but nothing asks it to.
- Each half is tested on its own, and the tests pin the disagreement. `price-route.test.ts:104` applies voucher "ten" to a lock with no coupon and gets a discount. `intent.test.ts:615` sends coupon "TEN" with a lock with no coupon and gets `coupon_no_longer_valid`.

**Failure scenario.** A customer on /checkout picks Business, opens "Have a voucher?", types a valid 10 % code and presses Apply. The summary shows the discounted total. They press PAY. The intent answers 409 `coupon_no_longer_valid`. `CheckoutForm.tsx:871-876` clears the voucher and shows "voucher no longer valid", and the total goes back up. No voucher can ever be used on the public checkout. Nobody is charged the wrong amount, but a live, shown control does nothing, and the customer pays more than the figure they were shown.

**Smallest fix.** When a voucher is applied, re-sign the lock with it. Call `/api/quote/reprice` with `coupon` from `applyVoucher` (the same call `resignFlight` makes, plus `coupon: voucher`), store the returned lock, and call `/api/checkout/price` only with that lock. Add one test that runs both halves on the same inputs: voucher applied, price, then intent.

### U11-2 · correctness · After a failed PAY, pressing PAY again with the same selection always fails until the page is reloaded

**What is wrong.** The browser keeps one idempotency key per selection: `CheckoutForm.tsx:785-786`, `if (!idem.current || idem.current.sel !== sel) idem.current = { sel, id: crypto.randomUUID() }`. When no unpaid booking exists, the intent opens a Stripe session under that same key (`intent.ts:625`, `openSession(idempotencyKey)` with `idempotencyKey = body.idempotency_key`). Each call builds `expires_at` from the clock (`stripe.ts:146`, `stripeSessionExpiresAtUnix(input.expiresAt)`, with `expiresAt` from `workerNowIso` at `intent.ts:510`). Stripe refuses a reused idempotency key whose parameters differ. Even when the parameters match, Stripe replays the first session, and the error path has already expired it.

**Failure scenario.** The customer presses PAY. Stripe creates session A. `createBooking` then fails with a non-unique error, for example a pool timeout (`intent.ts:698-706`). Session A is expired and the answer is 500 `checkout_rpc_failed`. The customer presses PAY again a few seconds later with nothing changed, so the key is the same:
- `loadOpenPayment` returns null.
- `openSession(sameKey)` sends a different `expires_at`, and Stripe answers 400 `idempotency_error`.
- The error goes uncaught out of `runWebIntent` and comes back as 500 `intent_unhandled`, shown as "payStartFailed".

Every later press fails the same way for 24 hours, until the customer changes a field or reloads. If the seconds happen to match, Stripe returns session A, which is already expired. `hostedPayable` then fails at `intent.ts:626`, and the answer is `invalid_request`.

**Smallest fix.** Make the browser drop its key after any failed answer: set `idem.current = null` in `fail()` and on any non-ok answer in `CheckoutForm.tsx`. Or, on the server, when `loadOpenPayment` is null, derive the Stripe key as `${body.idempotency_key}:${attempt}`, the same way the attach and supersede paths already use `:after:`.

### U11-3 · money · `charge.refunded` records only the first 10 refunds on a charge

**What is wrong.** `retrieveCharge` (`stripe.ts:286-288`) expands `refunds`, and Stripe's expanded list stops at 10 by default. `handleChargeRefundedWithDeps` loops only over `charge.refunds?.data` and, when `has_more` is set, only logs (`money-events.ts:126-129`):
```ts
const refunds = charge.refunds?.data ?? [];
if (charge.refunds?.has_more) {
  deps.emit("warn", "charge_refunds_truncated", { eventId: message.eventId, chargeId: charge.id });
}
```
The event is then settled and acknowledged (`:181-186`).

**Failure scenario.** A charge with 11 or more partial refunds, for example repeated small goodwill refunds from the Stripe Dashboard. Refunds 11 and up are never written to `booking_refunds`. The booking's refunded total in the database is lower than the money Stripe actually returned, and the event is marked done, so nothing ever retries it. This is unlikely today, but it loses money facts without any error.

**Smallest fix.** When `has_more` is set, page through `stripe.refunds.list({ charge: charge.id, limit: 100, starting_after })` before the loop. At the very least, return `settleWithError(..., "refunds_truncated")` so the event stays visible as unfinished instead of being acknowledged.

### U11-4 · security · The account check runs before the signed lock is verified, so anyone can ask "does this e-mail have an account"

**What is wrong.** In `intent/route.ts`, `gateAccountForRequest` runs at line 160, before `runCheckoutIntent` verifies the HMAC lock (`intent.ts:407`). Before the gate, the route checks only that `quote_id` is a UUID, that `lock` is a non-empty string (schema), and that `vehicle_class` is a real slug (`:98-108`). The gate then answers `200 { ok:false, code:"sign_in_first" }` for a known e-mail and mails it a sign-in link (`account-gate.ts:96-103`). For an unknown e-mail it lets the request through, and a forged lock then gets a different refusal.

**Failure scenario.** Someone with a Turnstile token posts `{quote_id:<random uuid>, lock:"x", vehicle_class:"economy", contact:{email:"victim@x.ch",...}, account:{choice:"create", consent:true, turnstile_token}}`. The answer `sign_in_first` means the address has an account, and a sign-in mail goes to the victim. `quote_not_found` means it does not. Turnstile, the per-IP limit and the per-e-mail limit slow this down, but the oracle needs no real quote at all.

**Smallest fix.** Move the account gate to after the lock is verified. The cleanest way is to pass it into `runCheckoutIntent` as a dependency and call it right after `checkIntentAgainstLock` succeeds, still before any Stripe call.

### U11-5 · correctness · The VAT rate falls back to 8.1 % at PAY, while the price route refuses instead

**What is wrong.** `vatRateBpsFromFlags` (`intent.ts:239-252`) returns `CH_VAT_RATE_BPS` (81) when `loadLaunchFlags` throws, even though its own comment says "fail closed". The price route treats the same failure as `pricing_not_live` (`price-route.ts:162-166`).

**Failure scenario.** The owner sets `vat_rate_bps` to anything other than 81, for example a VAT change. The customer sees a price computed at the new rate. At PAY, a short database error on `loadLaunchFlags` makes the intent compute VAT at 81. If the result differs, the customer is charged a different amount from the one shown. Nothing compares the charge with the figure on screen; the fingerprint carries the new amount. Today the rate is 81, so there is no difference.

**Smallest fix.** Refuse `pricing_not_live` when the flags cannot be read, exactly as the price route does.

### U11-6 · polish · A database failure on the extras list answers `ok: true` with no extras

`extras/route.ts:30-35` catches every error and returns `{ ok: true, extras: [], vat_rate_bps: 81 }`. On a database blip the checkout shows no extras, so a customer who needed a child seat cannot pick one, and the client cannot tell an outage from an empty price book. Fix: return `{ ok:false }` with status 503, so the client keeps its retry and error state. The intent already fails closed on the same read (`intent.ts:446-452`).

### U11-7 · polish · A failed details write leaves an unpaid booking whose only session has been expired

`intent.ts:719-725`: by the time `saveDetails` runs, `createBooking` has already committed the booking, the price snapshot and the payment row. When `saveDetails` throws, the session is expired and the answer is 500, but the booking stays. The hourly purge removes it after 35 minutes, because all its sessions are expired and unpaid, so the data heals itself. Together with U11-2, though, the next PAY with the same key also fails. Fix: write the details inside the same `checkout_create_booking` call, or treat a details failure as non-fatal (log it and return the session), since the company fields and note are not part of the charge.

## Paths checked and clean

- **Stripe webhook** (`api/stripe/webhook/route.ts`, `webhook.ts`, `webhook-verify.ts`): raw body, `constructEventAsync` with the SubtleCrypto provider, and a missing secret refused. It answers 500 when either the record or the enqueue fails, so Stripe retries, and enqueues even on a duplicate. No event is acknowledged without being queued.
- **DLQ** (`dlq.ts`, `worker.ts:177-193`): always acknowledges, and a failed alert is logged. This is by design (T-26.1-10).
- **Amounts**: the charge is computed only on the server from the signed lock, the live catalog and the evaluated coupon (`checkoutCharge`). The schema refuses client amount fields (`intent-schema.ts:10-16,170-184`, `price-route.ts:15`). The currency is pinned to CHF, and `hostedSessionIsPayable`/`amountMatches` check both currency and amount. The line sum is checked against the charge (`checkout-charge.ts:153-157`).
- **Return route** (`api/checkout/return`, `return-settle.ts`): paid status comes only from Stripe's session, never from the browser. It is rate-limited per IP, its targets are fixed paths with validated ids, and a failed settle falls back to the webhook.
- **Confirmation and status reads**: gated by the `vt_manage` hash or a session. `customer_confirmation_read` gets `claims.sub` (`booking-read.ts:393`). That looks like an auth-user id passed where a `customers.id` is expected, but migration `20261005110000_security_hardening.sql:39-61` takes the customer from `auth.uid()` and accepts either value, so it is correct.
- **Resume, lock-expire, pay-link open**: resume needs the cookie hash. The pay-link token is 32 random bytes, hashed, behind a CSRF check. The supersede and owner paths use guest RLS (`booking-owned.ts`).
- **Customer resend** (`customer-resend.ts`): both routes are CSRF-checked and rate-limited (`accountWriteForbidden`).
- **Quote routes**: thin wrappers; the rules live in the pipeline, which is outside this scope.
- **Notify**: claim first, never throws, and each manage token is an extra insert, so earlier links keep working.
- **No `begin()` catch-inside trap** in scope: every catch of an SQL error sits outside the `asCheckout`/`asSystem` call.
