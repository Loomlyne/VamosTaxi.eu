# Phase 26.3 Plan 01: Confirmation mail through definer RPCs Summary

The confirmation e-mail now claims its ledger row first, reads every field through `checkout_booking_for_email` v2 (a definer RPC), never throws to its caller, and is resent every hour for stuck, failed, or never-claimed paid bookings. This closes root cause 2 of VT-26-0737, where `vamos_system` hit 42501 on a raw `price_snapshots` read.

## Deviations from Plan

**1. [Rule 3 - Blocking] Updated signature-bound privilege asserts**
- `settle_revive.test.sql` (3 asserts) and `settlement_rpcs.test.sql` (6 asserts) named the 9-argument `checkout_payment_settle` signature. They now name the 10-argument signature. No other plan lists these files.
- Commit 4019c50a.

**2. [Rule 3 - Blocking] `tg_payment_update_whitelist` recreated**
- Without this, the settle UPDATE could not write the new `presentment_currency` column. It is now allowed, and it is write-once like the other FX columns.
- Commit 4019c50a.

**3. [Rule 1/2 - Bug] `notification_sweep` v2, and the sweep resumes the existing claim**
- **Problem 1:** the old sweep re-called `deliverConfirmation`, which called `notification_claim`. That returns null on the existing `dedupe_key`, so a stuck claim was never resent.
- **Problem 2:** `notification_settle` with an error sets `failed_at`, and the old sweep skipped any row with `failed_at` set, so a failed send was never retried either. The plan requires that the row "stays retryable".
- **Fix:** the sweep now passes `claimId` for these rows, and `notification_sweep` also returns failed rows. A row qualifies when its last failure is older than the threshold and its claim is under 3 days old, so a permanently bad address stops after 3 days. The signature, the `p_kinds` default and the grants are unchanged.
- Commit 4019c50a (SQL) and 8ff99870 (TS).

**4. [TDD order]** In Task 2 the implementation was written before `notify.test.ts`, so there is no separate RED commit. Test and implementation are in one commit (8ff99870).
