# G4 Summary - BLOCKED, product bug

A real customer cannot get German, French or Arabic on the Next pages (checkout, confirmation, review, sign-up). They always get English, `<html lang="en" dir="ltr">`. No helper or spec was built, because none would reproduce a customer path. There is none.

## How language is chosen today (file:line)
- `apps/web/i18n/routing.ts:19-21` - `localeDetection: false`. next-intl ignores the `NEXT_LOCALE` cookie and Accept-Language on unprefixed URLs, so those always resolve to `defaultLocale: "en"` (`routing.ts:17`).
- `apps/web/middleware.ts:530-543` - any `/de|/fr|/ar|/en` prefix on a public host gets a 308 to the unprefixed path, plus `Set-Cookie: NEXT_LOCALE=<prefix>`. The cookie is set but never read (see above). The `/de/...` URL never renders.
- `apps/web/lib/dc-mock-urls.ts:135` - the DC-page redirect sets the same dead cookie.
- `apps/web/app/[locale]/layout.tsx:44,62,76` - `<html lang dir>` come from the `[locale]` param only. That param is `en` for every URL that survives the middleware.
- `apps/web/lib/locale-shim.ts:103-107` - the Next SiteHeader switcher calls `router.replace(path, {locale})`, which requests `/de/...` and hits the same 308 back to English. The switcher is dead on Next pages.
- DC pages hand over via `localStorage.vamosLang` (`app/vamos-locale.js:45,96,467`), a DOM-relabel runtime. It is not loaded on Next pages (no `vamos-locale` reference in `apps/web/app` except `CheckoutClient.tsx:79`, which only imports the shim for currency). So the DC choice is not carried into Next.

## Evidence (live, curl GET, 2026-09-29)
- `GET /de/confirmation/x` returns 308 to `/confirmation/x` with `set-cookie: NEXT_LOCALE=de`.
- `GET /confirmation/x` with `Cookie: NEXT_LOCALE=ar` returns `<html lang="en" dir="ltr">`.
- `GET /checkout/trip` and `/checkout/details` with `NEXT_LOCALE=ar; vamosLang=ar` return `<html lang="en" dir="ltr">`.
- Following `/ar/checkout/trip` ends on `/checkout/trip`, still English.
- Origin of the change: commit `4d38a03c` ("Languages live on the page switcher, not /de /fr /ar /en"), which removed prefixed URLs but did not give Next pages another way to pick a locale.

## Smallest fix (for the owner to approve; not applied)
In `apps/web/middleware.ts`, at the block starting line 530, do not 308 when the stripped path is a Next-served page (`/checkout*`, `/confirmation*`, `/review*`, `/sign-up` if Next). Let it fall through to `handleI18nRouting` (line 616) so `/de/checkout/trip` renders German at its prefixed URL. Keep the 308 for DC pages, which relabel client-side. That also revives the SiteHeader switcher on Next pages. Alternative if prefixed URLs must stay hidden: set `localeDetection: true` limited to the cookie, and rewrite unprefixed to `/[locale]/...` from `NEXT_LOCALE`. That needs care, since the routing comment says detection also set the cookie on 404s.

Once either lands, the helper is short: `openInLocale(page, path, lang)` = `page.goto('/<lang>' + path)` (first option) or `context.addCookies([{name:'NEXT_LOCALE', value: lang, url}])` then goto (second), then assert `html[lang]`, `dir`, and `scrollWidth <= innerWidth` at 390. The spec assertions are ready to write.
