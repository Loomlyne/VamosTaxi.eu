# G5 Plan - the customer's language follows them onto the Next pages

## Objective
A language chosen on home (or in the header switcher on a Next page) renders on checkout (incl. /checkout/pay/<token>), confirmation and review: `<html lang>` = de|fr|ar, `dir="rtl"` for ar, visible translated text. Addresses stay unprefixed. Diagnosis: 26.3-G4-SUMMARY.md.

## Approach
1. One source of truth: cookie `NEXT_LOCALE` (en|de|fr|ar only). New pure module `apps/web/lib/locale-cookie.ts`: `resolveCookieLocale(value)` (validated, default en), `localeRewriteResponse(request, locale)`.
2. `app/vamos-locale.js` `setLang` also writes `NEXT_LOCALE` (Path=/, SameSite=Lax, 1 year, Secure on https), so home's choice carries over. The same file stays the DC runtime; nothing else in it changes.
3. `middleware.ts`: on the public host, for a request that reaches the next-intl step (Next page, not DC, not dashboard host, no locale prefix), if the validated cookie is not `en`, answer with an internal REWRITE to `/{locale}{path}` carrying the `X-NEXT-INTL-LOCALE` request header (what next-intl itself sets). English and missing/invalid cookies keep the existing next-intl path untouched. The 308 for `/de|/fr|/ar|/en` prefixed URLs (DC and Next alike) is unchanged, as are the /api document guard, the three browser-openable routes, security headers and DC serving. The rewrite call lives in the lib module, so middleware.ts still contains only `NextResponse.rewrite(gone)`.
4. Caching: Next-page responses get `Vary: Cookie` (appended); the marketing public-cache branch now appends to Vary instead of overwriting, and a non-en cookie forces `private, no-store`. Checkout/confirmation are already no-store.
5. `lib/locale-shim.ts`: `VamosLocale.setLang` and `useVamosLocale().setLang` write the cookie and `router.refresh()` instead of `router.replace(path,{locale})` (which requested /de/... and was 308'd back). Active locale in the shim comes from `useLocale()`, which follows the refreshed render.

## Files
- new `apps/web/lib/locale-cookie.ts`
- `apps/web/middleware.ts`, `apps/web/lib/locale-shim.ts`, `app/vamos-locale.js`
- tests: `apps/web/tests/unit/locale-cookie.test.ts`, `apps/web/tests/support/locale.ts` (`openInLocale`), `apps/web/tests/integration/locale-follow-26-3.spec.ts`
- not touched: checkout files, CheckoutClient.tsx, messages json (Plan 15).

## Acceptance
- Browser (Playwright on `next dev`): confirmation loading screen and /checkout/trip in de, fr, ar at 1440 and 390: html lang matches, ar dir=rtl, visible text in that language, scrollWidth <= innerWidth at 390.
- Switcher on a Next page changes language (cookie + html lang).
- Invalid cookie value renders en. DC pages still 308 away from /de.
- Unit tests for cookie validation and middleware wiring; existing middleware / dc-mock-urls tests green.

## Threat model
- Tampering: cookie is attacker-controlled; only exact matches of four literals are accepted, never interpolated unvalidated into a path (prevents open rewrite / path injection). Write side validates too.
- Cache poisoning / cross-language leakage: Vary: Cookie, no-store on personal paths, non-en never publicly cached.
- No new /api document-openable route; no new cookie beyond the existing NEXT_LOCALE (not HttpOnly by necessity: client sets it; holds no secret).
