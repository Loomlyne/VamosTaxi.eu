<objective>
Ship the two screens that get a staff member from "has a password" to "holds an `aal2` session",
prove the two gates that guard everything else in this phase, and close the one open question
Phase 2 explicitly handed forward.

`app/ops/AuthForm.dc.html` enumerates `mode: signin | signup | forgot` and nothing else — there is
no MFA challenge state anywhere in the mock set. That screen is therefore **designed, not ported**,
and this plan opens with a design review of the proposed interaction model rather than letting an
executor invent an auth screen unreviewed (`HANDOFF-CLAUDE-CODE.md` §7: "ask before inventing
these").

The plan also carries the assertion Phase 2's verification could not make. `02-VERIFICATION.md`
records U15 as owner-attested on 2026-08-24 — the dashboard toggle was set — but explicitly notes
that "a staff member who completes TOTP actually receives `app_metadata.vamos_role` in their minted
JWT" was never observed, because doing so required creating a real auth user on the hosted project.
That observation is this plan's Task 4. If the hook is not actually firing, **every RLS-gated
screen in Phase 6 silently returns zero rows with no diagnosable error** — so it is proven here,
before eleven screen plans are built on the assumption.

Purpose: a working front door, two automated gates, and the hook proven live.
Output: two screens, two fixtures, two specs, one hosted attestation.

Task sizing note: four tasks, two of which are checkpoints costing effectively no context. The
implementation surface is two forms and two specs.
</objective>

  <context>
    `AuthForm.dc.html`'s `data-props` cover `signin | signup | forgot` only. There is no TOTP
    challenge state, no factor picker and no recovery affordance anywhere in `app/ops/`. The project's
    own rule for a screen with no mock is to ask rather than invent. The design system supplies every
    primitive needed (`Card`, `Input`, `Button`, `Alert`, `StepIndicator`, `Icon`) — the question is
    the interaction, not the palette.

    Constraints that are fixed regardless of the answer: charcoal/white surfaces only, no glow, no
    tinted yellow, four languages, 54px primary CTA, logical properties for RTL, and copy in the
    console's neutral literal register.
  </context>
  <options>
    <option id="option-a">
      <name>Two pages, single-factor assumption (proposed)</name>
      <pros>
        `/ops/sign-in` is one centred Card: email, password, sign in. On success the middleware
        redirects to `/ops/mfa-challenge`, a second centred Card that auto-selects the staff member's
        single TOTP factor, shows a one-field 6-digit code entry with `inputmode="numeric"` and
        `autocomplete="one-time-code"`, and a single verify button. A wrong code re-renders an inline
        `Alert` and keeps the entered value; three wrong codes shows the same message (never a
        different one — an attacker must not learn attempt state). No factor list, no "trust this
        device", no recovery-code affordance. Fewest states, matches the fact that staff enrol
        exactly one factor.
      </pros>
      <cons>
        A staff member who loses their authenticator has no self-service path — they must ask an
        admin, and reset-MFA is deferred (D-28), so in practice they wait. Accepted knowingly.
      </cons>
    </option>
    <option id="option-b">
      <name>One page, progressive two-step</name>
      <pros>
        A single `/ops/sign-in` route that swaps its body from password to code using the ported
        `StepIndicator`. One URL, one visual frame, no redirect flash between steps.
      </pros>
      <cons>
        The middleware's `aal2` redirect target has to be that same URL, which makes "signed out"
        and "signed in but not verified" the same address — harder to test, harder to reason about
        in the gate specs, and it hides a real state change behind client state.
      </cons>
    </option>
    <option id="option-c">
      <name>Option A plus a visible factor list</name>
      <pros>Future-proof if a second factor type is ever enabled.</pros>
      <cons>
        `[auth.mfa.phone]` and `[auth.mfa.web_authn]` are both disabled in `config.toml`; a list of
        one item is UI debt today for a capability nothing has asked for.
      </cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b, or option-c — and flag any copy or layout change you want before implementation starts.</resume-signal>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous browser -> `/ops/sign-in` | Unauthenticated, rate-limited-by-Supabase credential submission |
| aal1 session -> `/ops/mfa-challenge` | A session that has proved a password but not a second factor |
| `next` query parameter -> redirect | Attacker-controllable string used to build a navigation target |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-17 | Information Disclosure | `OpsSignInForm` error copy | mitigate | One generic credential-failure message; never distinguishes unknown account from wrong password |
| T-06-18 | Spoofing | `next` parameter after MFA verify | mitigate | Accept only a same-origin path beginning `/`; anything else falls back to `/ops` — grep-asserted |
