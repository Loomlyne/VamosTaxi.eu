<objective>
Build the invitation half of AUTH-05: an admin invites an address, the invitee sets a password and
is walked straight into mandatory TOTP enrolment, and only then does a session that can reach ops
data exist.

Three things make this the most security-sensitive route in the phase.

**It is the only place the service-role key is used.** That key bypasses RLS entirely and can mint
any account. It is therefore constructed only after `requireAdminClaims()` has already proven the
*caller's own* session is an `aal2` admin — the check comes first in the file, not somewhere in the
middle of it.

**`user_metadata` is never authoritative.** `inviteUserByEmail`'s `data` field is writable by the
invited user through the client SDK afterwards. The role that matters is the `public.staff` row this
route writes itself, which is what the Custom Access Token Hook reads on every mint. `invited_role`
in metadata is cosmetic display only (D-06).

**`redirectTo` is pinned, never derived.** A `redirectTo` built from `request.headers.host` or from a
body field lets an attacker who can reach the route point a real invite email at their own origin.
One constant, matched against Supabase's own Redirect URL allow-list.

Neither `accept-invite` nor the enrolment step has a mock — `AuthForm.dc.html` covers
`signin|signup|forgot` only — so this plan opens with a design review, same as 06-04.

Purpose: staff accounts can be created by an admin and can never exist half-enrolled.
Output: one Route Handler, one two-step screen, one spec, and the Resend prerequisite named at the
exact point it becomes blocking.
</objective>

    URI, so no QR library is involved either way.

  </context>
  <options>
    <option id="option-a">
      <name>One route, three steps, StepIndicator (proposed)</name>
      <pros>
        `/ops/accept-invite` renders a single `OpsAuthCard` with the ported `StepIndicator` at
        1-of-3: (1) set password, (2) scan the QR / copy the secret, (3) enter the 6-digit code to
        confirm. Step 2 and 3 are one screen with the code field beneath the QR, so the staff member
        never navigates away from the QR while typing. Back is disabled after step 1 (the factor is
        already created server-side). Success lands directly on `/ops`. The whole flow is one URL,
        which keeps the middleware exemption to a single path and makes the "enrolment is mandatory"
        claim structurally true: there is no exit that is not completion.
      </pros>
      <cons>
        A staff member who abandons mid-flow has an unverified factor recorded; a re-entry must call
        `listFactors()` and unenrol the stale unverified one before enrolling again. That branch has
        to be built and tested — it is the one real complexity in this option.
      </cons>
    </option>
    <option id="option-b">
      <name>Two routes: set password, then redirect to a separate /ops/enrol</name>
      <pros>Each route does one thing; `/ops/enrol` is reusable later for a re-enrolment flow.</pros>
      <cons>
        Two middleware exemptions instead of one, and a real window where a session has a password
        and no factor and is sitting on a URL it can navigate away from — the exact state
        `research/staff-mfa.md` says must not be reachable.
      </cons>
    </option>
    <option id="option-c">
      <name>Option A, plus a printable recovery sheet</name>
      <pros>Answers "what if I lose my phone" without an admin round-trip.</pros>
      <cons>
        Supabase TOTP has no recovery-code primitive; this would mean inventing one, storing it, and
        making it a second credential to protect. Reset-MFA is already deferred (D-28) — this
        reopens it as a bigger problem than it defers.
      </cons>
    </option>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| ops browser -> `/api/staff/invite` | An authenticated but possibly non-admin session reaches a route that holds the service-role key |
| request body -> `public.staff.role` | An attacker-chosen string would otherwise become a database role value |
| invite email -> invitee's browser | A link an attacker could redirect if `redirectTo` were derived from input |
