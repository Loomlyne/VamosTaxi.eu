<objective>
Port `OpsCoupons.dc.html` onto the real `public.coupons` table.

This is the phase's most ordinary CRUD screen and the plan is deliberately small — but two schema
facts change the form from what the mock implies. `coupons_kind_field` makes `percent` and
`amount_rappen` mutually exclusive by CHECK, so the form is a discriminated pair, not two
independent fields that happen to be filled one at a time. And `code` carries
`check (code = upper(code))`, so lower-case input is a constraint violation, not a formatting
preference — the form uppercases before it submits and the database is the second gate.

Purpose: staff can run promotional codes without a deploy.
Output: one list, one form, four Server Actions, one spec.
</objective>

<interfaces>
`public.coupons` (…09_coupons.sql):
  id bigint identity PK
  code text unique, CHECK (code = upper(code))
  kind public.coupon_kind ('percent' | 'amount'), default 'percent'
  percent numeric(5,2) CHECK 0..100         -- NULL when kind = 'amount'
  amount_rappen public.rappen CHECK >= 0    -- NULL when kind = 'percent'
  valid_from timestamptz, valid_until timestamptz
  global_limit integer, per_user_limit integer      -- NULL = unlimited
  active boolean default true, note text, created_at timestamptz
  CONSTRAINT coupons_kind_field  — exactly one of percent / amount_rappen is set
  CONSTRAINT coupons_window      — valid_until > valid_from when both are present

RLS: `coupons` is in the seventeen-table staff working set (…23_rls_staff.sql) —
select/insert/update/delete to `vamos_staff` behind `coupons_staff_gate` (`app.is_staff()`).
**Not admin-only**: a dispatcher may manage coupons.

Audit: `coupons` is in `tg_audit_row`'s attached list, so every write is diffed into `audit_log`
automatically — this screen adds no audit call of its own.

From 06-07: `mapSqlState`, `OPS_SQLSTATE` in `apps/web/lib/ops/sqlstate.ts`.
From 06-02: `requireStaffClaims()`.
Seed: `public.coupons` is empty. The empty state is the state this screen ships in.
</interfaces>
