<objective>
Close OPS-09's remaining half: an admin runs the staff roster, and every staff member runs their own
profile.

**A dispatcher cannot read their own staff row.** `staff_admin_write` is `AS RESTRICTIVE FOR ALL to
vamos_staff using ((select app.is_admin()))` — restrictive, and `FOR ALL`, so it ANDs against SELECT
too. That is deliberate and correct: a dispatcher must not be able to write `public.staff`. It also
means a plain `select * from staff where user_id = app.uid()` returns nothing for them. 06-01 built
the way through — `app.staff_self()`, `public.staff_update_self(...)` and `public.staff_claim_invite()`,
three self-scoped security-definer functions, each carrying its own `where user_id = app.uid()`
because `public.staff` has no FORCE ROW LEVEL SECURITY and a definer function owned by the table owner
bypasses RLS entirely. This plan is the screen those functions were built for; it calls them and never
widens a policy.

**Deactivation is not instant, and the console should say so.** `custom_access_token_hook` reads
`from public.staff where user_id = … and s.active`, so clearing `active` removes the `vamos_role`
claim from the *next* minted token. An access token already in a browser stays valid until it
refreshes: `packages/db/supabase/config.toml` sets `jwt_expiry = 3600`, so the residual window is up to
an hour. Every RLS policy in the ops set is keyed on `app.is_staff()`, which reads the claim from that
token — so for that window a deactivated dispatcher still has a working console. This plan measures
the real configured value, states it in the deactivation confirmation, and checks whether the
installed Supabase Admin API offers a documented session-revocation call to shorten it. What it does
not do is pretend the window is zero.

**Reset-MFA stays deferred, visibly.** D-28 makes admin reset-MFA the sole launch-window item in an
otherwise in-scope staff-management list, and `docs/build/MISSING-FEATURES.md` marks it 🟡. So the
staff screen has no reset control, the profile screen has no self re-enrolment, and both say what
happens instead: a staff member who loses their authenticator contacts the owner, and until the
launch-window item lands that is a manual database intervention. A deferral a user can read is a
decision; a deferral they discover at 6am is a bug.

The mock's own security pane is partly refused. `OpsSettings.dc.html` offers passkeys and account
deletion. Staff use TOTP, not passkeys, and a staff account is deactivated by an admin, never
self-deleted — `staff.user_id` is `on delete cascade` from `auth.users`, so a self-delete would take
the audit trail's actor reference with it.

Purpose: the roster is manageable by an admin and every staff member owns their own record.
Output: two screens, six Server Actions, one spec.
</objective>
