<objective>
Build the photo pipeline three later plans depend on — Fleet (06-12), Chauffeurs (06-13) and Reviews
(06-14) — once, here, with a private bucket and a server-relayed write.

The mocks model this wrong on purpose: `OpsReviews.dc.html` and `OpsProfile.dc.html` "upload" with
`FileReader.readAsDataURL()` into `localStorage`. The schema does not: `vehicles.photo_path`,
`chauffeurs.photo_path` and `reviews.avatar_path` are `text` columns holding an **R2 object key**.
`OpsFleet.dc.html` has no upload control at all despite the columns existing — this is the sixth
and last of the phase's no-mock surfaces, so it opens with a design review.

One step here is irreversible. `apps/web/wrangler.jsonc` declares the `PHOTOS` binding and the two
bucket names, but Phase 1's scope was declaration only — the buckets themselves may not exist. A
bucket's jurisdiction can only be set at creation (Phase 2 D-24), and Swiss/EU data residency is a
project constraint. Checking before creating is therefore a blocking human step, not a script.

Purpose: one upload path, one read path, one field component, and a bucket that is EU-pinned.
Output: two routes, one component, one spec, and the Cloudflare resource doc updated.
</objective>

Cloudflare R2 Workers binding API used here:
  env.PHOTOS.put(key, body, { httpMetadata: { contentType } }) -> R2Object
  env.PHOTOS.get(key) -> R2ObjectBody | null    (`.body` is a ReadableStream, `.writeHttpMetadata(headers)`)
  env.PHOTOS.delete(key)

Schema columns this pipeline fills (all nullable `text`, all currently NULL everywhere — the seed
inserts no photo):
  public.vehicles.photo_path
  public.chauffeurs.photo_path
  public.reviews.avatar_path
  public.staff.avatar_path

`getCloudflareContext()` from `@opennextjs/cloudflare` is how a Route Handler reaches `env` — the
same accessor `apps/web/lib/db/identity.ts` documents (D-06: fetch/RSC only).

  <behavior>
    - `buildPhotoKey("vehicle", id, "image/jpeg")` returns a key under a fixed prefix with a random component and a normalised extension; it never contains a caller-supplied filename
    - `assertPhotoUpload` rejects anything whose declared type is outside {image/jpeg, image/png, image/webp} and anything over the size cap
    - `assertPhotoUpload` rejects a file whose leading bytes do not match its declared type (a PNG magic number under an `image/jpeg` label is rejected)
    - The upload route returns 401/403 for a non-staff caller before reading the body
    - `/photos/<key>` returns 404 for a key that does not start with one of the allow-listed prefixes, without touching R2
    - `/photos/<key>` returns 404 for any key containing `..`, a leading `/`, a backslash or a percent-encoded separator
    - A round trip — upload then fetch — returns identical bytes and the stored content type
  </behavior>
  <action>
    `lib/ops/photos.ts` — the contract everything else imports.
      - `PHOTO_PREFIXES` = the closed set `["vehicles/", "chauffeurs/", "reviews/", "staff/"]`.
      - `buildPhotoKey(kind, recordId, contentType)` = `<prefix><recordId>/<crypto.randomUUID()>.<ext>`.
        The extension is derived from the **validated** content type, never from the uploaded filename.
        A caller-supplied filename never appears in a key, which removes path traversal at the source
        rather than sanitising it afterwards.
      - `assertPhotoUpload(file)` — allow-list the three MIME types, cap the size (choose a value and
        state it in a comment; 5 MB is a reasonable default for a phone photo), and sniff the first
        bytes to confirm the declared type. Throw a typed error carrying a machine code, not prose.
      - `photoUrl(key | null)` -> `/photos/<key>` or `null`. Every screen renders through this so the
        read path can change in one place.

    `api/photos/upload/route.ts` — `export const dynamic = "force-dynamic"`. Order: `requireStaffClaims()`
    first; then read the multipart body; then `assertPhotoUpload`; then `env.PHOTOS.put(key, bytes,
    { httpMetadata: { contentType } })` with `env` from `getCloudflareContext()` inside the handler.
    Return `{ key }` only — never a URL the client could mistake for authoritative, and never the
    bucket name. This route writes **no database column**: the owning screen's own Server Action sets
    `photo_path`/`avatar_path` through `asStaff`, so every column write stays inside the audited,
    RLS-checked path. Say so in a comment; it is the reason the route looks incomplete on its own.

    `app/photos/[key]/route.ts` — deliberately **outside** `[locale]` and outside `(ops)`: a photo is
    not a localised page and is read by the public site. `export const dynamic = "force-dynamic"`.
    Validate the key against `PHOTO_PREFIXES` and reject traversal characters before calling R2; on a
    miss return 404 with no body. On a hit, stream `object.body` and set headers from
    `object.writeHttpMetadata(headers)` plus an explicit `Cache-Control` (keys are immutable by
    construction — a new upload gets a new UUID — so a long `max-age, immutable` is correct and is the
    reason the Worker proxy is worth having over a public bucket, D-23). Never set
    `Access-Control-Allow-Origin: *`.

    Add `PHOTOS` to `env.d.ts` if the generated Cloudflare types do not already carry it, and record
    the bucket/jurisdiction/IMAGES findings from Task 1 in `docs/build/CLOUDFLARE-RESOURCES.md`.
  </action>
  <verify>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser file picker -> upload route | Attacker-controlled bytes, filename, MIME label and size |
| object key -> R2 namespace | A key is a path; a caller-influenced key is a traversal primitive |
| `/photos/[key]` -> public internet | The only unauthenticated read surface this phase adds |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-32 | Tampering | photo object key | mitigate | Keys are generated from a fixed prefix plus `crypto.randomUUID()`; an uploaded filename never reaches a key, so traversal is removed at the source rather than filtered |
| T-06-33 | Tampering | `/photos/[key]` path traversal | mitigate | The key is matched against the closed `PHOTO_PREFIXES` set and rejected for `..`, leading `/`, backslash or encoded separators before R2 is touched — asserted in the spec |
| T-06-34 | Tampering | unrestricted file type | mitigate | MIME allow-list of three image types plus a leading-bytes sniff, so a declared `image/jpeg` carrying an HTML payload is refused |
| T-06-35 | Information Disclosure | R2 credentials in the browser | mitigate | R2 is reachable only through the Worker binding; no presigned URL and no client-side SDK — the browser sees only `{ key }` |
| T-06-36 | Denial of Service | oversized uploads | mitigate | Explicit size cap enforced server-side before `PHOTOS.put`; the client-side `accept` attribute is convenience only |
| T-06-37 | Elevation of Privilege | unauthenticated upload | mitigate | `requireStaffClaims()` precedes body parsing — grep-asserted line ordering |
| T-06-38 | Information Disclosure | data residency | mitigate | Buckets created with `--jurisdiction=eu` at first creation (Task 1, blocking, irreversible afterwards) and the outcome recorded in `docs/build/CLOUDFLARE-RESOURCES.md` |
| T-06-39 | Repudiation | a column written outside the audited path | mitigate | The upload route writes no database column; `photo_path`/`avatar_path` are set only by the owning screen's `asStaff` Server Action, so `tg_audit_row` attributes the change |
| T-06-SC | Tampering | package installs | n/a | This plan installs no package — no QR, no image library, no S3 SDK |
</threat_model>
