<objective>
Stand up the console's outer shell: the `/ops/*` route group, the middleware gate that keeps a
non-staff or aal1 session out of it, the ported `OpsSidebar` rail, and the complete four-language
`ops.*` dictionary every later screen will draw from.

Two things here are load-bearing beyond their size.

**The nav is a security-shaped UX decision, not styling.** `rate_versions_admin_write` and
`staff_admin_write` are `AS RESTRICTIVE FOR ALL`, so a dispatcher's query against those tables
returns **zero rows, not a 403**. A "Pricing" item that renders for a dispatcher therefore leads to
an empty table that looks like a data problem. The nav list is built server-side from the rendered
session's role and the item simply does not exist for that role (D-12).

**The dictionary is front-loaded on purpose.** `scripts/check-i18n-coverage.mjs` blocks a PR on any
`t('ops.x')` call site whose key is missing from `en.json`, and on any English key missing from
`de`/`fr`/`ar`. Rather than have seven parallel screen plans each race the same four files, this
plan harvests the whole `ops.*` namespace once from the thirteen `app/ops/*.dc.html` mocks — which
already carry `en`/`de`/`fr`/`ar` for their own labels.

Purpose: after this plan, a screen plan writes a page and a Server Action, nothing else.
Output: the route group, the gate, the rail, and a dictionary the rest of the phase consumes.
</objective>

| Boundary | Description |
|----------|-------------|
| public internet -> `/ops/*` | Any unauthenticated request can address every console URL |
| session role -> rendered nav | What a role can see is decided on the server; the client receives only a list |
| ops route -> data layer | Every read/write must cross `lib/db/identity.ts`, never `postgres` or `@vamos/db` directly |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-11 | Elevation of Privilege | ops middleware | mitigate | Three ordered redirects on `getUser()` + `vamos_role` + `aal2`; RLS remains the actual boundary, so a middleware failure degrades to zero-row queries, never a data leak |
| T-06-12 | Elevation of Privilege | `(ops)/ops/layout.tsx` | mitigate | The layout re-runs `requireStaffClaims()` server-side rather than trusting that middleware ran — a matcher regression cannot silently open the console |
