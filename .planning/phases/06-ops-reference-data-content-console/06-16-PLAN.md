<objective>
Make the database the runtime dictionary, at the one seam Phase 1 built for it, last — and ship the
way back before shipping the way forward.

`apps/web/i18n/request.ts` has carried this comment since Phase 1: *"The loader seam D-14 names:
Phase 1's implementation reads the matching JSON file below; Phase 6 swaps this function's body for a
`content_strings` query and no call site elsewhere has to move."* This plan is that swap and nothing
more. `stripMeta`, `mergeWithEnglishFallback`, `onError` and `getMessageFallback` stay exactly as they
are — D-03 says nothing else in that file moves, and the reason is that those four functions are what
make a partial dictionary degrade gracefully. Changing them in the same pass as the source would make
a rendering regression impossible to attribute.

**Why this plan is last.** D-17 sequences the swap after the editor is built and proven against a
seeded table, because swapping early risks a blank or English-only public site. There is a second,
sharper reason specific to this phase: after the swap, `content_strings` is where *every* string comes
from, including every `ops.*` key that plans 03 through 17 added to the JSON files. If the swap lands
before those keys are in the database, the console itself renders empty. So this plan regenerates the
seed from the finished JSON first, then swaps, then proves parity.

**Three ways back, because one is not a rollback.** `CONTENT_SOURCE` is an environment kill switch
that selects the JSON loader without a deploy of new code. A failed or empty database read falls back
to the JSON import at runtime and logs loudly rather than silently — a silent fallback is how a broken
swap survives to production looking fine. And `docs/build/CONTENT-STRINGS-RUNBOOK.md` writes down the
revert as a procedure a human can follow at 6am.

**The trap 06-10 found, closed here.** `packages/db/supabase/seed.sql` ends its `content_strings`
insert with `on conflict (key) do update set en = …, de = …, ar = …, pending_value = …`, and the seed
is generated from the JSON files. So `pnpm db:push`, which runs `supabase db push --include-seed`,
overwrites every console edit with the repository's values. Locally that is correct and wanted. On the
hosted project, once the Content screen is in real use, it is data loss. This plan makes both
directions explicit and scripted — `db:seed:gen` pushes JSON into the database, `i18n:pull` brings
database values back into the JSON — and states the release-order rule in the runbook.

Purpose: I18N-07's actual requirement, with a way back that exists before it is needed.
Output: one loader module, one seam swap, one parity gate, one reconciliation script, one runbook.
</objective>
