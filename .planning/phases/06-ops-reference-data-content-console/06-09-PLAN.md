<objective>
Give staff a way to find a customer and read what they have booked — and nothing more.

`bookings`, `booking_legs` and `customers` are all in Phase 2's seventeen-table staff working set,
so a staff session holds INSERT/UPDATE/DELETE on them at the database layer. This screen deliberately
uses none of it. Booking mutation — assign, cancel, refund, confirm — is OPS-01…05 in Phase 8, and
shipping a half-built write path here would mean Phase 8 inherits a surface it has to unpick (D-26).
The module this plan writes exports no mutation at all, which is a structural guarantee rather than
a discipline.

Two schema facts shape the screen. `customers.erased_at` is Phase 10's redaction marker and is
guarded by `tg_customers_erasure_guard` — a redacted customer must read as redacted, not as a
customer with oddly empty fields. And `bookings.price_total_rappen` is nullable: a booking that has
no `price_snapshot_id` yet has no total, which renders `CHF 000`, never `CHF 0.00`.

Nothing is seeded — `public.customers` and `public.bookings` are both empty until Phase 7 writes the
first real booking. The empty state is the state this screen ships in and must be designed, not
incidental.

Purpose: OPS-07, read-only, ready for Phase 8 to add mutation on top.
Output: a searchable list, a detail view with booking history, one spec.
</objective>

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|

| T-06-53 | Information Disclosure | redacted customer fields | mitigate | Redacted rows omit contact columns from the SQL projection, so no component change can leak them; the redaction branch renders before the field grid |
| T-06-54 | Information Disclosure | full customer list in the client payload | mitigate | Search is server-side via a `?q=` param; no client-side filter over a complete dataset |
