<objective>
Install the two Supabase SDKs and build the single most load-bearing piece of glue in this phase:
the function that turns a live Supabase staff session into the `VamosClaims` object
`asStaff(env, claims, fn)` binds into `request.jwt.claims`.

Nothing else in Phase 6 can be right if this is wrong. `app.is_staff()` reads three facts out of
that GUC — `app_metadata.vamos_role`, `aal`, and `sub` — and a claims object missing any one of
them makes every staff query return **zero rows with no error at all** (Phase 2's own stated
failure mode). The two facts are not in the same place: `app_metadata` comes off the re-validated
user object, but `aal` and `session_id` are JWT payload claims that `getUser()` does not return.
This plan is where that is resolved once, in one file, with a test — not re-derived per screen.

Purpose: give every later plan one import (`requireStaffClaims`) instead of an auth puzzle.
Output: two SDKs, three Supabase client factories shared with Phase 5, one claims bridge, one spec.
</objective>

    Sourcing each field, and why the two sources are different:
    - `sub`, `email`, `app_metadata` come from `supabase.auth.getUser()` — a server round-trip that
      re-validates the token. `getSession()` is never the authority for an authorisation decision
      (Supabase's own documented rule, and the anti-pattern 06-RESEARCH names).
    - `aal` comes from `supabase.auth.mfa.getAuthenticatorAssuranceLevel()`'s `currentLevel`, mapped to
      the `"aal1" | "aal2" | "aal3"` union. Do not read `aal` off the user object — it is not there.
    - `session_id` comes from the access token's `session_id` claim. Read it by base64url-decoding the
      JWT payload segment of `getSession()`'s `access_token` **for that one non-authorisation field
      only**, with a comment stating that the authenticity decision was already made by `getUser()`
      above and this decode is transport-format parsing, not trust. Do not add a JWT library for this.
      If the field is absent, leave `session_id` undefined — `claimsForSql` tolerates it.
    - `role` is the literal `"authenticated"`. It is the Supabase JWT role, not the Vamos role, and
      naming it anything else breaks `app.jwt()`'s expected shape.

    Never spread the user object into the claims. Build the object field by field, mirroring
    `claimsForSql`'s own defence, so `user_metadata` (customer-writable through the client SDK, Phase 2
    D-04) has no path into SQL.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser cookie -> Next.js server | An attacker-supplied session cookie reaches `getUser()`; only the server round-trip decides authenticity |
| Supabase session -> `request.jwt.claims` GUC | Whatever this bridge emits becomes SQL-visible identity for every ops query |
| build output -> browser bundle | The service-role key must never cross into client JS |
