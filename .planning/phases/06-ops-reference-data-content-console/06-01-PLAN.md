<objective>
Add the one small, additive SQL surface Phase 6's console needs and Phase 2 deliberately did not
build: three self-scoped, security-definer functions that let a **non-admin** staff member read
and edit their own `public.staff` row and claim their own invite — plus the pgTAP that proves
`settings_versions` cannot be mutated from the console's connection.

**Why a migration at all, when 06-CONTEXT's `<domain>` says this phase writes none.** That
sentence was written against the schema as designed; the schema as *applied* closes a door the
phase's own scope needs open. `20260823000023_rls_staff.sql` creates `staff_admin_write` as
`AS RESTRICTIVE FOR ALL to vamos_staff using ((select app.is_admin()))` — restrictive, and `FOR
ALL`, so it ANDs against SELECT too. A dispatcher session therefore reads **zero rows** from
`public.staff`, including its own. OPS-09's "staff's own profile" screen and AUTH-05's
accept-invite step both need that row. The two alternatives are worse:

- Widening `staff_admin_write` would reopen the exact door Phase 2's own comment says it closed
  ("a dispatcher must not be able to write `public.staff`"). Rejected.
- Doing the writes with the service-role key from a Route Handler bypasses RLS *and* the audit
  trail's attribution: `tg_audit_row` (`…17_audit_log.sql`) derives the actor from `app.uid()`,
  which is NULL under `service_role`, so every profile edit would land in `audit_log` as
  `actor_kind = 'system'`, `actor_id = null`. Rejected.

A security-definer function called from inside `asStaff` keeps the transaction's
`request.jwt.claims` GUC set, so `app.uid()` and `app.is_staff()` still resolve and the audit row
is attributed correctly. `public.staff` has no `FORCE ROW LEVEL SECURITY` (only the nine
append-only tables in `…19_append_only.sql` do), so a definer function owned by the table owner
bypasses RLS — which is precisely why every statement in this file must carry its own
`where user_id = app.uid()` scope rather than leaning on a policy.

Purpose: unblock the profile screen (06-17) and accept-invite (06-05) without loosening any
Phase 2 policy.
Output: one additive migration numbered clear of Phase 4's reservation, two pgTAP files, and a
hosted apply.
</objective>
