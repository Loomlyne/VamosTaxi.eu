## What changed

- `/sign-in` "Email me a link" for an address with no account now makes the account (public site only; the
  dashboard never does). The person gets the approved "Confirm your email" mail. After SIGN IN on the confirm
  page, or after the 6-digit code, they land on `/sign-up?state=finish`: their address read-only, first name,
  last name, mobile number (optional), the 26.5 account tick, "Finish account", "Not you? Sign out".
- Finish stores the tick (`account_agreement_records`, surface `sign-up`, choice `create`, version
  2026-09-29), marks the account finished, copies name and mobile onto `public.customers` (your dashboard's
  customer list and checkout's prefill read that row), then saves them on the account.
- Until finished, `/account` and `/bookings` send the person back to the finish step. A password-reset link
  keeps its own page. Accounts from `/sign-up`, checkout, staff and everything made before the ship are never
  asked.
- Both `/sign-up` forms ask for the optional mobile number; "Sign up with a link" now also asks the names.
  Mobile numbers are stored as `+` and digits, like checkout.
- The sign-in link has its own per-address limit (same limiter as the other auth mails).
- Nine new dictionary keys in de/fr/ar (the eight signed ones plus "Could not save. Try again.").

Deviation from the plan, settled before hand-over: the plan decided "must finish" from "made after the ship and
no agreement row for the e-mail". The Worker run showed that sends a changed e-mail and checkout accounts to the
step, so the migration instead keeps a mark by user id (`account_finish_pending`), set only for an account the
sign-in link just made. Same migration number. Also from review: the sign-up trigger is NOT changed, so a
sign-up mobile number stays on the account only (see "Not done").

## Migration (one): `20261007170000_account_finish.sql`

- Additive only: new table `public.account_finish_pending` (RLS on, no grant to any role) and three
  `SECURITY DEFINER` functions with an empty search_path, EXECUTE for `vamos_system` only:
  `account_finish_mark(text)`, `account_finish_required(uuid)`, `account_finish_done(uuid, text, text)`.
- Changes no existing row, table or function. Safe on real paid bookings: it never touches bookings or
  payments; `account_finish_done` updates only the signed-in person's own `customers` row, and only when a
  name is given.
- Number given by the coordinator; checked free on every remote branch (2026-10-01). It is not on the control
  board's reservation table (only the control session edits the board).
- Read back after applying: the table exists with RLS on; `has_function_privilege` true for `vamos_system`
  and false for `anon`, `authenticated`, `vamos_public` on all three; no table privilege for any role.

## Deploy order (one Worker)

2. Deploy Worker `vamos`. The dashboard gateway is not touched.

Tested pairs: old Worker + new migration is safe (nothing calls the new functions). New Worker without the
migration is not: new link accounts would never be asked to finish and Finish would answer 503. So the
migration goes first.
