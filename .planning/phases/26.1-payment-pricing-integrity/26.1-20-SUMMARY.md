# Phase 26.1 Plan 20: Staff aal2 when enrolled Summary

**The staff check requires aal2 once the admin has a verified second factor. It runs in SQL and in the app on every request, and only the admin role gets in.**

## Performance

- **Duration:** about 20 min
- **Completed:** 2026-09-28T13:39Z
- **Tasks:** 2 of 2, each with a RED commit and then a GREEN commit
- **Files:** 6 created, 4 modified

## Accomplishments

- `app.is_staff()` and `app.is_admin()` now add one condition: `aal = 'aal2'` or no `verified` row in `auth.mfa_factors` for the caller. Every RESTRICTIVE `*_staff_gate` policy calls `app.is_staff()`, so an admin at aal1 with a verified factor reads zero rows. The pgTAP test proves this on `staff` and `vehicles`.
- New column `staff.sign_in_method` (default `password`, CHECK `password|magic_link`). New setter `public.staff_set_sign_in_method(text)`: SECURITY DEFINER, `search_path=''`, EXECUTE for `vamos_staff` only, requires `app.is_admin()`, and updates only the caller's row. Plan 26.1-22 uses it to enforce the method.
- `staffGateDecision` is one pure function: `allow`, `step-up` or `deny`. `requireStaffClaims` throws `needs-mfa` on step-up and `not-staff` on deny. The dashboard host gate sends step-up and deny to `/login`. The `/ops/*` gate sends them to `/ops/sign-in`, so it no longer redirects to the missing `/ops/mfa-challenge`.
- `nextLevel` is stored on `StaffSession`. `claimsForSql` lists its fields by name, so `nextLevel` never reaches SQL. SQL reads `auth.mfa_factors` itself.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Migration timestamp**
- The plan's filename `20260928170000_…` is already taken by `20260928170000_confirmation_refund_facts.sql`. The migration is `20260928180000_staff_aal2_when_enrolled.sql` instead, which is later than 20260928170000 as required.

**2. [Rule 1 - Bug] The `/ops/*` gate read `vamos_role` from `getUser().app_metadata`**
- The access-token hook mints that claim into the token only, so the old gate saw no role for every user and redirected everyone to `/`. It now reads the role from the access token first, the same way the dashboard host gate and `session.ts` do. Commit `b166d0b5`.

**3. [Rule 2 - Security] nextLevel does not trust the cookie alone**
- `getAuthenticatorAssuranceLevel()` with no JWT argument works out `nextLevel` from the session user stored in the cookie, which the client controls. `effectiveNextLevel()` also checks `getUser().factors`, which the auth server answered. If either shows a verified factor, aal2 is required. SQL is the backstop either way, because it reads `auth.mfa_factors` directly.

**4. [Rule 2 - Security] Added mutant `M3_staff_aal2_dropped.sql`**
- It drops the aal clause from `app.is_admin()`. The mutation gate confirms `staff_aal2_factor.test.sql` goes red.

**5. [Rule 2 - Convention] `OPS_EXEMPT` module-scope `Set` became a frozen array**
- The line had to change anyway to remove `/ops/mfa-challenge`, and apps/web does not allow module-scope collections.

**6. `requireAdminClaims` keeps `not-admin` for a dispatcher**
- It checks for the dispatcher role before the shared gate, so the existing `staff-json` "dispatcher hits withAdmin → 403 not-admin" contract holds. Every other case goes through the same `gateClaims` path as `requireStaffClaims`.
