# Phase 26.1 Plan 09: Mapbox boundary facts and flight number reach the kernel Summary

**Server-resolved canton, city id, airport flag and flight number now flow from Mapbox through toQuoteInput/inputFromLock into QuoteLegInput and the signed lock, closing the pin-pickup canton gap and giving the 26.1-04 kernel's airport-fee/pair-matching logic real inputs instead of undefined ones.**

## Performance

- **Duration:** ~45 min
- **Completed:** 2026-09-28
- **Tasks:** 2
- **Files modified:** 8

## Accomplishments

- `RetrievedPlace`/`ReversePlace` gain `cityId`/`cityName` (from `properties.context.place.mapbox_id`/`.name` — the same context shape Search Box `/retrieve` and Geocoding v6 `/reverse` both return) and `isAirport` (from `properties.poi_category` / `properties.poi_category_ids` / `properties.maki` naming an airport). `reverse()` now also resolves `canton` — previously only `retrieve()` did, which is the exact gap 26.1-04's summary named ("canton is resolved for Search Box picks but not for pins").
- `defaultResolvePlace`'s `"pin"` branch now reads `canton`/`cityId`/`isAirport` off the `reverse()` result instead of only overwriting the display text — a pin dropped on Zurich Airport now produces `origin_is_airport: true` exactly like a Search Box pick of the same POI.
- `toQuoteInput` sets `flight_no` from `request.legs[i].flight_no`, and `origin_is_airport`/`origin_city_id`/`dest_city_id` from the resolved places, so a customer-entered flight number and a server-resolved airport/city id now reach `QuoteLegInput` — the exact fields 26.1-04's kernel (`airportFeeApplies`, `matchCityPair`) already consumes but had never been fed.
- The lock leg gains optional `origin_city_id`/`dest_city_id`/`origin_is_airport` (HMAC-signed, backward compatible); `inputFromLock` restores them on reprice. A lock minted before this plan still verifies and prices with these fields `null`/`false` — never re-derived from the reprice request body.
- `FORBIDDEN_CLIENT_PRICE_FIELDS` grows by eight names (`origin_canton`, `dest_canton`, `canton`, `origin_city_id`, `dest_city_id`, `is_airport`, `origin_is_airport`, `airport`) so a client body carrying any of them anywhere in the tree is refused by that exact field name — these facts are Mapbox-resolved server-side only, per D-08b/D-10's trust boundary.

## Decisions Made

- Kept the new Mapbox behaviour-test fixtures local to `mapbox.test.ts` rather than adding them to the shared `apps/web/lib/geo/fixtures.ts`, per the plan's explicit instruction (`fixtures.ts` is also imported by `aerodatabox.test.ts`, an unrelated suite).
- Added `origin_canton`/`dest_canton`/`canton` to the forbidden-fields list even though the plan's `<behavior>` bullet named only `origin_canton`/`canton` — `dest_canton` is the same trust-boundary fact on the other leg and was already a legitimate internal field name (set by the pipeline, never accepted from a client body), so leaving it off the list would have been an inconsistent gap.
- Field names for Mapbox POI/city detection (`properties.context.place.mapbox_id`/`.name`, `properties.poi_category`, `properties.poi_category_ids`, `properties.maki`) were taken from this plan's own `<interfaces>` section, which the plan-authoring pass had already flagged for Context7/ctx7 confirmation. Neither the Context7 MCP tool nor the `ctx7` CLI fallback was available in this execution environment (`command -v ctx7` → not found, no `mcp__context7__*` tools present), so the field names are the plan-authored ones plus training-data knowledge of the stable, long-documented Mapbox Search Box / Geocoding v6 `context.place` and POI-category shapes — not a fresh live-doc fetch. Anyone reviewing pricing-relevant behavior later should re-verify these four field names against a current Mapbox Search Box / Geocoding v6 response before relying on them for anything beyond this plan's offline fixture tests.
