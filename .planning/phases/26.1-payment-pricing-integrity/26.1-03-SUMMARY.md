# Phase 26.1 Plan 03: Dead-letter queue consumer + ops must-fix alerts Summary

**A Stripe event that exhausts its 8 retries now reaches a live DLQ consumer that alerts info@vamostaxi.site once (event id, type, object id, and — when resolvable — the booking reference, never a card or customer name) and always acks, closing the D-06 gap where the producer-side DLQ existed with no consumer at all.**

- **Completed:** 2026-09-28T02:47:00+04:00

- **Files modified:** 10 (2 created, 8 modified)

## Accomplishments
- `worker.ts`'s `queue()` branches `batch.queue.endsWith("-dlq")` to `lib/checkout/dlq.ts` before the ordinary Stripe-event dispatch, and always `message.ack()`s in that branch regardless of outcome — a DLQ message is structurally incapable of being retried into itself
- `handleDlqMessage` resolves a `cs_` object id's booking reference via `public.checkout_reference_for_session` (`vamos_system` EXECUTE only, no table SELECT — the existing 20260924193000 migration), leaves `pi_`/`ch_` ids with `reference: null`, and never calls `settlePayment`, `begin`, or Stripe
- `wrangler.jsonc` adds the DLQ's own consumer entry (`max_batch_size: 1`, `max_batch_timeout: 30`, deliberately no `max_retries`/`dead_letter_queue`) under both `env.staging` and `env.production`
- `OpsMustFixKind` gains `"stuck-payment"` and `"paid-after-cancel"`; `OpsMustFixForEmail` gains an optional `detail: { eventId, eventType, objectId }` rendered in its own Fact block, with a new test asserting the stuck-payment HTML contains the event id/type/object id and never a customer name, email, card, or `CHF`
- `deliverStuckPaymentAlert` sends the alert even when no booking row can be resolved (a `pi_`/`ch_` id, or a `cs_` id with no matching payment row) — it deliberately does not route through `deliverOpsMustFix`'s or `sendOpsMustFix`'s `trips.length === 0` early-return guards
- `deliverPaidAfterCancelAlert` mirrors the existing `deliverOverlapMustFix` pattern for a real booking row
- New copy in all four languages for both kinds (Swiss German "ss", no "ß" — count unchanged at 0)
- 105 emails tests green (7 new stuck-payment/paid-after-cancel assertions), 19 dlq+settle tests green, full web suite 1641/1641 green, `pnpm i18n:check` green (2493 keys), `tsc --noEmit -p .` clean in both `apps/web` and `packages/emails`, `wrangler deploy --dry-run --env staging` parses the edited config cleanly
