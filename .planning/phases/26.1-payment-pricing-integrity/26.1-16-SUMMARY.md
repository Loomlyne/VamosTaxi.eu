# Phase 26.1 Plan 16: Pay-link recipient states Summary

**The pay-link recipient now sees one of three states. "Already paid" shows the reference and no card form. "Payment received twice — refunded" appears when their own charge lost the race. An expired link shows a recipient-specific message. The return route sends a refunded duplicate to `/confirmation/<ref>?charge=refunded`. All states ship in en, de, fr and ar.**

## Performance

- **Duration:** ~20 min
- **Tasks:** 2/2
- **Files:** 16 (2 created, 14 modified)

## Accomplishments

- **Pure mapper (`pay-client-states.ts`):**
  - `pay_link_paid` maps to `alreadyPaid`.
  - `pay_link_refunded_duplicate` maps to `raceRefunded`.
  - `pay_link_expired` and `quote_expired` map to `expired`.
  - A client secret maps to `payable`.
  - Any other refusal keeps its existing alert key.
  - A reference that does not match `BOOKING_REFERENCE_RE` is never echoed.
- **PayClient:**
  - Stores its own Checkout Session id in `sessionStorage` under `vamos.payLink.session.<first 12 token chars>` and sends it as `session_id` on every open.
  - For paid and refunded states, renders a static `Card`:
    - Already paid: `circle-check` icon in `--vt-success`. The reference sits in a `vt-dir-keep` span.
    - Race refunded: the same card in the neutral `--vt-text-muted` tone.
  - Neither card shows `TokenDummyFields`, `PaymentPanel` or the Pay button.
  - An expired link shows `Alert tone="danger"` with a title and body.
- **Settle and return:**
  - `settle.ts`: the ack carries `settled` once a duplicate refund lands.
  - `settlePaidReturn`: returns `"duplicate"`.
  - Return route: redirects a duplicate to `?charge=refunded`.
  - `ConfirmationClient`: shows an info `Alert` above the voucher for that query.
- **Design laws:**
  - No new colour, radius or shadow. Only tokens are used: `--vt-space-3`, `--vt-success`, `--vt-text-muted`.
  - No tinted yellow and no glow.
  - Logical properties only (`margin-block-end`).
  - Both new CSS rules hang off `[data-*]` attributes.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] PaymentPanel leaves the page right after confirm**
- **Found during:** Task 2.
- **Issue:** `PaymentPanel` calls `window.location.assign(settleUrl)` straight after `checkout.confirm`. PayClient therefore could not poll the open route after an in-page payment, as the plan requires.
- **Fix:** Added an optional `onPaid(destination)` prop, used on the card path and the express path. PayClient passes a stable `useCallback`. Without the prop, the old behaviour stays, so CheckoutClient is untouched.
- **Commit:** `999919b4`

**2. [Rule 3 - Blocking] `token-pay.test.ts` pinned `chargeGateAlert` inside PayClient**
- **Issue:** The charge-gate table moved into the pure mapper, as the plan's "other codes → existing alert keys" requires.
- **Fix:** The pin now slices `chargeGateAlert` from `pay-client-states.ts` with the same assertions. The "no ternary fallback" check also runs on the lib file. Two new asserts: PayClient calls `payStateFromOpen(json)`, and it no longer defines its own `chargeGateAlert`. No assertion was removed.
- **Commit:** `999919b4`

**3. [Rule 1 - Correctness] `settled` only after the refund lands**
- **Issue:** Mirroring `row.duplicate` directly would let the return route say "automatically refunded" even when the Stripe refund failed. In that case the code only alerts ops.
- **Fix:** `settled: { duplicate: true, revived }` is returned only after `refund` and `recordDuplicateRefund` succeed. Pinned in `settle.test.ts`.
- **Commit:** `c03e83c3`

**4. [Rule 2] Spacing rules for the new elements**
- `confirmation.css`: `[data-confirmation-charge-refunded] { margin-block-end: 24px }`.
- `checkout.css`: `[data-pay-link-done]` sets the gap and resets margins.
- Neither file was in `files_modified`. Both are layout-only.

## Known limitations (for the verifier)

- **Webhook first, then the return route:** if the webhook settles a duplicate before the browser reaches `/api/checkout/return`, the return route's own event is `superseded` and answers `paid`. The payer then lands on the normal confirmation without the refunded notice. The in-page flow covers this case, because the open-route poll reads `pay_link_refunded_duplicate` from Postgres. A redirect-only wallet return in that order does not. Closing the gap needs a system read of the payment status by session id, which means new SQL. It is out of scope and was not invented here.
- **Before the refund is recorded:** `checkout_pay_link_state` answers `refunded_duplicate` only once the duplicate refund is recorded. A poll that lands between settle and refund-record reads `paid` and continues to the settle route. The window is one handler run.
