# Phase 26.1 Plan 25: Passkey option end to end Summary

**A registered passkey is now a real factor. The staff gate needs aal2 or a passkey sign-in once one exists. Settings lists passkeys from the auth server and removes them behind the re-auth dialog. The ops sign-in offers "Use your passkey" as the second step. Adding a passkey needs a fresh re-auth (D-17c).**

Passkeys are ON (26.1-24), so this plan ran in full. It was not skipped under D-16c.

## Verified against GoTrue (local v2.195.0, software authenticator)

The passkey API is experimental and its AMR name is not in the auth-js types, so it was checked on the running server. Passkeys were switched on in the local `config.toml` for the probe only; the change was reverted afterwards and never committed. The probe used a throwaway user and made no live calls.
- A password session has amr `[password]` at `aal1`.
- After `passkey.verifyRegistration`, `getUser().factors` is `[]` and `nextLevel` stays `aal1`. `passkey.list()` returns the passkey.
- A passkey sign-in has amr `[passkey]` at `aal1`.
- `passkey.delete({ passkeyId })` works.
- The new code, run on the same server:
  - With no passkey, a password session is `allow`.
  - After registering, the same password session is `step-up` (`hasPasskey: true`).
  - A passkey session is `allow`, and no passkey list call is made.
  - `listPasskeys` returns only `id, friendlyName, createdAt, lastUsedAt`.
  - `removePasskey` from a step-up session returns `mfa-aal2-required`. From an allowed session with re-auth it succeeds, and the list is then empty.

auth-js 2.112.4 API used (from `dist/module/lib/types.d.ts`): `auth.passkey.startRegistration / verifyRegistration / startAuthentication / verifyAuthentication / list / delete`. The client needs `experimental.passkey: true`.

## Accomplishments

- **Gate (`staff-gate.ts`):** `staffGateDecision` takes `hasPasskey` and `amrMethods`. The rules, in order:
  1. Not the admin: `deny`.
  2. A verified MFA factor: aal2 is required, as before.
  3. A passkey: aal2 or amr `passkey`.
  4. Otherwise: `allow`.

  New helpers: `isPasskeySession`, `amrMethodsOf`, and `passkeyCheckNeeded`. The last one lists passkeys only for an admin whose session is not already decided.
- **Claims (`session.ts`):** `passkeyGateInputs` reads the amr from the access token that `getUser()` just had the auth server verify (T-26.1-77), and lists passkeys from the server when needed. `getStaffClaims` stores `amrMethods` and `hasPasskey`. `claimsForSql` lists its fields by name, so neither reaches SQL. `staffDecisionOf(claims)` is the one decision used by `gateClaims` and `/api/auth`.
- **Both middleware gates** (the dashboard host and `/ops/*`) pass the same passkey inputs, so every door decides the same way. The middleware Supabase client turns on `experimental.passkey`.
- **`/api/auth`:**
  - `passkey-list` returns id, name and dates only.
  - `passkey-remove { passkeyId }` requires, in order: a UUID, a gate `allow`, a fresh `vt_reauth`, and the id being in the caller's own list. Then it deletes. A failed check answers 403.
  - `passkey-register-start` and `passkey-register-verify` run `staffPasskeyAddGate()` for staff sessions: admin only, gate `allow`, fresh re-auth (D-17c). Customers are unchanged.
  - `mfa-status` still reports `passkey`.
- **OpsSettings:**
  - Passkey rows come from `passkey-list`, loaded on mount and reloaded after every add or remove. `passkeyAdded` is `passkeys.length > 0`. The local-state override is gone.
  - Each row shows the `shield-check` icon, "Passkey registered for this account.", the friendly name (muted, `vt-dir-keep`, `data-i18n-skip`) and a secondary **Remove passkey** button.
  - **Add a passkey** and **Remove passkey** both go through `withReauth`, which opens the "Confirm and continue" dialog.
  - After adding, if the authenticator app is off, the page asks for the new passkey once (`confirmPasskey`, through `passkey-start/verify`). If the admin cancels, a **Use your passkey** button stays. If the app is on, the session is already aal2, so the page does not ask.
- **AuthForm (ops) stage `mfa`:**
  - `stepUpNeed(method)` asks `mfa-status` and returns `totp` if the app is enrolled. Otherwise it returns `passkey` if a passkey exists and this sign-in was not a passkey. Otherwise it returns nothing.
  - `openStepUp(need)` is the only way into `stage: 'mfa'`. `resumeStepUp` (needs-mfa) uses it too.
  - The passkey step shows "One more step", "This account has a passkey. Use it to finish signing in.", a primary `shield-check` **Use your passkey** button, a danger alert on failure, and "Use another sign-in".
  - `/dashboard` opens only after `result.ok`. `passkeySignIn()` is shared with the form's "Sign in with a passkey".

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] A passkey sign-in never reached the browser**
- **Found during:** Task 1
- **Issue:** `passkey-verify` answered `json({ ok: true })` without the new session's `Set-Cookie`s. OpenNext does not attach `cookies().set` to a hand-built response (CLAUDE.local.md), so the existing "Sign in with a passkey" button could never sign anyone in.
- **Fix:** `sessionJson({ ok: true }, setCookies)`, pinned by a test.
- **Commit:** `2621d712`

**2. [Rule 2 - Security] Middleware gates learn passkeys too**
- **Issue:** If only `requireStaffClaims` knew about passkeys, the dashboard host would render the console for a password-only session while every API call answered `needs-mfa`.
- **Fix:** Both gates call `passkeyGateInputs`, and the middleware client turns on `experimental.passkey`. Files outside `files_modified`: `apps/web/middleware.ts`, `apps/web/lib/supabase/middleware.ts`, `apps/web/lib/ops/session.test.ts`.
- **Commit:** `2621d712`

**3. [Rule 2 - Correctness] Confirm the new passkey after adding it**
- **Issue:** Registering a passkey does not upgrade the current session, so the gate would bounce the admin to sign-in on the next click.
- **Fix:** The page asks for one passkey sign-in straight away. It skips this when the authenticator app is on, because that session is already aal2 and a passkey sign-in would drop it to aal1.
- **Commit:** `4aeb8b88`

**4. [Rule 2 - Correctness] The passkey step-up is offered only without the authenticator app**
- **Issue:** A passkey session is aal1. With the app enrolled, SQL still needs aal2, so offering the passkey there would lead into a second step-up.
- **Fix:** With both enrolled, the step is the 6-digit code.
- **Commit:** `4aeb8b88`

**5. [Scope] Other files touched:** `app/vamos-i18n-dict.js` (AuthForm strings are translated through the shared dictionary, not a local key table) and `ops-signin-stepup-dc.test.ts` (the plan's own verify command runs it).

**6. [Naming] The plan's `mfaUsePasskey` key has no equivalent**
- AuthForm has no key table; its visible text is English in the markup, looked up in the dictionary. The string "Use your passkey" is what was added.

## SQL note (for the owner, no change made)

Passkeys are in `auth.webauthn_credentials`, which a SECURITY DEFINER function could read. `app.is_staff()` could count them. But a passkey session is aal1, so SQL would also have to accept the `passkey` amr from the JWT instead of requiring aal2. That is a follow-up migration only if the owner asks. For now the app gate covers the console on every request and in both middleware gates.
