# Phase 26.1 Plan 08: Stripe refund and dispute events reach the database Summary

**`charge.refunded` and `charge.dispute.created|updated|closed` no longer fall through to `ignore`. The consumer re-reads the charge or dispute from Stripe. Dashboard refunds land in `booking_refunds` as `stripe_dashboard` against the exact payment row. App refunds are applied exactly once, whichever event arrives first. Disputes are mirrored into a new staff-only `booking_disputes` table.**

## Accomplishments

- `stripe_charge_refunded_record`:
  - Idempotent on `stripe_refund_id`.
  - Refuses an app-tagged refund with `P0002 app_refund_pending` until the app's own recorder has written the row. After that it is a no-op. Both arrival orders are proven by pgTAP.
  - A refund on a `duplicate` payment row never touches the booking's `refunded_rappen` or `refund_status`.
- `stripe_dispute_upsert` keeps one row per dispute. An older event timestamp never overwrites a newer status (T-26.1-29).
- `booking_disputes` has forced RLS. Only `vamos_staff` can read it, and only with SELECT. pgTAP proves that anon, customer (`authenticated`) and `vamos_guest` are all refused.
- Both functions: `SECURITY DEFINER`, `search_path=''`, `EXECUTE` for `vamos_system` only.
- Consumer changes:
  - The charge (with `refunds` expanded) or the dispute is retrieved before `begin()`, so `[ch_/du_, pi_]` share one ordering window.
  - A Stripe retrieve failure means retry.
  - `app_refund_pending` means `{ retry: true, delaySeconds: 30 }`, which `worker.ts` passes to `message.retry({ delaySeconds })`.
  - Other `P0002` errors retry; the DLQ alert fires if they never resolve.
  - Permanent SQL errors stamp the event and ack.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The stalled agent's migration called `pg_catalog.least(...)` and `pg_catalog.coalesce(...)`**
- **Found during:** Task 1 GREEN.
- **Issue:** `LEAST` and `COALESCE` are SQL constructs, not catalog functions. A schema-qualified call raises `function pg_catalog.least(integer, numeric) does not exist` the first time a dashboard refund is recorded.
- **Fix:** Removed the qualification. `least(100::pg_catalog.numeric, …)` and `coalesce(…)` work under `search_path=''`.
- **Files:** the migration. **Commit:** `df646423`.

**2. [Rule 1 - Plan conformance] Two corrections to the stalled migration**
- Payment resolution now tries the PaymentIntent first and the session second. The draft did session first; the plan says "by PI (or session)".
- `refund_status='refunded'` is now set only once refunds reach the full charge. The draft set it on any refund; the plan says "at full".
- **Files:** the migration. **Commit:** `df646423`.

**3. [Rule 3 - Blocking] `tests/integration/webhook-replay.spec.ts` fixtures**
- **Issue:** Two hand-built `SettleDeps` literals stopped compiling once `SettleDeps` gained the five money-event deps.
- **Fix:** Added stubs to both. The charge and dispute retrieves throw "not used". Neither scenario is a charge or dispute event. No assertion changed.
- **Commit:** `28d733d1`.

**4. [Test fix, not loosening] pgTAP `is(rappen, integer)`**
- The spec compared the `rappen` domain against an integer literal, and pgTAP has no overload for that. It now casts `::int` before comparing. Same values, same assertions. **Commit:** `df646423`.

**5. [Structure] `applyHandleResult` extracted into settle.ts**
- `worker.ts` imports the OpenNext bundle, so vitest cannot import it.
- The ack/retry branch now lives in `applyHandleResult`. The worker calls it, and a source-scan test asserts that call.
- This is how the plan's requirement is met: "a test asserts the queue handler passes delaySeconds".

### Behaviour choices not spelled out in the plan

- Only refunds with status `succeeded` are recorded.
- A `pending` refund retries after 30 s, so it lands once Stripe settles it. A pending refund that later fails would otherwise inflate `refunded_rappen`.
- A charge whose `refunds` list is truncated (`has_more`) emits a warn.
- A refund in a currency other than CHF is never recorded as rappen: the event is settled with `non_chf_refund`. The same rule applies to a non-CHF dispute amount, which is stored as `null`.
