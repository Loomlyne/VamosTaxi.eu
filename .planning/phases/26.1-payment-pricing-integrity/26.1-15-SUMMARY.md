# Phase 26.1 Plan 15: 24-hour pay-link hold and pay-link state Summary

**A sent pay link now holds the booking and its price for 24 hours from the moment it is sent. The link lookup, the charge gate trigger and the unpaid cron all read one clock, `bookings.hold_until`. When a link is no longer payable, the open route answers `pay_link_paid` (with the reference), `pay_link_refunded_duplicate` (with the reference) or `pay_link_expired`.**

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Correctness] The hold is capped in SQL and a resend does not restart it**
- **Found during:** Task 1.
- **Issue:** The plan's text says `hold_until = token_expires_at`. Taken literally, a resend (D-37: allowed, and "the 24h clock does not restart") would push the hold another 24 hours. The threat register (T-26.1-47) also wants the hold capped at 24 hours.
- **Fix:** `hold_until = least(p_token_expires_at, coalesce(pay_link_sent_at, now()) + 24 h)`, and the new pay token is stored with that same expiry. pgTAP section 3 proves it.
- **Commit:** `6a7c6f0a`

**2. [Rule 1 - Consistency] Both charge-gate clocks honour the hold**
- **Found during:** Task 1.
- **Issue:** The plan names "the expiry check", but the trigger has two: the `expires_at` payment window and the `quote_lock_expires_at` lock (D-25). If only one honoured the hold, the payment would still be refused.
- **Fix:** Both checks use the greatest-of expression. The rest of the body is verbatim.
- **Commit:** `6a7c6f0a`

**3. [Rule 3 - Blocking] `pay-link-gate.test.ts` in the plan's verify list pinned the old behaviour**
- **Issue:** The file is not in `files_modified`, but its source pins contradict D-20/D-21. The plan's verify command runs it, and the plan's own acceptance grep requires the old call to be gone.
- **Fix:** Updated the pins as described above.
- **Commit:** `da36e90f`
