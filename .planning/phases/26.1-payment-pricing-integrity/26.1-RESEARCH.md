# Phase 26.1: Payment and pricing integrity - Research

**Researched:** 2026-09-27
**Domain:** Stripe payments/webhooks/refunds on Cloudflare Queues, server-side pricing engine (TypeScript, no SQL pricing function), Supabase Auth MFA (TOTP + WebAuthn), Postgres/Supabase RLS
**Confidence:** HIGH for code-path findings (all file:line evidence read directly from this branch); MEDIUM for Supabase Auth WebAuthn passkey API (fast-moving, "experimental" flag); LOW/owner-only for anything requiring Stripe dashboard or live-DB access

## Summary

Phase 26.1 fixes nine requirement clusters (INT-01…INT-09), all evidenced in
`docs/audit/2026-vamos-audit.md`. This research re-verified every audit claim against
the actual code on this branch (not the audit's HEAD `f0238bd`) and found the branch has
already partially closed some gaps (X0 root cause fixed by the owner, `ops_refund_record`
rappen-cast fix already migrated, `#57` abandon-unpaid already shipped) while the core
integrity bugs remain: the capture gate still silently acks a paid-but-cancelled booking
instead of reviving it (D-03), the DB never stores the real PaymentIntent id at
settlement (D-05/X0b), no DLQ consumer exists (D-06/X2), `charge.refunded`/
`charge.dispute.*` fall through `settle.ts`'s `outcomeFor()` as `"ignore"` (D-07), the
airport fee *replaces* the start fare instead of adding to it (D-08/P1), city and canton
pairs only match one direction (D-08/D-09/P2), `pricing_live` is hard-coded `true` in the
pay-link route (D-12/X4), coupon redemptions are never written at booking time (D-11/X3),
canton matching has no data path at all — the Mapbox-derived canton code is computed but
never sent to `/api/quote` or read by the pricing engine (D-10/D-10a/P6), the refund-tier
RPC has a silent "no refund, no review" zone inside 6 hours and after pickup that
contradicts D-24/D-25, vehicle-class hard-delete already works but "hide with a reason"
does not exist (D-15), and staff `aal2` enforcement is fully absent even though the
session helper already fetches the AAL (D-16a/S1).

Two of the nine requirement clusters (INT-01, and half of INT-06/INT-07) are lighter than
the audit implies once this branch's PR #60 fixes are accounted for. The heaviest clusters
are INT-03 (money/webhooks — new schema needed for disputes), INT-04+INT-05 (pricing
formula + real canton matching — touches the pricing kernel and its Zod input schema),
and INT-09 (MFA enrollment UI does not exist in code at all; the DC mock
`app/ops/OpsSettings.dc.html` is the only source of visual truth for it and needs
inspection before planning tasks).

**Primary recommendation:** Split into five sub-plans/waves by blast radius —
(1) money/webhooks (INT-01, INT-02, INT-03), (2) pricing formula + zones (INT-04,
INT-05), (3) pay-link + refund tiers (INT-06, INT-07), (4) classes (INT-08), (5) admin
sign-in (INT-09) — in that order, because 1–3 touch live payment correctness and 4–5 are
isolated. Every SQL migration in every wave is written to disk, tested with
`pnpm db:start && pnpm db:reset && pnpm db:test`, and handed to the owner as a file to
apply in the SQL editor — the agent never runs `db:push` or `db:link` against
`yaumjzvylngfjhtuffqs`.

### Locked Decisions

**Stripe**
- D-01: Only the Vamos Taxi sandbox (`acct_1UIZmqHcNp9GZYjz`) is used. The old account (`…AJS2YBf21S`) is retired, and Koss disables its webhook.

- D-03: A successful payment always ends as a confirmed booking. If the booking was cancelled or expired while the customer paid, the payment **revives it as confirmed**, and the customer gets the confirmation. Refund only when the trip truly cannot run. This replaces the capture gate's silent ack (`settle.ts:163-179`).
- D-04: Every cancel or expire path also expires the open Stripe session (account cancel, cron expire, abandon).
- D-05: Refunds use the real PaymentIntent ID, never the `cs_` session ID. The sandbox charge `cs_test_a1lyA5…` (CHF 77.80, Apple Pay) gets a refund recorded in `booking_refunds`.

- D-07: `charge.refunded` and `charge.dispute.*` reach the DB.

**Price formula (owner rule, decisions 14 and 2026-09-27 evening)**
- D-08: Per leg: start fare + per-km × km + airport fee (airport pickup only, **added** to the start fare) + city-to-city price (when the pair matches) + every surcharge enabled in the dashboard − coupon. VAT 8.1 % on top. No minimum fare. No distance bands. No region premiums.
- D-08a (order): fare lines add up first; then the **coupon** (percentage) comes off, and the total **never goes below CHF 0**; then **VAT 8.1 %** is added on top. Coupon before VAT.
- D-08b (airport fee trigger): the airport fee applies when the pickup is an airport **or** the customer entered a flight number.
- D-09: A city pair covers both directions. It applies only when pickup and destination are in different places.
- D-10: Zones are official **city or canton boundaries** from Mapbox, so any address inside matches. Clean up the duplicate and point-of-interest zones.
- D-10a: Start with **all 26 Swiss cantons**. Every **canton → different canton** pair (both directions) carries **CHF 50**, the **same for Economy, Business and Van luxury** (owner-given amount, 2026-09-27). Other places are added later.
- D-11: Coupon caps are enforced at payment (`coupon_redemptions` is written; customer and email are passed to `evaluate_coupon`).
- D-12: Checkout fails closed when the price book cannot load. `pricing_live` is read, never hard-coded.
- D-13: Every amount comes from the dashboard. Nothing is invented. Version 18 is labelled "placeholder, not owner-approved", and Koss reviews its numbers before any publish. The agent does not click Publish.

**Payment and cancellation rules (owner, 2026-09-27 evening)**
- D-18: A customer who pays is always confirmed (D-03).
- D-19: A customer who does not pay and leaves the payment page has the booking **cancelled automatically** (shipped in #57; keep it).
- D-20 (pay link): when the customer emails a pay link, the booking stays **locked for 24 hours**. The other person paying from the email **confirms** it. Unpaid after 24 hours, it is **cancelled automatically**.
- D-21: if the customer then pays it themselves on the same page, the booking is confirmed, and the pay-link recipient sees a page saying it is **already paid, no need to pay again**.
- D-22 (race): if both try to pay at the same time, **only one is accepted**. If both charges succeed anyway, the second one is **refunded automatically**.
- D-23 (refunds): a paid booking the customer cancels **more than 24 hours before pickup** gets a **full refund automatically**.
- D-24: cancelled **within 24 hours** of pickup: ops (the admin) must **approve** the refund and set the **percentage**.
- D-25: a refund asked for **after** the trip: the admin **accepts or rejects** it.

**Classes and deletes**
- D-14: The three classes are **Economy, Business, Van luxury**. Saden → Economy, V-Class (`mercedes-benz-v-class`) → Business, Van luxury stays. First is dropped.
- D-15: Delete in the dashboard = hard delete when nothing references the row; otherwise hide it everywhere with a reason. `mahaha` is deleted if unreferenced, and tests use Economy.

**Admin sign-in (supersedes the earlier "MFA now" wording)**
- D-16: There are no other staff logins; **only the admin signs in** to the dashboard. The admin is not forced to use a second factor.
- D-16a: In the dashboard account settings the admin chooses how to sign in, and every option must actually work end to end: add a **passkey**, add a **one-time code app (TOTP)**, or switch from **password to magic link**. When the admin has enrolled a factor, sign-in requires it (aal2); without one, password or magic link alone is accepted.
- D-17: Leaked-password protection is on (owner toggle in Supabase Auth). Changing the admin password or email asks the admin to sign in again first.

### Recommended shape for the DLQ consumer (Wave "money/webhooks")

```jsonc

"queues": {
  "producers": [
    { "binding": "STRIPE_EVENTS", "queue": "vamos-stripe-events-staging" }
  ],
  "consumers": [
    {
      "queue": "vamos-stripe-events-staging",

    {
      // New: a consumer for the DLQ itself is just another Queues consumer —
      // Cloudflare has no separate "DLQ consumer" API.
      // https://developers.cloudflare.com/queues/configuration/dead-letter-queues/
      "queue": "vamos-stripe-events-staging-dlq",

      "max_batch_timeout": 30
      // no max_retries/dead_letter_queue — this is the end of the line

```
```ts
// worker.ts::queue() — dispatch on batch.queue, do not add a second exported handler
async queue(batch, env, _ctx) {
```

### Pattern: pricing kernel stays I/O-free (keep)

`lib/pricing/lines.ts`'s own header comment states the contract precisely: "this module
reads no clock, performs no I/O, formats nothing, and never decides IF a surcharge
applies." Every fix in INT-04/INT-05 must stay inside this contract — canton resolution
happens upstream (Mapbox call + request schema), not inside `buildFareLine`/
`buildFixedRouteExtraLine`.

### P1 fix shape — airport fee must ADD, not replace

```ts
// apps/web/lib/pricing/lines.ts — buildFareLine, current (buggy) shape:
const start =
  kind === "airport_pickup"
    ? (distanceRate?.airport_start_rappen ?? null)   // REPLACES base_fare_rappen
    : rowBase;

// D-08 target shape — start fare always applies; airport fee is additive:
const airportFeeApplies = kind === "airport_pickup"; // D-08b: airport OR flight_no present
const start = rowBase; // always the base start fare
const airportFee = airportFeeApplies
  ? (distanceRate?.airport_start_rappen ?? null) // reinterpret this column as a FEE, not a start-replacement
  : null;
amount = start + (airportFee ?? 0) + perKm(...) + classBandExtrasRappen(...);
```
Owner's worked example (Mapbox-verified 2026-09-27, ZRH Airport → Swiss National Museum,
10.19 km): expected `20.00 + 30.00 + 25.48 = CHF 75.48` net; today's code produces
`30.00 + 25.48 = CHF 55.48` because `airport_start_rappen` (30.00) *replaces* the base
start (20.00) instead of adding to it. **Naming caution for the planner**: the DB column
is literally named `airport_start_rappen`, which reads as "the start fare AT an airport"
— renaming it (schema migration) vs. reinterpreting it in code only is a real decision;
reinterpreting in code only keeps rate_version 18's existing (placeholder) data
semantically wrong until the owner re-enters it, which is fine per D-13 (owner reviews
numbers before publish) but should be flagged in the plan's UI/copy so the owner knows
what to enter into that field going forward.

```ts
    (placeHasLabel(leg.origin_place, row.dest_label)   && placeHasLabel(leg.dest_place, row.origin_label))
  )
)
```
Same shape applies to `matchCantonPair`. This means only ~325 unordered canton-pair rows
are needed for all 26×25 ordered combinations (D-10a), not 650.

### Canton wiring gap (D-10/D-10a/P6) — the real root cause

`lib/geo/mapbox.ts::cantonFromProperties()` already extracts the Swiss canton
(`context.region.region_code`) from every Mapbox Search Box suggestion
[VERIFIED: apps/web/lib/geo/mapbox.ts:218-223, `canton: cantonFromProperties(props)` at
line 368]. But:
- `apps/web/lib/quote/schema.ts` (the Zod schema validating `/api/quote` request bodies)
  has **no `origin_canton`/`dest_canton` field at all** [VERIFIED: grep found zero matches
  outside `lib/pricing/types.ts` and `lib/pricing/lines.ts`].
- `lib/pricing/types.ts:230-231` declares `origin_canton?: string | null` /
  `dest_canton?: string | null` on `QuoteLegInput`, and `matchCantonPair` in `lines.ts`
  already prefers these fields over zone-based derivation — but they are never populated
  because nothing upstream sends them.
- `service_zones` (added in `20260825000002_service_zone_types.sql`) has a `zone_type`
  column whose CHECK constraint is `('airport','city','ski','other')` — **`'canton'` is
  not a legal value today**. Canton derivation in `cantonOfZone()` (`lines.ts:158-166`)
  instead scans a free-text `tags text[]` column for a `canton:XX` pattern, or parses the

  fires").

**Smallest correct fix:** the browser already receives `canton` per Mapbox suggestion
(client-side `PlaceCombo`/suggest flow); thread it through to the `/api/quote` request
body as `origin_canton`/`dest_canton`, add those two optional fields to
`lib/quote/schema.ts`, and pass them through `preprocess.ts`/`pipeline.ts` into
`QuoteLegInput`. This makes `matchCantonPair`'s existing "trust `leg.origin_canton` first"
path work with **zero new geometry** — Mapbox's own administrative boundaries *are* the
"official Swiss canton boundaries" D-10 asks for. `service_zones` rows are then only
needed as anchors for `fixed_routes.origin_zone_id`/`dest_zone_id` (which reference a UUID,
not a raw canton code) — 26 zone rows, one per canton, `zone_type` extended to allow
`'canton'` (migration touches the CHECK constraint), tagged `canton:ZH` etc. so
`cantonOfZone()` still has a fallback path for any caller that only has a zone id.

**Confidence: MEDIUM.** The Mapbox extraction code is read directly and is HIGH
confidence; the recommended wiring is this researcher's synthesis, not something already
half-built elsewhere in the repo — verify no other consumer of `QuoteLegInput` assumes
`origin_canton` stays empty before landing this.

### Anti-Patterns to Avoid
- **Writing to `booking_payments.stripe_payment_intent_id` at booking-creation time only**:
  it must ALSO be corrected/backfilled at settlement time, because `ui_mode: "elements"`
  sessions have `payment_intent: null` until the customer confirms.
- **Treating "cancelled while paying" as a refund-first default**: D-03 is explicit that
  revival-to-confirmed is the default; refund is the exception ("only when the trip truly
  cannot run").
- **Building a new geometry/PostGIS layer for cantons**: Mapbox's own geocoding already
  resolves this; adding polygon storage duplicates a solved problem and is a much larger
  surface than D-10a asks for.
- **A single unconditional `aal2` gate**: would lock out the admin before they've enrolled
  a factor, directly violating D-16 ("the admin is not forced to use a second factor").

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Stripe idempotency for concurrent pay-link race (D-22) | A custom in-app lock/mutex | Stripe's own `idempotencyKey` on `checkout.sessions.create`/`refunds.create` (already used everywhere in `lib/checkout/stripe.ts`) + a DB-level uniqueness constraint on `booking_payments` (the audit references a `booking_payments_one_success` constraint already causing `23505` in `settle.ts`) | The constraint + idempotency key combination already exists in the codebase's own patterns; a second successful charge should be *detected* by this existing uniqueness path and then refunded, not prevented by a new lock |
| WebAuthn ArrayBuffer/base64url plumbing | Hand-rolled base64url encode/decode for credential challenges | `supabase-js`'s `auth.mfa.enroll`/`challengeAndVerify` (returns/accepts the shapes the WebAuthn browser API expects) — or `@simplewebauthn/browser` only if friction is real | Supabase's SDK is designed to interoperate directly with `navigator.credentials`; hand-rolling this is a classic source of subtle security bugs |

missing architecture. Plan tasks should say "extend X" far more often than "build Y".

## Common Pitfalls

### Pitfall 1: Fixing the capture gate without fixing the PI-id storage first
**What goes wrong:** If D-03 (revive to confirmed) ships before D-05 (store the real PI
id at settlement), the newly-revived confirmed booking still has `cs_...` in
`stripe_payment_intent_id`, so any subsequent refund on it fails exactly like X0b today.
**Why it happens:** both bugs live in the same SQL function (`checkout_payment_settle`)
and the same code path, and it's tempting to patch only the status-machine part.
**How to avoid:** land the PI-id fix and the capture-gate fix in the *same* migration/PR,
or explicitly sequence D-05 before D-03 within Wave 1.
**Warning signs:** a refund test passes against a *freshly created* booking (payment_intent
already known) but fails against one that went through the full webhook settle path.

### Pitfall 2: Queue consumer testing gap — Miniflare cannot see Hyperdrive
**What goes wrong:** `apps/web/vitest.config.ts`'s own comment says unit tests are
"scoped deliberately away from... Cloudflare Workers pool tooling — Miniflare cannot see
a Hyperdrive binding." A DLQ consumer test that tries to exercise the real `queue()`
handler end-to-end against a live binding will not run in CI the same way `settle.ts`'s
existing tests do (which use `handleStripeMessageWithDeps` with injected deps).
**How to avoid:** write the DLQ consumer the same way `settle.ts` is written — a pure
`handleDlqMessageWithDeps(message, deps)` function unit-testable with injected deps, with
a thin `worker.ts` wrapper wiring real bindings, mirroring the existing `handleStripeMessage`
pattern exactly.

### Pitfall 3: Ordering guarantee assumption for `charge.refunded` vs. `checkout.session.completed`
**What goes wrong:** `stripe_event_begin`'s "superseded" check only compares `object_id`s
already in `p_object_ids` (session id + PI id) — adding `charge.refunded` handling means a
`ch_...` charge id enters the picture for the first time. If the "out-of-order" guard isn't
extended to include the charge id in its object-id set, a `charge.refunded` that arrives
before its `checkout.session.completed` has been processed (unlikely but not impossible
with Queue retries) could be silently treated as unrelated.
**How to avoid:** when implementing D-07, trace how `charge.refunded`'s `objectId` (a
`ch_...` id, distinct from both `cs_...` and `pi_...`) maps back to a `booking_payments`
row — likely needs a lookup by `latest_charge` on the PaymentIntent, not a direct column
match, since `booking_payments` only stores the PI id today.

### Pitfall 4: `service_zones.zone_type` CHECK constraint blocks a straightforward canton row insert
**What goes wrong:** attempting to `INSERT ... zone_type = 'canton'` today throws a CHECK
violation because the constraint added in `20260825000002_service_zone_types.sql` only
allows `('airport','city','ski','other')`.
**How to avoid:** the canton-zones migration must `ALTER TABLE ... DROP CONSTRAINT` and
re-add it with `'canton'` included, before any seed/owner-entry of canton zone rows.

### Pitfall 5: `Duplicate index on distance_bands` / RLS advisor items are Phase B, not this phase
**What goes wrong:** the audit's S14 (Info) performance advisor items are easy to conflate
with this phase's schema changes since both touch `packages/db/supabase/migrations`.
**How to avoid:** keep this phase's migrations scoped to D-01…D-25 only; do not "while
we're in there" fix unrelated advisor findings (that's Phase B, explicitly deferred).

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Replay of an old `checkout.session.completed` after a booking was legitimately re-cancelled for a different reason | Tampering / Repudiation | `stripe_event_begin`'s ordering-by-`stripe_created` "superseded" check already guards this — D-03's revival fix must not bypass it |
| A second, concurrent Checkout Session paid on the same booking (D-22) | Tampering | Existing DB uniqueness constraint (`booking_payments_one_success`, referenced in `settle.ts` as a `23505` case) + Stripe idempotency keys; auto-refund the loser via the existing `applyStripeRefund` pattern |
| Coupon enumeration via `evaluate_coupon` (S6, out of scope for 26.1 but adjacent) | Information Disclosure | Not this phase's fix (Phase B) — do not conflate with D-11's coupon_redemptions write, which is a different bug |
| Staff account takeover via phished password, no second factor | Elevation of Privilege | D-16a's conditional `aal2` gate — must not be bypassable by an attacker who also compromises the session cookie *before* aal2 is checked (verify `requireStaffClaims` checks `aal` on every request, not just at login) |
| A stale/cached `cs_...` value in `stripe_payment_intent_id` used for a refund against the wrong resource | Tampering | D-05's fix directly addresses this; add a defensive check that a refund is refused (not silently misrouted) if the stored id doesn't look like a `pi_...` |
