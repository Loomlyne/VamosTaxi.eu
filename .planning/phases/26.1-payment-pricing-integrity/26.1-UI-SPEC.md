**Law 02 compliance for every new element in this phase:**
- Refund-review "awaiting admin" state uses `Alert tone="info"` (`--vt-info`, blue-grey oklch), **not** `tone="accent"` and **not** `Badge tone="warning"` — both are tinted-yellow by default and forbidden.
- The vehicle-class "Hidden" state badge uses `Badge tone="inverse"` (charcoal) or a plain `--vt-grey-100` chip with `--vt-text-secondary` text — never a yellow chip.
- Dispute Alert uses `tone="danger"` (full-strength `--vt-danger`, not a tint).
- No coloured glow anywhere in this phase's new controls: every new Dialog/Button/Input inherits `--vt-shadow-accent:none` already set at the page root; no new `:root` block needed since these controls live inside existing `.dc.html`/`layout.tsx` roots that already carry the law.

## Copywriting Contract

Voice: confident, plain, second person for customer-facing copy; neutral and literal for
ops copy (per `design-system/readme.md` §2). Sentence case everywhere except button
labels/kickers/table headers/badges (UPPERCASE, 0.09em tracking). No invented CHF, no
invented legal text — any owner-owed value stays a `data-tok` pill. **No single-word
button label for a financially consequential action** — every accept/decline/reject/
remove/confirm button below names the money or the factor it acts on.

### 1. Pay-link recipient page (`PayClient.tsx`)

| Element | Copy | State | Notes |
|---|---|---|---|
| Locked, 24h window still open, not yet paid | *(existing)* recap shown, Pay button live | normal | no change — current `finishPayment` / `pay-and-continue` copy stands |
| **Already paid by the traveller (D-21)** | Heading: `"Already paid"` · Body: `"No need to pay again — {reference} is confirmed."` | **new state — does not exist today** | The existing `quoteAlreadyBooked` key ("This quote already has a booking.") is generic price-tampering copy, not this state's copy. Add a distinct alert key, e.g. `payLinkAlreadyPaid`, and stop rendering `TokenDummyFields`/`PaymentPanel` — show a confirmed-state card instead (reuse the `Card` + a `check-circle`/`circle-check` `Icon`, tone success, same shape as `BookingVoucher`'s confirmed header) |
| **Expired / cancelled (24h elapsed, D-20)** | Heading: `"This payment link has expired"` · Body: `"It was open for 24 hours and closed automatically. Contact the traveller for a new one."` | *(existing `quoteExpired` key reused, but its copy — "This quote has expired. Get a new price." — is written for the *booker*, not a pay-link recipient who cannot "get a new price" themselves)* | **Open item for the owner**: either add a pay-link-specific expiry key, or confirm the generic `quoteExpired` copy is acceptable for this audience too. Flagged, not decided here. |
| **Race lost — charge already refunded (D-22)** | Heading: `"Payment received twice — refunded"` · Body: `"Your card was charged and automatically refunded because the booking was already paid. No action needed."` | **new state — does not exist today** | Only reachable if the recipient's own charge is the one that loses the race. Needs its own alert key; distinguish from the "already paid" state above (that one never charged the recipient's card, this one did and reversed it) |
| Locked-out generic (network/session error) | *(existing)* `paymentWindowClosed` — "The payment window closed. Get a new quote." | normal | unchanged |

### 3. Post-trip refund (D-25/D-25a) — no new customer UI

Per the signed context (D-25a), the customer never gets a new refund button. They open a
support ticket exactly as today (`/contact`, `info@`). **This phase adds zero customer-facing
UI for post-trip refunds.** The only UI surface is the ops side (§4 below).

### 4. Ops refund review panel (`OpsDetail.dc.html`) — new, build once with every state

Today `OpsDetail.dc.html` only has a binary "Refund" button that always refunds the full
captured amount (`markRefund` → `POST /api/staff/bookings/:id/refund` with `{}`). D-24
needs the admin to set a **percentage**; D-25 needs an explicit **accept/reject** decision
for a post-trip request. Neither exists. Build one new component region inside the
existing money card, reusing the existing `Alert` pattern already proven at lines
271–274 of that file (`tone="danger"` for "Refund due", `tone="success"` for "Refund
issued"). Every button below names the money or the request it acts on — no bare
"Accept"/"Reject"/"Decline"/"Confirm".

| State | Trigger | Visual |
|---|---|---|
| **Refund review needed, <24h cancel (D-24)** | `refund_mode = pending_ops` and booking not yet past pickup | `Alert tone="info"` heading `"Refund review needed"`, body `"Cancelled inside 24 hours of pickup. Set the percentage to refund."` + a percentage `Input` (`type="number"`, `min=0`, `max=100`, size `md`, 44px) defaulting to empty (never pre-filled with 100 — the admin must actively choose) + `Button variant="primary"` `"Confirm refund"` (disabled until a value 0–100 is entered) + `Button variant="secondary"` `"Decline refund"` |
| **Decline-refund confirm (new, financially consequential)** | "Decline refund" clicked | `Dialog size="sm"` title `"Decline this refund?"`, one-sentence body stating the consequence: `"{reference} stays charged in full — the customer gets nothing back."` + `Button variant="secondary"` `"Keep reviewing"` (context-specific dismiss, not "Cancel") + `Button variant="danger"` `"Decline refund"` (repeats the action label, confirms it) |
| **Refund requested after the trip (D-25)** | A post-trip refund request exists (support ticket → admin opens the booking) | `Alert tone="info"` heading `"Refund requested"`, body `"Asked after the trip. Accept or reject the refund."` + `Button variant="primary"` `"Accept refund"` + `Button variant="danger"` `"Reject refund"` — no percentage field for this state per D-25's "accepts or rejects", not "accepts a percentage of" |
| **Reject-refund confirm (new, financially consequential)** | "Reject refund" clicked | `Dialog size="sm"` title `"Reject this refund?"`, one-sentence body: `"The customer is told no money will be returned for {reference}."` + `Button variant="secondary"` `"Keep reviewing"` (context-specific dismiss, not "Cancel") + `Button variant="danger"` `"Reject refund"` |
| **Refund confirmed / issued** | *(existing, reuse verbatim)* | `Alert tone="success"` — unchanged copy pattern |
| **Refund failed** | Stripe refund call errors | `Alert tone="danger"` heading `"Refund failed"`, body states the Stripe error is retryable, `Button variant="secondary"` `"Try again"` — mirror the existing `refundFailed` pattern already in the file's `t.refundFailed` string, just give it a dedicated Alert instead of only a toast |
| **Loading (refund in flight)** | Button clicked, request pending | `Button` `loading` prop (already supported by the kit's `Button`) on "Confirm refund"/"Accept refund"/"Decline refund"/"Reject refund" — disable the sibling action while one is in flight |
| **Dispute (D-07, read-only)** | `charge.dispute.*` row exists for this booking's payment | `Alert tone="danger"` heading `"Payment disputed"`, body: dispute status as received from Stripe (`"Needs response"` / `"Under review"` / `"Won"` / `"Lost"` — neutral, literal, ops-voice) + `"Manage in the Stripe dashboard."` (no in-app accept/respond action — Stripe is the decision surface per research's "don't hand-roll dispute reconciliation") |

Four languages for every new key above (`declineRefundConfirmTitle`, `declineRefundConfirmBody`, `keepReviewing`, `rejectRefundConfirmTitle`, `rejectRefundConfirmBody`, plus the renamed button labels), same pass, in
`OpsDetail.dc.html`'s own `T` object (the file's existing en/de/fr/ar block, same pattern already used for
`refundTitle`/`refundBody`).

### 6. Vehicle class delete vs. hide-with-reason (D-15, `OpsPricing.dc.html` + `OpsTable.dc.html`)

| State | Trigger | Visual |
|---|---|---|
| **Hard delete, unreferenced** | `deleteVehicleClassIfUnreferenced` succeeds | *(existing, reuse verbatim)* the generic `Dialog size="sm"` confirm pattern already in `OpsTable.dc.html` (`confirmTitle`/`confirmBody`/`Button variant="danger"` "Delete") |

### 7. Admin sign-in methods (`OpsSettings.dc.html` — INT-09)

The Security pane already has Email + Password (with the required show/hide eye,
`data-af-eye`/`Icon name="eye"|"eye-off"` pattern — **do not rebuild this, copy it

| Section | State | Visual |
|---|---|---|
