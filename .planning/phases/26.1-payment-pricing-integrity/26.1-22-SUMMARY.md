# Phase 26.1 Plan 22: Admin TOTP, step-up, sign-in method switch and re-auth gate (server) Summary

**TOTP enrol/verify/remove and aal2 step-up on `/api/auth`, a 5-minute HMAC `vt_reauth` cookie bound to the Supabase session that gates password/email change, method switch and factor removal, and a real password-to-magic-link switch that refuses password sign-ins with the generic error.**

## Accomplishments

- `lib/auth/staff-mfa.ts`: `staffMfaAccess` (admin only, D-16/D-16b), `enrolTotp`, `verifyTotpEnrolment`, `challengeTotp`, `verifyTotpChallenge`, `stepUpTotp`, `unenrolFactor` (aal2 + fresh re-auth + own factor), `listFactors` (TOTP + passkey via `passkey.list()` or a verified webauthn factor), `passwordSignInRefused`, `checkCodeAttemptLimit`.
- `lib/auth/reauth.ts`: `mintReauthCookie` / `hasFreshReauth` / `reauthGate` / `clearReauthCookie` (HMAC-SHA256 through `crypto.subtle`, constant-time verify), `recentRecovery`, `sensitiveProfileChange`, plus `verifyOwnPassword`, `sendReauthCode`, `verifyReauthCode` over an isolated client.
- `/api/auth` actions (all behind the existing CSRF check and per-IP `auth` write limit; code and password checks also take a per-account `auth-code:<sub>` limit that fails closed):
  - `mfa-status` returns `{ ok, totp, totpFactorId, passkey, signInMethod }`.
  - `mfa-totp-enroll` returns `{ ok, factorId, qrSvg, secret }`. It clears stale unverified TOTP factors and refuses a second verified one.
  - `mfa-totp-verify` and `mfa-step-up` copy the refreshed aal2 cookies onto the response. A wrong code returns `mfa-code-mismatch`.
  - `mfa-unenroll` answers 403 without aal2 or without a fresh re-auth.
  - `reauth-password`, `reauth-code-send` / `reauth-code-verify` (6-digit e-mail code), and `reauth-totp` set `vt_reauth` (HttpOnly, Secure, SameSite=Strict, Max-Age 300, Path /).
  - `set-sign-in-method` needs a fresh re-auth, then calls `staff_set_sign_in_method`.
  - `signout` also clears `vt_reauth`.
- Password sign-in: a staff account stored as `magic_link` is signed out and gets `FORM_CREDENTIALS`. Only the sign-out's cookie removals are returned, never the refused session. With a factor enrolled, the row is hidden at aal1, so `mfa-step-up` runs the same check at aal2 using the session AMR.
- Profile PATCH checks `hasFreshReauth` before any write when the password or email changes (403 `reauth-required` or `reauth-unavailable`). `changeOwnPassword` and `changeOwnEmail` enforce the same gate themselves, so the Server Actions cannot bypass the route.
