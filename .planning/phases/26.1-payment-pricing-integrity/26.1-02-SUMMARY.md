# Phase 26.1 Plan 02: Settlement revive, PI write-back, duplicate detection Summary

**Rewrote `checkout_payment_settle` (same 9-argument signature, 8 new return columns) so a successful late Stripe charge always revives a cancelled or lock-expired booking to confirmed — except when the cancel was a requote, which is refunded instead because a successor booking already exists — writes the real `pi_` id back over a stored `cs_` session id, and turns a second successful charge on an already-paid snapshot into a flagged `duplicate` row instead of a `23505` crash; proven by 85 new pgTAP assertions plus one corrected pre-existing assertion, 1196/1196 pgTAP total.**

## Accomplishments
- `checkout_payment_settle` v2 revives to `confirmed` on any cancel path (account cancel, cron expire, customer abandon, staff/ops cancel — D-03/D-03a), clearing `refund_status`/`refund_owed_rappen` and any `coupon_redemptions.released_at` on the booking
- A requote-cancelled booking is never revived — its payment settles `succeeded` with `refund_required=true, refund_reason='requote_superseded'` (D-03b), because the requote already produced a separate successor booking and reviving the old one would double-book
- A booking whose pickup has already passed also stays cancelled and gets `refund_reason='paid_after_cancel'` (D-03 exception)
- `is_test` bookings capture money without any status change, `refund_reason='test_booking'`
- The stored `cs_...` session id on `booking_payments.stripe_payment_intent_id` is corrected to the real `pi_...` id in the same UPDATE that settles the row (D-05) — `tg_payment_update_whitelist` now allows exactly that one transition on a non-succeeded row and nothing else (verified: a `pi_...` value can never be changed to anything, and a succeeded row stays fully terminal)
- A second successful charge on a snapshot that already has one lands as `booking_payments.status = 'duplicate'`, `already_settled=true` (so the live Worker's existing check never double-confirms), `refund_required=true, refund_reason='duplicate_charge'` — proven with no `23505` raised
- Every succeeded settle returns `other_open_session_ids` (the booking's other `requires_payment` Checkout Session ids) so a consumer can expire them (D-21/D-22)
- New `checkout_duplicate_refund_record`: idempotent on `stripe_refund_id`, records the refund for any of the four new reasons; `duplicate_charge` leaves `bookings.refund_status`/`refunded_rappen` untouched (the booking's own ledger is unaffected by a stray second charge), the other three reasons set them
- `packages/db/supabase/tests/settle_revive.test.sql`: 85 pgTAP assertions, all green, covering every behaviour bullet in the plan
- Full suite: `pnpm db:reset && pnpm db:test` → 1196/1196 pgTAP pass (55 files); `pnpm db:types:check`, `pnpm db:seed:check`, `pnpm check:db-fences`, `pnpm check:numbers`, `pnpm db:mutation-gate` all exit 0

## Decisions Made
- Read `booking_events.payload->>'via'` on the most recent `booking.status_changed` row to `cancelled`, rather than adding a schema column, to distinguish the one non-revivable cancel path (`requote_cancel`) from every other one — matches the interfaces section's own instruction to read the abandon/requote migrations' exact `via` strings before writing the migration
- `checkout_capture_gate` stays in the schema, unused by this migration's own code, because the live Worker still calls it; 26.1-05 is the plan that stops calling it
- `other_open_session_ids` is computed once, before the settling row's own status changes, and reused across every succeeded-outcome return path (revive, duplicate, is_test, requote, paid_after_cancel, and the ordinary pending→confirmed path) rather than recomputed per-branch — simpler and matches the plan's "(4b) every succeeded branch" instruction literally

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `settlement_rpcs.test.sql` asserted the exact 23505 this plan removes**
- **Found during:** Task 2, `pnpm db:test` full-suite run after the migration landed
- **Issue:** `settlement_rpcs.test.sql` line ~617 (`throws_ok(..., '23505', ...)`) asserted that a second succeeded charge on the same snapshot raises a unique-index violation — the exact behaviour D-22 (this plan) replaces with the `duplicate` branch. Once `checkout_payment_settle` v2 landed, that assertion correctly failed ("caught: no exception, wanted: 23505"), because the new code intentionally never reaches that INSERT/UPDATE path anymore.
- **Fix:** Replaced the `throws_ok` with a `lives_ok` plus an `is()` asserting the row lands as `status = 'duplicate'`, matching the new documented contract. This is not a loosened test — it now asserts the correct, intentionally-changed behavior instead of the bug this plan exists to fix.
- **Files modified:** `packages/db/supabase/tests/settlement_rpcs.test.sql` (plan count 93 → 94)
- **Commit:** `f00374a3`

**2. [Rule 3 - Blocking] `settle_revive.test.sql` fixture bugs found while turning RED into GREEN**
- **Found during:** Task 2, iterating the new test file to green
- **Issues fixed:** wrong join column (`o.id` instead of `o.booking_id` against the `checkout_create_booking`-shaped temp tables); missing `stripe_events` rows for every event id the file settles (the function only stamps `processed_at` on an existing row, it does not insert one); `grant select ... to public` issued after `reset role` instead of before (the temp table's owner at that point was the login role, not `vamos_checkout`, so the grant silently no-op'd with a WARNING); a fake `actor_id` UUID passed to `ops_cancel_booking` that failed `booking_events`'s `actor_id` FK to `auth.users` (fixed to `null::uuid`, which the function already tolerates); two `checkout_abandon_unpaid`/`checkout_requote_cancel` calls joined `public.bookings` directly under the `vamos_checkout` role, which has no table grant on `bookings` (fixed by passing the already-known literal `quote_id` instead of looking it up via a join)
