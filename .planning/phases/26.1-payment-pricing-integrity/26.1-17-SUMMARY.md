# Phase 26.1 Plan 17: Refund review tiers and admin refund decisions Summary

SQL now follows D-23/D-24/D-25. A paid booking is refunded in full automatically only when it is cancelled more than 24 h before pickup. Every other paid cancel (inside 24 h, inside 6 h, after pickup) becomes `pending_ops`, and the admin picks a percentage or declines. After the trip, the admin accepts (`post_trip`) or rejects. Refunds can only be decided through the admin API.

## What changed

- **`compute_cancellation_refund` v2** (same signature):
  - More than 24 h before pickup: `auto_full`, 100 % of captured.
  - Otherwise, if anything was captured: `pending_ops`, with `refund_rappen` and `refund_percent` both null.
  - Nothing captured: `none`.
  - `apply_customer_cancel` and `ops_cancel_booking` were not touched. They already map `pending_ops` to `refund_status = 'pending_ops'`, and the owed amount is now null until the admin decides.
- **Schema (additive):**
  - `refund_status` can now be `declined`.
  - `booking_refunds.reason` can now be `post_trip`, and `stripe_dashboard` is kept.
  - New `booking_events` kinds: `refund.declined` and `refund.rejected`.
- **`ops_refund_record`:**
  - The old function was dropped and recreated with two new trailing parameters, `p_reason` and `p_refund_rappen`. Both default to null, so the live Worker's 5-argument call still resolves.
  - It validates the reason and the amount (`invalid-reason`, `invalid-amount`, `refund-exceeds-remaining`).
  - The event payload now carries the reason and the percentage.
- **`ops_refund_decide`:**
  - SECURITY DEFINER with `search_path=''`. It refuses anyone who is not an admin (`app.is_admin()`) with 42501.
  - `decline` needs `pending_ops`. `reject` needs a completed, partially completed or no-show booking with a capture and `refund_status none`.
  - It sets `declined` and owed 0, and writes the event with the admin as actor.
  - EXECUTE is granted to `vamos_staff` only. `authenticated` has no grant, so there is still no customer refund button (D-25a).
- **API:**
  - The refund route now uses `withAdmin`, and `parseRefundBody` validates the body (integer percent 0–100, otherwise `invalid-percent` 400).
  - `refundBooking` sends every admin refund through Stripe (PaymentIntent resolved first, D-05) and then `ops_refund_record`, passing the reason and the decided amount.
  - The old partial branch, which used the customer path `applyStripeRefund` → `record_booking_refund` and had no `decided_by`, has been removed.
  - Before Stripe is called, `refundBooking` checks that the booking is post-trip (for `postTrip`) and that the amount fits the payment's remaining capture.
  - New `refund-decision` route (dual-mounted) → `decideRefund` → `ops_refund_decide`, run as the staff identity so the SQL's own admin check applies.
  - A dispatcher gets 403 `not-admin` from both routes.

## Deviations from Plan

**1. [Rule 1 - Bug] `ops_refund_record` also takes `p_refund_rappen`.** The plan added only `p_reason`. The old body always recorded the full remaining amount, so a 40 % Stripe refund would have been written as 100 %. The new parameter is trailing and defaulted. (1c96df03)

**2. [Rule 1 - Bug] Nothing captured means `none` in every window.** Without this, an unpaid booking cancelled inside 24 h would land in the admin's review queue with nothing to refund. It also keeps `manage_booking_mutation (6b-1)` and `booking_status_rollup` passing unchanged: both use unpaid after-pickup bookings and still expect `none`. The mode is set with a single `case` expression, so the acceptance grep for `v_mode := 'none'` returns 0. There is no time-based no-refund zone left. (1c96df03)

**3. [Rule 2 - Missing critical] Validation before Stripe.** `refundBooking` checks the per-payment cap and the post-trip status before `createRefund`, so money never leaves Stripe without a row that can record it. (4e04751f)

**4. [Rule 3 - Blocking] `booking_events_kind_check` extended** with `refund.declined` and `refund.rejected`. Without it the decision events could not be inserted.
