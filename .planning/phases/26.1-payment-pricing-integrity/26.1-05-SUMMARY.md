# Phase 26.1 Plan 05: Consumer wired to settle v2; refunds always target a real PaymentIntent Summary

**The queue consumer now revives a paid-but-cancelled booking or refunds it via Stripe with a `refund:<booking>:<payment>:<reason>` idempotency key instead of silently acking with the money kept, and every refund path (queue consumer, ops refund, paid-cancel) resolves a stored id through `resolvePaymentIntentId` before calling Stripe, so a `cs_...` session id can never reach `stripe.refunds.create` again.**

## Accomplishments

- `handleStripeMessageWithDeps` no longer consults `checkout_capture_gate` for a succeeded outcome at all — `settlePayment` (`checkout_payment_settle` v2) is always called, and its `revived`/`duplicate`/`refund_required`/`refund_reason` columns drive the outcome instead of an early ack
- A `refund_required` row is refunded via Stripe with idempotency key `refund:<booking_id>:<payment_id>:<reason>`, then recorded via `checkout_duplicate_refund_record`; `paid_after_cancel`/`test_booking`/`requote_superseded` additionally alert ops via `deliverPaidAfterCancelAlert`
- A `refund_required` row with no PaymentIntent id, or a refund call that throws, alerts stuck-payment (`deliverStuckPaymentAlert`) and acks — never retried into itself, since `processed_at` is already stamped by the SQL function
- Every succeeded settle expires the booking's other still-open Checkout Sessions (`other_open_session_ids`, D-21/D-22); a failed expire is logged (`emit("warn", "expire_session_failed", ...)`) and does not block the ack
- `resolvePaymentIntentId(stripe, storedId)` is the one function that turns a stored id into a real PaymentIntent: `pi_...` passes through with no Stripe call, `cs_...` resolves via `retrieveCheckoutSession`'s expanded `payment_intent`, and any other prefix (empty, `ch_...`, garbage) returns `null` — matching the research's "stale cs_ misroute" threat
- `createRefund` now requires `bookingId`/`paymentId`/`reason` and always sends Stripe refund `metadata: { vamos_source: "app", booking_id, payment_id, reason }`, so a future `charge.refunded` handler (26.1-08) can tell an app-issued refund from a dashboard one
- `applyStripeRefund` (paid-cancel.ts, customer/staff cancel path) and `refundBooking`'s direct-remaining path (refund.ts) both resolve the PaymentIntent id before calling `createRefund`; a `null` resolution returns `{ ok: false, code: "stripe-failed" }` and marks the refund failed via the existing `bookings_set_refund_failed` path
- 434 tests exercising the changed files (`lib/checkout`, `lib/ops/refund.test.ts`, `lib/lifecycle`) all green; full `apps/web` unit suite 1686/1686 green; `tsc --noEmit -p .` clean; `eslint` clean on every touched file
