# Phase 26.1 Plan 04: Owner pricing formula in the kernel Summary

**Pricing kernel now computes start + per-km with an additive airport fee and bidirectional city/canton pairs (D-08/D-08a/D-08b/D-09/D-09a), replacing the old airport-start swap, one-directional pair matching, and city_price_rappen dropdown filter.**

- **Tasks:** 3
- **Files modified:** 11

## Accomplishments

- `buildFareLine` always uses `base_fare_rappen` as the start and never adds distance-band extras to the amount (D-08) — `fare_kind` no longer branches the formula.
- New `buildAirportFeeLine`/`airportFeeApplies` add the airport pickup fee on top of the fare line when the pickup is an airport (`origin_is_airport` or an airport-typed zone) or a flight number was entered (D-08b); a trigger with a null `airport_start_rappen` still emits the line with a null amount so the class becomes unpriced rather than silently free (D-13).
- `matchCityPair`/`matchCantonPair` now match both directions, refuse a pair when pickup and destination resolve to the same place/canton (D-09), and prefer 26.1-09's future Mapbox `mapbox_place:<id>` zone tag over the label-substring fallback. `buildFixedRouteExtraLine` picks the city pair over a canton pair on the same leg (D-09a), reversing the old canton-wins precedence.
- `priceQuote.ts` removes the `distance_rates.city_price_rappen` dropdown filter and the `city_to_city`-only restriction — a published pair now applies whenever it matches, regardless of `fare_kind`.
- The owner's Mapbox-verified worked example (ZRH Airport → Swiss National Museum, 10.19 km: 2000 start + 3000 airport fee + 2548 per-km = 7548 rappen net, 10% coupon = −755, never negative) is a passing test in `lines.test.ts`.
- `price.line.airport_fee` ships in en/de/fr/ar; the ops Distance rules tab relabels the airport field as "Airport pickup fee (added to start)" (four languages) and drops the dead city-price picker column/field (the DB column and save API are left untouched so existing drafts still load).

## Decisions Made

- Kept `fare_kind` on the type surfaces (still consumed by 26.1-09/26.1-11/checkout callers out of this plan's scope) but stopped the kernel from reading it for pricing — a client-sent value is not a pricing trust boundary; server-resolved airport/place fields are.
- Left `buildCityPriceLine` exported and tested (it was already unused by `priceQuote.ts` before this plan) rather than deleting it, since removing the `distance_rates.city_price_rappen` column path end-to-end is 26.1-09/26.1-10/26.1-11 territory per the plan's stated boundary.
- `priceQuote.test.ts`'s `pricedBook()` fixture needed `airport_start_rappen` added to every class so the new additive airport-fee line didn't null out totals in tests that were never about airports — this is a test-fixture fix (Rule 1), not a kernel change.

Reworded the comment to convey the same fact without those literal tokens.
- Several pre-existing `priceQuote.test.ts` fixtures default their legs to zone `z-a`, which is zone-typed `airport` in that file. Once `buildAirportFeeLine` is wired in unconditionally, every test using that default incidentally exercises the airport-fee path. Verified case by case that none of the affected tests hardcode a total that the new line would change (`return + coupon reconstruction`, `determinism`, `launch state` all either don't hardcode totals or are fully null already); added `airport_start_rappen` to `pricedBook()` so the one test that does check `total_rappen is not null` keeps passing with a real (not hardcoded) total.
