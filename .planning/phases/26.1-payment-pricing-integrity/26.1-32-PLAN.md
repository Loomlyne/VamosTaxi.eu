<objective>
Close VERIFICATION.md gap 1 (BLOCKER): "Coupon cap can be skipped at payment." Success criterion 3, requirement INT-04, decision D-11.

`runCheckoutIntent` (`apps/web/lib/checkout/intent.ts`) currently derives the coupon to re-evaluate at payment from `body.coupon` only. The signed lock's class total (`payload.class_totals`, read via the `reprice` board) is already post-coupon from quote time — `payload.coupon` carries which coupon that is. A request that sends `coupon: null` while replaying a lock signed with a coupon is charged the discounted total, `evaluate_coupon` is never called, no `coupon_redemptions` row is written, and the per-user/global cap is never checked. `/api/checkout/pay-link/route.ts` shares `runCheckoutIntent`, so it inherits the same exposure for booking creation, plus its own smaller display-only exposure (the confirmation email's coupon label reads `body.coupon` instead of the lock's coupon).

Task 1 closes the server-side gap. Task 2 closes what Task 1's stricter refusal exposes on the client: today, when the intent route refuses `coupon_no_longer_valid`, `CheckoutClient.tsx` clears `couponApplied` but keeps posting the same coupon-priced lock — every retry is refused the same way, up to exhaustion, and the payer is stuck. Task 2 makes the client recover automatically via a bounded `couponRefusalAction` decision (reprice with the coupon cleared when the lock priced one, or simply drop a stale applied-coupon state when it did not — never more than once per lock) on that refusal, from both the intent and pay-link routes, and restores `couponApplied` from the lock after a page reload, so the phase is never in a state where the server correctly refuses but the client cannot recover, and never loops.

Purpose: D-11 ("Coupon caps are enforced at payment") must hold for every request shape, not only the one the legitimate client happens to send — and the legitimate client must still be able to complete a booking once that coupon is gone.
Output: the coupon actually charged is always the coupon the verified lock priced, always re-evaluated with the payer's identity, with a closed refusal ladder when body and lock disagree, and a client that recovers from that refusal instead of looping.

Out of scope: if a coupon's discount *percent* changes between quote-time (lock mint) and payment, `preCouponRappen`/`chargedRappen` (`intent.ts:349-352`) gross up using the freshly evaluated percent against `netRappen`, which itself reflects whatever percent was live when the lock's board was priced. Whether that reconciles correctly under a percent change is unverified and not part of this gap — this plan closes coupon-*code* identity (which coupon, if any, is charged), not coupon-*percent*-value staleness.

Known edge case, not fixed here (Info 1): the lock pins `payload.coupon` even when that coupon was never actually applied to pricing (`pipeline.ts:1021`; flight reprice `1082-1092`), so the mount-time reload-restore effect (Task 2, I1) may show an unapplied code as applied. The payment-time recovery corrects this the moment the payer reaches payment — that case reaches `couponRefusalAction` with `lockCoupon` null and `bodyCoupon` non-null and resolves to `"drop_body_coupon"`. The reload display itself is not fixed by this plan.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → /api/checkout/intent, /api/checkout/pay-link | Untrusted `coupon` field in the request body, independent of the HMAC-verified lock it accompanies |
| Browser (client-side peek) → the lock it already holds | `peekLockCoupon` reads `payload.coupon` without verifying the HMAC; the value is used for display, for the reload-restore effect, and to seed `couponRefusalAction`'s `lockCoupon` input for request bodies — it cannot change what is charged, because the server always re-derives its own `lockCoupon` from the HMAC-verified `payload.coupon` and refuses any mismatch between that and `body.coupon` |
