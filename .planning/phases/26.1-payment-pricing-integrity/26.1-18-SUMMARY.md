# Phase 26.1 Plan 18: Refund review UI Summary

Admins now handle every refund state from one panel in the ops booking detail. A cancel inside 24 h shows an empty 0–100 percentage field with Confirm or Decline. A post-trip request has Accept or Reject, and both negative actions ask for confirmation first. Disputes and Stripe failures appear as danger Alerts. Only admins see these controls. On the customer side, "Pending Ops" is gone: the voucher says "Refund under review" or "No refund" and shows the amount. Both customer cancel screens now follow D-24 (more than 24 h before pickup: automatic full refund; later: review).

## What changed

- **Read model** (`bookings.ts`, `bookings-map.ts`):
  - Adds `refundStatus`, `refundOwedRappen` (null until decided), `capturedRappen` (every captured charge) and `tripPassed`. `tripPassed` means the earliest leg's `original_scheduled_at <= now()` in SQL, so the Worker clock never decides it.
  - Adds `dispute`, taken from the latest `booking_disputes` row by `stripe_created`. It carries the status and reason code only, never evidence text (T-26.1-59).
  - `vamos-ops-data.js` `cleanBooking` passes these fields through to the DC (Rule 3: without this the DC would never see them).
- **OpsDetail.dc.html:**
  - **Admin check.** `isAdmin = role === 'admin'` comes from `VamosOps.profile` (`/api/staff/me`), and the page re-renders when the profile changes. Dispatchers see no Refund, Confirm, Decline, Accept or Reject controls (D-16b).
  - **Review needed.** When `pending_ops` and paid: an info Alert "Refund review needed", a `Input type=number min=0 max=100 size=md` that starts empty, "Confirm refund" (disabled until the value is an integer 0–100) and "Decline refund".
  - **Refund requested.** When `tripPassed && paid && refundStatus none` and the status is completed, partially_completed or no_show, the Refund button opens an info Alert "Refund requested" with "Accept refund" (`{postTrip:true}`) and "Reject refund".
  - **Dialogs.** Decline and reject each open a `Dialog size="sm"`. The body puts the reference in a `vt-dir-keep` span. "Keep reviewing" is `autoFocus`, and the danger button repeats the action. Decisions POST `/refund-decision {decision}`.
  - **Dispute.** A danger Alert "Payment disputed" shows the status word (Needs response / Under review / Won / Lost; any other Stripe status appears as its raw code) and "Manage in the Stripe dashboard."
  - **Refund failed.** A danger Alert with "Try again". It retries the last body, or `{rappen: refundOwedRappen}` when `refund_status` is `failed`.
  - **Loading.** The kit `Button` has no `loading` prop. While a request is in flight, every refund action is disabled and the acting button carries `aria-busy="true"`.
  - **Layout and laws.**
    - Added `.vt-input--focus{box-shadow:none}` (the page had no Input before).
    - Layout uses `[data-ops-refund-*]` flex-wrap rows with 44 px controls, so they wrap at 390 px.
    - Only logical properties are used, and there are no new colours, radii or shadows.
  - **Copy.** All 23 keys are in the en, de, fr and ar `T` blocks. German uses "ss".
- **Customer side:**
  - `refundPendingOps` now reads "Refund under review" / "Rückerstattung in Prüfung" / "Remboursement en cours d’examen" / "الاسترداد قيد المراجعة".
  - New `checkout.refundDeclinedLabel`: "No refund" / "Keine Rückerstattung" / "Aucun remboursement" / "لا يوجد استرداد".
  - The voucher refund row reads "{status} · {formatAmount(amount)}", followed by the existing payout sentence when refunded.
  - The amount comes from `voucherRefundAmountRappen`: the decided amount while pending or processing, the refunded amount once refunded, and nothing for declined, failed or none.
- **Deferred items from 26.1-17:**
  - `manage/booking/route.ts` `cancelWindow` and `ConfirmationClient` `cancelWindowOf` are replaced by `customerCancelWindow`. The 6 h "none" zone is gone, and a customer inside 6 h can confirm the cancel.
  - The sheet uses the existing, already-approved `cancelSheetOps` copy ("This trip will be cancelled. Refund needs a person — we will email you."). No new sentence was written.
  - ConfirmationClient keeps `refundRappen` from the cancel response and passes it to the voucher.

## Deviations from Plan

**1. [Rule 3 - Blocking] `app/vamos-ops-data.js` passes the new fields through.** `cleanBooking` whitelists fields, so without this change the DC could not see refund or dispute facts. (0d92f26f)

**2. [Rule 2 - Missing critical] Refund controls are hidden for non-admin staff (D-16b).** This was deferred from 26.1-17. The API already returns 403 to dispatchers. The plain Refund button is also hidden while a booking is `pending_ops` or `declined`, so it cannot bypass the review. (0d92f26f)

**3. [Rule 1 - Bug] Customer cancel tiers now match D-24.** This was deferred from 26.1-17. Both helpers still showed "too close, no refund" inside 6 h, while SQL now sends those cancels to admin review. (d18db88f)

**4. No `refundAmountLabel` key.** `checkout.refund` already reads "Refund" in all four languages and labels the refund row, so a second "Refund" row would duplicate it. The amount sits in that row instead. The plan's behaviour still holds: a `credit-card` ReceiptRow shows the amount through `formatAmount`.

**5. Percentage 0 routes to the Decline dialog** instead of sending `{percent:0}`, which 26.1-17 answers with 400 zero-amount.

**6. Confirm-dialog key names** follow the plan (`declineConfirmTitle`, …) rather than the UI-SPEC examples (`declineRefundConfirmTitle`, …).
