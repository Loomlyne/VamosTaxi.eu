Finish the Worker's operational surface: every binding Phases 3-7 will reach for exists and is
declared, the two non-fetch handlers are proven to actually fire in staging, staging is gated and
unindexed, and structured logs are flowing before anything exists worth debugging.

Purpose: D-34's point is that Phases 3-7 add code, not infrastructure, and that there is one place
to see the Worker's full surface. D-38's point is that when a booking fails in Phase 7 the trail is
already there rather than added after the incident. Both are cheap now and expensive later.

Output: a staging Worker behind Access, unindexed, emitting structured logs, with a cron trigger
and a queue consumer that have each been observed to fire.
</objective>

    reaching staging at all, and the robots header stops a crawler that somehow does from competing
    with the live site's rankings. D-37 wants both, and from Phase 7 there is a real payment form
    behind this hostname.

    Enable Cloudflare Access directly on the Worker rather than as a self-hosted application bound
    to a hostname. RESEARCH's State of the Art table records this as newly supported (Cloudflare
    changelog, 2026-08-14) and simpler, and its Assumptions Log rates A3 medium confidence because
    it was read in docs, not tested against a live account. So verify it empirically here: if
    Worker-level Access does not gate the custom hostname as documented, fall back to the older
    self-hosted-application pattern and record which one was used in the resources document. Do not
    leave staging ungated because the newer mechanism disappointed.

    applied to production. Write that consequence into the resources document now so Phase 5/7
