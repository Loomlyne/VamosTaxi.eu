<objective>
Migrate the platform's whole dictionary — 1,428 English source strings and 44 concatenation
patterns across four languages — from the mocks' English-string-keyed table into per-locale JSON
with dotted keys and ICU messages, collapsing the duplicates and marking the product names on the
way through.

Purpose: D-13 makes this a one-time move, and D-18 is explicit that the duplicate collapse and the
non-translatable marking happen *during* it — the one moment the file is being rewritten anyway.
The parameterised-message conversion is what makes ADR-001's third point real: the class of bug
where a string stays English because it contains a number stops being possible rather than being
caught after the fact.

Output: four locale files the coverage gate passes over, and a source-string-to-key map Phase 5
uses to port each mock's copy without guessing.
</objective>

    Write the transform as a re-runnable script rather than editing 1,428 entries by hand, then run
    it and review its output. A script makes the scheme auditable and lets a mistake be fixed by
    re-running instead of by 1,428 corrections.

    Key scheme, which is the only genuinely non-mechanical decision here. Each key is
    `<namespace>.<leaf>`. The namespace comes from where the string is actually used: grep the mock
    tree for each English source string and take the owning surface's name as the namespace
    (`header`, `footer`, `booking`, `checkout`, `account`, `ops`, `legal`, and so on), falling back
    to `common` for a string used by three or more surfaces. The leaf is a slug of the English
    source, truncated at a sensible length and disambiguated with a numeric suffix only where two
    different strings on the same surface would otherwise collide. Print every collision and every
    `common` fallback so the reviewer sees where the scheme had to guess.

    Emit two files. `messages/en.json` is the key authority, nested by namespace. `key-map.json`
    maps each original English source string to its dotted key — this is what Phase 5 uses when it
    ports a mock's copy, so that porting a page is a lookup rather than a re-derivation, and it is
    also how a reviewer checks the migration lost nothing.

    Handle the three special classes explicitly rather than letting them fall through the generic
    path:
    - Strings the duplicates ADR records as duplicates collapse to one key. The script reads the
      duplicate list from the ADR rather than hardcoding it, so the two cannot drift.
    - The four product names get a marker in the message file identifying them as non-translatable,
      and the coverage gate from Plan 03 already knows to read that marker rather than a hardcoded
      list.
    - Copy that appears inside a pending-value pill stays English in every locale, per the pill-copy
      ADR, and is marked so the coverage gate does not report it as a gap.

    Read the mock dictionary; never write to it. The mocks remain the visual source of truth for
    every later phase (D-03).

  <action>
    Emit the three translated files from the same mapping, and convert the concatenation patterns.

    Locale files. For each source entry the script already resolved to a dotted key, write the
    German, French and Arabic values from the source dictionary into the matching key. Where the
    source leaves a translation genuinely absent, report it rather than filling it with the English
    string — an English value silently sitting in the German file is exactly the failure the
    coverage gate exists to catch, and quietly satisfying the gate would defeat it. Print the list;
    the summary carries it.

    Patterns. The source's 44 regex entries exist to catch strings the code built from parts — a
    review count, a question count, a child-seat multiplier. Each becomes a parameterised message
    with a named placeholder, and anything countable becomes an ICU plural so the form is correct at
    zero, one and many in each language rather than pluralised by an English rule. This is the
    mechanical heart of I18N-06: after this conversion there is no post-render string matching left
    to maintain, and a number in a string can no longer be a reason it stayed English.

    Pluralisation is not uniform across these four languages, and Arabic in particular distinguishes
    more categories than English does. Use the ICU categories each language actually needs rather
    than mirroring the English one-and-other shape into all four; where the source dictionary's
    translation only covers one form, that is a reported gap like any other.

    Direction-sensitive content: any message whose text carries a reference, a time, a flight number
    or a currency figure must keep that fragment left-to-right inside Arabic. The design system
    already has the marker class for this; the message file carries the markup fragment so the
    behaviour travels with the string rather than depending on every call site remembering.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| message file content → rendered HTML | Message values become page content; a message carrying markup is interpolated into the DOM |
| locale segment → message file selection | Already validated in Plan 01; restated here because this plan adds the fallback path |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-02 | Tampering | message file selection | high | mitigate | The fallback path resolves only against the fixed four-locale set already validated in the loader seam; a missing key falls back to English, never to a caller-supplied locale name |
| T-01-21 | Tampering | markup fragments inside messages | medium | mitigate | Messages carrying a direction-keeping fragment use the library's rich-text mechanism with a fixed tag allowlist, never raw HTML interpolation, so a message value cannot inject arbitrary markup |
| T-01-10 | Information Disclosure | raw key path rendered to a visitor | low | mitigate | Upgraded from accept to mitigate by this plan: production renders empty rather than the key path, so internal namespace structure is never exposed |
</threat_model>
