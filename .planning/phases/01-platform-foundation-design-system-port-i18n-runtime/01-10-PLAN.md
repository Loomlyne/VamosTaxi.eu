<objective>
Port the three navigation components and the five feedback components, and automate the three
behaviours a screenshot diff physically cannot see: that focus stays inside an open dialog, that
scrolling stops and restarts around it, and that a toast is announced.

Purpose: UI-SPEC is explicit that Phase 1 automates the feedback set's focus and scroll behaviour
rather than deferring it, because deferring would let a silent regression sit in the foundation
every later phase composes on. The navigation trio matters for a different reason: it carries the
product's directional affordances, and progression that points the wrong way in Arabic is a defect
that only a human or a deliberate assertion will catch.

Output: eight components, two gallery sections, and a behaviour spec that fails a pull request when
a dialog leaks focus or leaves the page unscrollable.
</objective>

    Same recipe as the previous batches: extract the CSS literal into a sibling stylesheet, import it
    statically, drop the injection call, derive the interface from the source signature, convert
    physical inline-direction properties to logical ones and change nothing else.

    `Tabs` carries hover, focus, selected, and a per-tab disabled state — disabled applies to one
    tab, never to the whole control. Two layout rules come out of the four-language contract and
    must survive the port: each tab's width is intrinsic to its content so a longer translation
    widens the tab rather than truncating it, and if the row would overflow its container the row
    scrolls horizontally rather than wrapping to a second line. That horizontal-scroll region owns
    its own scrolling and is marked so the smooth-scroll instance skips it.

    `StepIndicator` carries a selected state meaning the current step, per-step completed and
    upcoming variants, and an error state for an invalid step. Its progression chevrons mirror under
    right-to-left, because forward motion points with the reading direction.

    `SectionHeader` is a typographic composition with an optional action-link slot; the slot inherits
    the button or link states rather than owning any of its own. Do not give it states it does not
    have.

    Component-owned copy — a tab's assistive-technology label, a step's "completed" announcement —
    resolves through the dictionary, never as an English literal.
  </action>

    Tone. `Alert` and `Toast` are tone-as-variant. The source declares an accent tone whose fill comes
    from the design system's pale-yellow scale, and CLAUDE.md bans that surface outright — it names
    this exact component's accent tone as one of the kit defaults that must not ship. **Decision: the
    accent tone is dropped from both tone unions and its rules are not carried into the extracted
    CSS**, matching the call Plan 06 made for the card's equivalent tone. The remaining tones —
    informational, success, danger, and the inverse charcoal treatment — carry every attention state
    this product needs. Record the removal in the summary.

    `ProgressIndicator` is the loading primitive. This is the component a busy button composes with
    rather than growing a loading prop of its own, so it must be able to render inline at label
    scale as well as at block scale. It also carries an error state for a failed step.

    `Dialog` is the one component in the phase with real behaviour beyond rendering. Port, in order:
    a focus trap that keeps keyboard focus inside the open dialog; focus restoration to the element
    that opened it when it closes; a body scroll lock while open, released on close — the same
    document-overflow lock the smooth-scroll provider from Plan 08 already observes and stops on, so
    the two mechanisms meet rather than fighting; and a body region that scrolls inside itself,
    marked as owning its own scroll. Its content may itself be loading, in which case it composes
    the progress indicator rather than owning a loading state.

    `Toast` renders inside a live region so assistive technology announces it, and carries enter and
    exit motion only — no interaction states. One toast renders at a time; the mocks never stack
    them, so no queue behaviour is invented here.

    `Tooltip` becomes visible on hover or focus; that visibility is not a separate interaction state
    in the matrix and should not be modelled as one.

    Motion values come from the source: press, hover, toast and sheet timings are already tokenised.
    Every keyframe-driven entrance gets its reduced-motion companion rule, as every mock already
    does. Nothing scales, nothing springs, nothing loops.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| open dialog → the page behind it | A leaking focus trap lets keyboard interaction reach content the dialog is meant to block |
| caller-supplied alert/toast body → rendered DOM | Message text becomes page content, and from Phase 5 some of it originates server-side |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-27 | Elevation of Privilege | dialog focus trap | medium | mitigate | Focus containment and restoration are asserted by the behaviour spec; a dialog that leaks focus lets a keyboard user act on the surface it was blocking, which matters from Phase 9's cancellation confirmation onward |
| T-01-23 | Denial of Service | body lock never released | medium | mitigate | The lock-and-restore cycle is asserted from both the dialog's side and the scroll provider's side, so a permanently unscrollable page fails the pull request |
| T-01-24 | Tampering | caller-supplied alert and toast bodies | medium | mitigate | Body copy renders as text nodes, never as raw markup, so a message sourced from a future server response cannot inject elements |
| T-01-17 | Tampering | ported CSS carrying a banned surface | medium | mitigate | The accent tone is dropped from both tone unions rather than neutralised at runtime; every feedback file is asserted free of the banned yellow steps |
</threat_model>
