<objective>
Build the page the customer lands on after paying — and make it structurally incapable of being the
thing that confirms their booking.

Purpose: this is where the anti-pattern would be easiest to commit. The browser comes back from
Stripe with a session id in hand, the temptation is to read it and mark the booking paid, and the
result is a system that confirms bookings for customers who abandoned mid-3DS and fails to confirm
for the TWINT customers who never came back at all. The page instead renders a processing state and
waits for the webhook that plan 07-07 owns. PAY-07's five facts appear when — and only when — that
webhook has landed.

Output: one SSR page, one client component that polls with a real backoff and a real give-up, one
narrow status endpoint, one shared guest-scoped read, and the Playwright spec the research's Wave 0
gap list names.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser cookie → `asGuest` | A bearer credential decides which booking is readable |
| `/confirmation/[ref]` URL → the world | The reference is in the address bar, the history, and any Referer |
| poll → `/api/checkout/status/[ref]` | An unauthenticated-looking GET repeated many times |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-45 | Information Disclosure | Someone else's booking rendered by guessing or enumerating a `VT-YY-####` reference | mitigate | The RLS policy `bookings_select_by_manage_token` is the gate, not the URL; an unset GUC makes the policy false and returns zero rows. The query also matches the reference to the token's booking, so a mismatched pair renders nothing |
| T-07-46 | Spoofing | Probing which references exist by reading status codes | mitigate | "No cookie", "unknown token" and "wrong reference" return one byte-identical shape at 200; the status route never returns 403 or 404, and the tests assert the identity of the two failure responses |
| T-07-47 | Tampering | A future contributor confirming the booking from the `return_url` because the page "already knows" the session | mitigate | D-16 — the page never receives a session id, imports nothing from `lib/checkout/stripe.ts`, and a Playwright route interception fails the suite if any Stripe request is attempted from it |
| T-07-48 | Denial of Service | A confirmation page left open in a background tab polling indefinitely | mitigate | Named backoff, capped interval, bounded total window, poll paused on tab hide and stopped after give-up; the integration test asserts the request count plateaus |
| T-07-SC | Tampering | npm/pip/cargo installs | mitigate | No install in this plan — the `.ics` builder is reused from `@vamos/emails`, a workspace package, rather than adding a second calendar dependency to `apps/web` |
</threat_model>
