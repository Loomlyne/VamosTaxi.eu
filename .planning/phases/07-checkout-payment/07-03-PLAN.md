<objective>
Ship the database half of the webhook path: dedupe, ordering, the `pending → paid → confirmed`
transition, and the claim-then-send notification ledger.

Purpose: `07-RESEARCH.md`'s Pattern 3 writes `publicSql(env)\`insert into public.stripe_events …\``.
That cannot work here — `publicSql` is branded to five public-content tables, and
`…023_rls_staff.sql` revokes **everything** on `stripe_events` from `anon`, `authenticated`,
`vamos_guest`, `vamos_edge`, `vamos_public` and `vamos_staff`, granting only a column-scoped SELECT
to staff. `booking_notifications`, `booking_events` and `booking_payments` are the same story.
Every write in this path therefore needs a definer RPC granted to `vamos_system` — and that is also
where PAY-05's ordering, one-success and no-double-send guarantees belong, because a guarantee that
lives in the Worker is a guarantee a stale deploy can lose.

Output: one migration with seven small functions, one pgTAP file, refreshed generated types.
</objective>

**1. `public.stripe_event_record(p_id text, p_type text, p_stripe_created timestamptz, p_object_id
text, p_payload jsonb) returns boolean`** — the webhook fetch handler's only database call (D-13).
`insert into public.stripe_events (id, type, stripe_created, object_id, payload) values (…) on
conflict (id) do nothing`; return `true` when a row was inserted, `false` when it already existed.
Insert-first, so the ledger records the delivery before anything downstream can fail. Comment that
the caller enqueues regardless of the return value — the return is telemetry, not a gate, because
the consumer re-checks `processed_at` anyway (the exact reasoning in the `…014` header comment
about a retry being "discarded silently with a 200").

**2. `public.stripe_event_begin(p_event_id text, p_object_ids text[], p_stripe_created timestamptz)
returns table (should_process boolean, reason text)`** — the consumer's admission check (D-14),
called at the top of every message. In one statement set: increment `attempts`, then decide:
- `processed_at is not null` → `(false, 'already_processed')`.
- A row exists with `object_id = any(p_object_ids)` and `processed_at is not null` and
  `stripe_created > p_stripe_created` → `(false, 'superseded')`. This is the out-of-order rule
  stated as SQL: a `canceled` delivered after a `succeeded` for the same object is refused here,
  not in the Worker. `p_object_ids` is an array because a Checkout Session's events carry a `cs_…`
  object id while the PaymentIntent's carry `pi_…`, and both describe the same payment — the
  consumer passes both so the ordering window spans the whole family. The
  `stripe_events_object (object_id, stripe_created)` partial index already serves this predicate.
- Otherwise `(true, 'ok')`.
Comment that ordering is on Stripe's own `created`, never `received_at`, quoting the table's comment.

**3. `public.stripe_event_settle(p_event_id text, p_error text) returns void`** — sets
`processed_at = now()` when `p_error` is null, or `last_error = p_error` (leaving `processed_at`
null so the unprocessed sweep and the Queue retry both still see it) when it is not.

**4. `public.checkout_payment_settle(p_event_id text, p_session_id text, p_payment_intent_id text,
p_outcome text, p_charged_currency text, p_fx_rate numeric, p_fx_source text, p_fx_quoted_at
timestamptz, p_presentment_amount_minor bigint) returns table (booking_id uuid, reference text,
locale text, contact_email text, already_settled boolean)`** — the whole state machine, one
transaction (D-15):
- `p_outcome` is constrained to `'succeeded'`, `'failed'` or `'canceled'`; raise on anything else.
- Resolve the payment row by `stripe_checkout_session_id = p_session_id` **or**
  `stripe_payment_intent_id = p_payment_intent_id` (either may be the one the event carried).
  `IF NOT FOUND` → raise `'payment_not_found'` with `errcode = 'P0002'`; the consumer treats that as
  retryable, because the intent route's own transaction may not have committed yet.
- If the row is already `'succeeded'` and `p_outcome = 'succeeded'`, return early with
  `already_settled = true` and change nothing — the idempotent redelivery path.
- Update `public.booking_payments` setting `status`, `captured_at` (only on success), and the FX
  quadruple + `charged_currency` when the caller supplied them. Plan 07-01's whitelist enforces
  write-once and terminality; do not defeat it with a second update.
- On success: move `public.bookings.status` `pending → paid → confirmed` and move each
  `public.booking_legs.status` the same way, following the roll-up rule
  `manage_booking_cancel` already implements — read it and mirror it rather than inventing a second
  rule. Write one `booking.status_changed` `booking_events` row per transition with both
  `from_status` and `to_status` set (`booking_events_status_pair` requires it) plus one
  `payment.succeeded` row with `payment_id` set, `actor_kind = 'stripe'`, `actor_label = 'Stripe
  webhook'`. On failure/cancel: leave the booking `pending`, write one `payment.failed` row.
- Set `public.stripe_events.processed_at = now()` for `p_event_id` in the same transaction, so
  "processed" and "the effect of processing" commit together — this is the gap the `…014` comment
  describes ("the retry hits the primary key, is discarded silently with a 200, and the customer has
  been charged while the booking stays 'pending' forever").
- Let a `23505` on `booking_payments_one_success` propagate — a second distinct PaymentIntent
  reaching `succeeded` on one booking is a fact the consumer must surface, not swallow.
Never write a CHF amount, and never compute a timestamp in the Worker for a value this function
compares — `now()` here is Postgres's.
