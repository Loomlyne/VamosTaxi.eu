<objective>
Turn the two proven no-ops in `worker.ts` into the only path that confirms a booking.

Purpose: the payment succeeds somewhere this application cannot see. TWINT sends the customer to a
banking app, 3DS sends them to their card issuer, and both may never come back to the tab that
started the payment — so the browser's return is a UI event, not a fact. The verified webhook is the
fact. Plan 07-03 already put the ordering, the dedupe and the state transition in SQL where a stale
deploy cannot lose them; this plan is the thin, testable Worker that calls them in the right order
and hands the result to the email.

Output: one route that does four things and returns, one Queue consumer that owns the state machine,
one cron sweep, and a runbook for the morning something is stuck.
</objective>

   `cs_…` id; `retrieveCheckoutSession` yields the `pi_…` id, and **both** go in the array. Write

2. **Branch** (D-15). The primary fulfillment signal is `checkout.session.completed` with an explicit
   `session.payment_status === 'paid'` check — one path covering an instant card payment and a
   delayed TWINT redirect alike, which is why it is preferred over branching on
   `payment_intent.succeeded`. Map `paid` → `succeeded`; any other status on a completed session →
   `failed`; `checkout.session.expired` and `checkout.session.async_payment_failed` → `failed`;
   `payment_intent.canceled` → `canceled`. Any other type is recorded processed with no state change
   and acked — the ledger keeps it, the state machine ignores it. Note in the comment that D-15 is
   MEDIUM confidence in the research and that both candidate events are idempotent against the same
   dedupe and ordering scheme, so being wrong here costs efficiency, not correctness. Corroborate
   against `docs.stripe.com/checkout/fulfillment` while writing it and record the answer.
