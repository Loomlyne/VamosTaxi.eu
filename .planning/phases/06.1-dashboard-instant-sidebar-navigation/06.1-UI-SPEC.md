# UI Design Contract — Phase 06.1: Dashboard instant sidebar navigation

## Purpose and boundary

Make authenticated dashboard sidebar routing immediate and in-place. Selecting a sidebar destination changes only the existing ops-shell hash route and rendered view; it must not read as document navigation.

### In scope

- Dashboard-host (`dashboard.vamostaxi.site`) hash-route changes within the existing ops shell.
- Removal of the dashboard-only visual hash-switch treatment in `app/vamos-page-transition.js`.
- Retention of existing `app/ops/ops.dc.html` local route rendering, sidebar active state, and narrow-sidebar close behavior.
- A narrow source-level regression proof in `apps/web/lib/ops/ops-dc-settings.test.ts` that the dashboard transition cannot return unnoticed.

### Explicitly out of scope

- **Public-site cross-document transitions:** unchanged, including page-transition sheets, boot cover, document-navigation interception, and public-page reduced-motion handling.
- **Data/API changes:** no endpoint, database, authentication, cache, or model changes.
- No redesign, copy, layout, component replacement, or replacement motion treatment.

## Interaction contract

### Sidebar route selection

1. A dispatcher activates an existing sidebar hash link such as `#bookings`, `#calendar`, `#vehicles`, `#reviews`, `#settings`, or `#profile`.
2. The browser performs its normal same-document hash update.
3. The ops shell’s existing `hashchange` handler reads the route and updates local component state.
4. The active sidebar item updates from that existing route mapping.
5. The corresponding view renders inside the current dashboard shell.
6. No transition controller, overlay, temporary cover, transition class, keyframe, opacity change, translate, fade, or delay is applied to the dashboard root or its content.

### Motion

- Sidebar hash navigation has **no authored motion**. It is instantaneous, including when `prefers-reduced-motion` is not set.
- The operations dashboard never invokes the document-level transition overlay for same-document hash changes.
- Public cross-document navigation retains its current motion policy exactly.

### Loading and failure states

- This interaction adds no loading state, skeleton, white surface, or concealment layer.
- Existing rendered-view errors and empty states remain owned by their current feature components; this phase adds none.

## Visual contract

- Preserve the existing shell, sidebar, route content, typography, spacing, colors, tokens, and focus treatment.
- No new CSS token, color, z-index layer, animation timing, or transition class is allowed.
- A route change must not cause a white flash, opacity dip, translation, stale cover, or blank intermediate frame.

## Accessibility contract

- Preserve native anchor/hash semantics and keyboard activation.
- Preserve `:focus-visible` treatment and the existing active-route indication.
- Do not add focus management, ARIA roles, live announcements, or time-dependent motion.
- Narrow screens retain the existing behavior where a selected sidebar route closes the open navigation panel; the route becomes immediately available in the same shell.

## Responsive contract

- **Desktop (≥900px):** persistent sidebar and content switch in place immediately.
- **Narrow (<900px):** the current navigation drawer/scrim may close as part of the established mobile navigation behavior, but the content itself receives no route-transition overlay or animation.
- No new breakpoints or layout changes.

## Engineering and verification contract

- Remove the dashboard-only `runDashboardHashTransition` handler, its `hashchange` registration, the injected `vtOpsHashSwitch` keyframes, and the `vt-ops-hash-switch` class usage from `app/vamos-page-transition.js`.
- Do not change the generic page-transition controller or public navigation interception.
- Update the focused test so it asserts local ops hash rendering remains wired, while asserting no `vt-ops-hash-switch`, `runDashboardHashTransition`, dashboard `hashchange` visual listener, or dashboard animation keyframe remains.
- Run the focused test, then `pnpm run lint`, `pnpm run typecheck`, and `pnpm run build` during implementation verification. Exercise the authenticated staging dashboard’s desktop and narrow sidebar routes before UAT.

## Acceptance criteria

1. Each existing sidebar destination changes the visible dashboard view without a white/concealing overlay or any fade/translate motion.
2. The URL remains an in-document hash route and the ops shell is not replaced.
3. Desktop active navigation and narrow-drawer close behavior remain correct.
4. Public-site document transitions remain unchanged.
5. No data/API contract changes occur.
6. The focused regression proof and all required quality gates pass.
