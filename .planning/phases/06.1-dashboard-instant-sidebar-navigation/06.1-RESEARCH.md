# Phase 06.1 Research — Dashboard instant sidebar navigation

## Research question

How can the operations dashboard switch sidebar hash routes immediately in the existing document, without a visual overlay or page-like transition, while preserving public-site document transitions?

## Findings

- The violation is isolated to `app/vamos-page-transition.js:66-82`.
  - `isDashboardPage()` identifies the dashboard.
  - `runDashboardHashTransition()` listens to `hashchange`, then toggles `vt-ops-hash-switch` on `#dc-root`.
  - Injected `@keyframes vtOpsHashSwitch` animates root opacity and `translateY(2px)` for 150ms.
- `app/ops/ops.dc.html:188-205` already owns the correct local route lifecycle.
  - `readHash()` parses the hash into existing routes.
  - Its `hashchange` handler sets local route state and `navOpen: false`; this preserves the narrow-drawer close behavior without using the transition controller.
- `app/ops/OpsSidebar.dc.html` already uses hash anchors and active-route props. It needs no source change.
- The generic document-transition controller excludes hash-only links from document navigation interception. This protects same-document dashboard routing; it must remain untouched.
- `apps/web/lib/ops/ops-dc-settings.test.ts:130-140` currently proves the rejected hook/class exists. It is the focused test to update.
- `apps/web/public/app/vamos-page-transition.js` is a generated mirror. Do not edit it directly; build/sync regenerates it from `app/`.

## Exact change approach

1. In `app/vamos-page-transition.js`, remove only the dashboard-specific hash animation block:
   - `isDashboardPage()` if it has no remaining call sites;
   - `runDashboardHashTransition()`;
   - injected `opsHashStyle` / `vtOpsHashSwitch` CSS;
   - the dashboard `hashchange` registration.
2. Preserve all generic page-transition behavior, especially same-document hash exclusion and public cross-document covers.
3. In `apps/web/lib/ops/ops-dc-settings.test.ts`, retain proof that the existing ops shell has local `hashchange` routing. Replace positive assertions for the removed transition with negative assertions for the class, function, handler, and keyframe.

## Verification

1. Run the focused Vitest proof for `ops-dc-settings.test.ts`.
2. Run `pnpm run lint`, `pnpm run typecheck`, and `pnpm run build`.
3. Start the appropriate local/staging dashboard path and manually activate every sidebar route at desktop and a narrow viewport. Confirm the active view changes in place; no opacity/translation, white cover, concealment, blank intermediate frame, or document reload occurs.
4. Confirm a public-site navigation still uses the existing document-transition path.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| Accidentally removing public transition behavior | Edit only the named dashboard hash-animation block; retain generic controller code and document-navigation eligibility rules. |
| Losing narrow drawer close behavior | Do not alter `app/ops/ops.dc.html` hash listener, which already sets `navOpen: false`. |
| Editing a generated asset | Treat `app/vamos-page-transition.js` as canonical; let build/sync update `apps/web/public/app/`. |
| Existing unrelated quality-gate failure | Report inherited failure exactly and do not broaden scope; historical Phase 06 notes a pre-existing readonly `process.env.NODE_ENV` mutation in `apps/web/lib/ops/invite.test.ts` that may still affect typecheck. |

## Conclusion

This is a two-file, low-risk change. The current dashboard hash animation is the sole source of the page-like feeling; the ops shell already has the correct immediate local state update.
