<objective>
Replace Supabase's own auth email with one this project controls, so AUTH-01's confirmation and
AUTH-02's recovery link arrive in the customer's language.

Supabase's default auth email is one Go-templated HTML document per project. There is no
per-locale branching in it, and the well-known workaround — stashing a language string in user
metadata and branching inside that single template — cannot produce a genuinely separate
document per language. The Send Email Hook replaces the send entirely and hands this
application the user record, the action type and the token, which is the only mechanism that
satisfies the four-language law.

One sequencing decision is recorded rather than assumed: `packages/emails` does NOT stand up a
React Email toolchain in this phase. The candidate packages carry no legitimacy audit in any
phase's research, and three transactional emails consisting of a heading, a sentence, a code and
a link do not need a rendering framework. The package's exported surface is designed so Phase 7
can put one behind it without changing a caller.

Purpose: an English-only confirmation email is a four-language product with an English seam in
the single moment a new customer is paying most attention.
Output: `packages/emails` filled, `/api/auth/email-hook`, unit and integration proofs.
</objective>

         a closed union, `user.email` as an email, `email_data.token`/`token_hash`/`redirect_to`

         Phase 5 flows — return 200 without sending and log the skipped type, so an unexpected

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public internet -> /api/auth/email-hook | An unauthenticated endpoint that can cause mail to be sent |
| user-controlled metadata -> email HTML | `full_name` is whatever the visitor typed at signup |
| application -> Resend | A third-party service receives an address and a token-bearing link |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-52 | Spoofing | forged hook calls | mitigate | `standardwebhooks` `Webhook#verify` runs before any payload read; failure is a bare 401 with no body; the integration spec proves tampered and unsigned calls are both rejected |
| T-05-53 | Information Disclosure | the hook as a user-existence oracle | mitigate | Every failure path returns a status only, with identical shape regardless of whether the address exists; no log line carries the address, token or link |
| T-05-54 | Tampering | HTML injection via `full_name` | mitigate | Every interpolation passes through one `escapeHtml`; a grep asserts no unwrapped template interpolation exists in `auth.ts`; a unit test proves a `<script>` display name renders inert |
| T-05-55 | Information Disclosure | token leaking into logs | mitigate | The file header states the rule and a grep asserts no `logger` call takes `token`/`redirect_to`; the no-Resend-key path logs a redacted body |
| T-05-56 | Denial of Service | hook timeout on a cold Worker | accept | Deferred to plan 05-24 (D-27), which times a real round trip against the dashboard's stated timeout once the owner's Auth settings are reachable; nothing in application code can settle it |
| T-05-57 | Repudiation | an unexpected Supabase action type silently failing | mitigate | `email_change` and `invite` return 200 and log the skipped type rather than 500ing a customer's request; the integration spec covers `invite` |
| T-05-SC | Tampering | package installs | mitigate | This plan installs nothing new — `resend`, `zod` and `standardwebhooks` were pinned by plan 05-01 against 05-RESEARCH.md's `[OK]` audit. `@react-email/*` is explicitly NOT installed because it carries no audit row |
</threat_model>
