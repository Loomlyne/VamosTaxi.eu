<objective>
Stop the account mock from treating browser-local `vamosAuth` data as a valid authenticated
session. A customer who has no live Supabase session must be sent to sign-in, rather than shown
an editable profile whose save request is guaranteed to return `no-user`.

Purpose: make the account edit flow depend on the same server-authenticated session that the
profile API requires.
Output: an account session guard and regression coverage for both the stale-browser state and a
real signed-in profile update.
</objective>

<context>
The reported page is `/account#security`. The deployed handler is present: an anonymous staging
POST to `/api/auth` with `action: "update-profile"` returns `{ ok: false, reason: "no-user" }`,
which proves the request reaches `runUpdateProfile` rather than falling through to sign-in.

The fault is the client/server auth split:

- `apps/web/public/app/pages/account.html` calls `/api/auth/session` at lines 504–533.
- When that endpoint says `signedIn: false` (or fails), lines 509–510 and 528–532 retain
  `localStorage.vamosAuth` and render the account editor anyway.
- `saveName` then posts to `/api/auth` (lines 617–632). `runUpdateProfile` correctly calls
  `supabase.auth.getUser()` and returns `no-user` without a real session (`apps/web/lib/auth/run.ts`
  lines 175–202).
- The client deliberately collapses every non-success response to “Could not save. Try again.”
  (lines 624–631), hiding the actual state.

The authenticated update implementation itself is already covered at unit level and correctly
writes `first_name`, `last_name`, and `full_name` to Supabase user metadata. This plan does not
change the API contract, Supabase schema, pricing, ops, or account design.
</context>
