<objective>
Wire the auth components to real Supabase Auth and give them their three routes, so AUTH-01,
AUTH-02 and AUTH-03 are demonstrable end to end against a local `supabase start`.

Everything auth-related that talks to Supabase lives in one Server Action module. The components
from plan 05-07 make no network call, the pages are thin, and the actions are the single audited
surface — which is what makes "no `getSession()` anywhere" and "no enumeration oracle" greppable
facts rather than review promises.

Two decisions 05-CONTEXT leaves to the planner are settled here: a dedicated `/sign-up` route
(because `lib/metadata.ts`'s one-canonical-URL-per-page contract is the reason that file exists)
and the non-distinguishing signup response (because ASVS V2 and Supabase's own guidance both
favour it, and plan 05-07 keeps the mock's distinguishing banner built and reachable so nothing
is lost from the design).

**Out of scope, stated because these pages sit next to them in the mocks:** `account`,
`bookings` and `booking-detail` are Phase 8; AUTH-06's "we found bookings under this email"
claim UI is Phase 8 too — D-07 already gives it the data linking for free.

Purpose: a session that survives a refresh and a signup that does not skip verification.
Output: the action module, the callback route, three pages, and AUTH-01..03 integration proofs.
</objective>

        with the code or an error message in the URL.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> Server Action | Every credential in the product crosses here |
| emailed link -> /api/auth/callback | An attacker can craft the query string a victim clicks |
| Worker -> Supabase GoTrue | The only party that can mint or verify a session |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-76 | Spoofing | session fixation | mitigate | Every successful authentication ends in a redirect through next-intl's helper, so the authenticated state is only ever observed on a fresh request carrying the newly minted cookie; the callback renders nothing |
| T-05-77 | Information Disclosure | account enumeration on signup and reset | mitigate | `signUpAction`, `requestOtpAction` and `requestPasswordResetAction` return `{ stage: "sent" }` unconditionally; sign-in returns one generic `credentials` banner; a test asserts two signups with the same address are byte-indistinguishable |
| T-05-78 | Tampering | open redirect through the callback's `next` | mitigate | A named validator requires a leading `/`, rejects `//` and `/\`, and requires membership of `PUBLIC_ROUTES` after stripping the locale segment; two tests drive off-site targets |
| T-05-79 | Spoofing | trusting an unverified cookie | mitigate | D-03: `getUser()` only, asserted repo-wide by grep; `updatePasswordAction` re-reads the user before updating so a stale cookie cannot change a password |
| T-05-80 | Elevation of Privilege | a password signup yielding a usable session | mitigate | D-06: the action returns the `sent` stage and the test proves no session exists until the emailed link or code is exercised; the local stack's confirm-email setting is asserted, and the hosted toggle is plan 05-24's check |
| T-05-81 | Denial of Service | Set-Cookie folding on a real auth response | mitigate | D-02's single-instance middleware mutation, re-asserted here against an actual sign-in response with `getSetCookie()` |
| T-05-82 | Information Disclosure | credentials in logs | mitigate | A grep asserts no `logger` call in `lib/auth/actions.ts` takes `email` or `password`; failures log a code only |
| T-05-83 | Elevation of Privilege | Server Actions as an unauthenticated RPC surface | mitigate | Every action validates with zod before touching Supabase and derives identity from the cookie jar, never from an argument; no action accepts a user id |
| T-05-SC | Tampering | package installs | mitigate | This plan installs no package. |
</threat_model>
