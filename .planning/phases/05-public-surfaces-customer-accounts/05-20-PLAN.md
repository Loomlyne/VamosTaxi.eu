<objective>
Build the one piece Phase 1 deliberately left unbuilt, and satisfy AUTH-04 with it.

`apps/web/components/shell/SiteHeader.tsx` carries a comment naming its own gap: the mock's
signed-in branch — the avatar disc, the account menu and the notification bell — was not ported
because all of it read the mock-only `vamosAuth` and `vamosNotices` storage keys. Phase 5 has a
real session, so the avatar, the menu and sign-out get built against `getUser()`.

One architectural decision is recorded rather than assumed. Reading the session in the layout
would force every public page in the project to dynamic rendering, which is exactly what Phase
1's Pitfall 2 warns against and what the Phase 10 traffic target depends on not happening. So
the header keeps its SSR signed-out control row — byte-identical to today's — and a small client
component swaps in the signed-in control after fetching a minimal, `getUser()`-backed snapshot.

One piece is deliberately not built and flagged: the notification bell, whose every mock notice
is booking-attached and whose data source does not exist until Phase 7.

Purpose: "sign out from any page" is a header feature, and the header is the one component
CLAUDE.md makes mandatory on every page.
Output: the session route, `SiteHeaderAccount`, extended gallery and baselines, an AUTH-04 proof.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> /api/auth/session | Any script on the page can read this response |
| account menu -> signOutAction | A state-changing action reachable from every page |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-103 | Information Disclosure | session snapshot contents | mitigate | Three fields only; a grep asserts no email, user id, token, `app_metadata` or role claim appears in the route, and the sign-out spec asserts the body contains no `@` |
| T-05-104 | Information Disclosure | a shared cache serving one visitor's snapshot to another | mitigate | `Cache-Control: private, no-store` on the response, and the route is `force-dynamic` so it is never statically generated |
| T-05-105 | Spoofing | trusting a client-side session claim | mitigate | The snapshot is `getUser()`-backed server-side and is used ONLY to choose which header control renders; no authorisation decision anywhere in the product reads it |
| T-05-106 | Elevation of Privilege | sign-out as a client-side call | mitigate | Sign-out is a `<form action={signOutAction}>` Server Action that clears cookies through the same server client that set them; no client-side Supabase call exists |
| T-05-107 | Denial of Service | Set-Cookie folding on sign-out | mitigate | The D-02 pattern applies to the sign-out response too; the spec asserts the expired cookies arrive as separate `getSetCookie()` entries |
| T-05-108 | Repudiation | a half-built notification bell implying notices exist | mitigate | The bell is not built at all rather than stubbed; the header's comment records why and plan 05-24 raises it for the owner |
| T-05-109 | Denial of Service | the session fetch blocking first paint | mitigate | The signed-out control is the SSR default and the fetch happens after hydration; the layout reads no session, so no public page loses static rendering |
| T-05-SC | Tampering | package installs | mitigate | This plan installs no package. |
</threat_model>
