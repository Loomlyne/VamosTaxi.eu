<objective>
Create the two tables SITE-04's forms write to, and the only access path `anon` gets to them.

Phase 2 designed 29 tables and none of them is a contact form. Phase 3 designed five identity
doors and stated, in `asQuote`'s own doc comment, that the writer behind an anonymous door
should be a `SECURITY DEFINER` RPC rather than a table grant. This plan is the first time that
stated preference gets exercised, so it is written to be the pattern Phase 7's checkout INSERT
copies rather than a one-off.

It is the second and last Phase 5 plan that applies a migration, and it is held to Wave 2 behind
plan 05-02 on purpose: migrations reach one shared local Postgres through `supabase db reset`,
and two plans applying migrations in the same wave would race the same database.

Purpose: "reaches both the inbox and the database" is half a schema problem and half a
privilege problem, and the privilege half is the one that fails silently.
Output: one additive migration, one pgTAP suite, regenerated types.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous visitor -> Postgres | An unauthenticated party's input reaches a definer function |
| definer function -> table | The function runs with the owner's privileges, above every policy |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-33 | Elevation of Privilege | anonymous access to submission data | mitigate | `anon` holds EXECUTE on two functions and no privilege on either table; the RPCs return only `(id, created)`; pgTAP asserts both the `42501` insert denial and the `42501` select denial |
| T-05-34 | Tampering | `search_path` hijack inside a definer body | mitigate | `set search_path = ''` on both functions plus schema-qualification of every identifier and type in body and DECLARE |
| T-05-35 | Elevation of Privilege | PUBLIC inheriting EXECUTE on a new function | mitigate | Explicit `revoke all on function ... from public` before each grant, asserted by `function_privs_are` (F-13: a new function does not inherit the schema default-privilege revoke) |
| T-05-36 | Denial of Service | unbounded writes through the anonymous RPC | mitigate | Length `check` constraints on every free-text column plus the unique `idempotency_key`; the request-rate control is plan 05-13's always-on Turnstile (D-22), and the two layers are deliberately separate |
| T-05-37 | Information Disclosure | a submission served from a stale cache | mitigate | D-23: the write path is `asAnon` on `HYPERDRIVE_NOCACHE`; neither table is granted to `vamos_public` and neither joins `publicSql`'s five-table allowlist, so a cacheable read of this data is impossible by grant |
| T-05-38 | Repudiation | a lost submission that reached the inbox but not the database | mitigate | `idempotency_key` makes the Route Handler's retry safe, so plan 05-13 can retry the insert without producing a second record or a second email |
| T-05-SC | Tampering | package installs | mitigate | This plan installs no package. |
</threat_model>
