## 1. Supabase Auth — the three calls

| Call | Creates user? | Sends mail? | Unknown e-mail | Known e-mail | Fit for 26.5 |
|------|---------------|-------------|----------------|--------------|--------------|
| `auth.signInWithOtp({ email, options: { shouldCreateUser: false } })` | no | yes (magic link + 6-digit code, via our Send Email Hook) | error `code: "otp_disabled"`, message "Signups not allowed for otp", HTTP 422 | sends mail, no error | **Sign-in path** (Option 2 and known-email). Swallow `otp_disabled` → same `SENT` answer |
| `auth.admin.createUser({ email, email_confirm: false, user_metadata })` (service role) | yes, unconfirmed, no password | **no** | creates | error `email_exists` (422) | **After-payment account creation** — silent, then we send our own mail |
| `auth.admin.generateLink({ type: "magiclink", email, options: { redirectTo } })` (service role) | no (user must exist) | **no** — returns `properties.hashed_token` | error | returns link data | **Account-ready mail**: we build `/api/auth/callback?token_hash=…&type=magiclink&next=/{locale}/account` and send with our own template |
| `auth.admin.inviteUserByEmail(email)` | yes | yes (type `invite`) | creates + mails | error `email_exists` | **Rejected**: our `invite` template is staff copy ("You're invited to Vamos Taxi… Accept invite", `packages/emails/src/messages.ts`) and the redirect is the invite flow |

Facts to prove in the local Worker e2e (not assumed on faith — tag `[VERIFY-E2E]`):
- `otp_disabled` for an unknown address with `shouldCreateUser:false` (Supabase GoTrue behaviour, [CITED: supabase-js docs "shouldCreateUser"]).
- For an **existing but unconfirmed** user, GoTrue's `/otp` sends the **signup confirmation** mail (hook `email_action_type: "signup"`), not `magiclink`. Our hook maps `signup` → the sign-up template; the callback's `verifyOtp` accepts it (`OTP_TYPES`). Following it confirms the e-mail. [VERIFY-E2E]
- Verifying a `magiclink` token_hash for an unconfirmed user sets `email_confirmed_at`. [VERIFY-E2E]
- `generateLink` does not trigger the Send Email Hook. [VERIFY-E2E]

- `apps/web/app/api/auth/route.ts` `fields.method === "magic"` branch passes `createUser: !dashboard` → **on the public host a magic-link sign-in creates an account today.** The checkout sign-in must pass `createUser: false` (binding checker rec. 1). ## 2. Timing and enumeration (binding checker rec. 1)

Unknown e-mail returns fast (422 from GoTrue, no mail); known e-mail waits for the hook → Resend. Mitigation for the checkout sign-in send: same body `{ stage: "sent" }`, same status 200, and a **response floor** (answer no earlier than a fixed floor, e.g. 1 200 ms from request start, plus ≤150 ms jitter). `ctx.waitUntil` is **not** usable: the PKCE verifier cookie set by `signInWithOtp` must ride on the response. Same floor for resend. Wrong code already answers generic `CODE_INVALID`.

The PAY-time known-email check (D-04) is enumeration **by owner decision**: the page shows the sent stage instead of Stripe. Mitigations (UI-SPEC): neutral copy, Turnstile on PAY when a check runs, per-IP + per-e-mail rate limit.

## 3. Where the account is created — decision: after payment, in the settle queue consumer

`apps/web/lib/checkout/settle.ts`:
- `handleStripeMessageWithDeps(message, deps)` — on a succeeded, first (`!row.already_settled`), non-extra settle it calls `deps.deliverConfirmation(row)` inside try/catch (a mail failure never retries the settle).
- `SettleRow` carries `booking_id`, `reference`, `locale`, `contact_email`, `already_settled`, …
- `handleStripeMessage(env, …)` wires deps; every DB call is `asSystem(env, sql => sql\`select * from public.<definer fn>(…)\`)`.

Hook point: right after `deliverConfirmation`, a new best-effort `deps.provisionAccount(row)` (never throws, never changes `ack`). It:
1. reads the account request for the booking through a **SECURITY DEFINER** function (`vamos_system` has no table grants — raw table SQL is 42501 on live; `apps/web/lib/db/system-reads.ts` + its guard test `system-reads.test.ts` "asSystem never touches a table it has no grant on");
2. `admin.createUser({ email, email_confirm: false, user_metadata: { full_name, vamos_locale, vamos_account_origin: "checkout-<choice>" } })` — never `signup_consent` (D-10)`; `email_exists` → stop, no mail (idempotent under queue retry);
3. per-address limiter `account-mail:<email>` (fail-closed for this mail);
4. `admin.generateLink({ type: "magiclink", email })` → own callback link → mail "Your Vamos Taxi account is ready — confirm with this link" (new `account_ready` auth-mail kind in `@vamos/emails`, four languages, not legal copy).

Why not at PAY / booking creation: binding checker rec. 3 — abandoned checkouts must create no account and send no mail.

D-05 already holds on main (quick 260929-acl): `app.ensure_customer_for_user` returns null unless `auth.users.email_confirmed_at` is set; `customer_claim_guest_bookings()` links bookings only for a confirmed e-mail and runs from `/api/account/bookings`. An unconfirmed checkout-made user cannot get a session (no password; the only way in is a link/code, which confirms). 26.5 adds a pgTAP case proving it for a `createUser(email_confirm:false)` user.

## 4. Consent — shape and decision

`public.consent_log` (20260823000018) is **cookie** consent: `method in ('accept_all','reject_all','save_choices','settings_change')`, category booleans, written only through `record_consent`, and Phase 27 reads "the latest row wins" for Meta. Putting account rows in it would corrupt that rule. → **New append-only table** `public.checkout_account_consent`:

| column | type | note |
|--------|------|------|
| id | bigint identity pk | |
| booking_id | uuid fk bookings on delete set null | |
| email | text not null | copied **server-side from `bookings.contact_email`** at write time (tied to the e-mail actually paid with, checker rec. 5) |
| choice | text check in ('guest','create') | |
| notice_version | text null | **not null when choice = 'guest'** (CHECK); null for 'create' only while the owner notice does not exist |
| locale | text check in ('en','de','fr','ar') | |
| user_agent | text | |
| ip_truncated | inet | via existing `truncateClientIp(cfConnectingIp(headers))` (`lib/consent/ip.ts`) |
| recorded_at | timestamptz default now() | |

RLS on, no policies, no table grants to `anon`/`authenticated`/`vamos_*`; append-only trigger (pattern `20260823000019_append_only.sql`). Written only by a definer function granted to the checkout role.

Existing sign-up consent (`lib/auth/signup-consent.ts`): sign-up leaves `user_metadata.signup_consent = "pending"`; the callback writes a cookie-consent row on first confirmation. **Not used** by checkout-made accounts (D-10: no consent of any kind until the owner's notice exists).

**Revision 1 (D-10):** the table above is split in two. `checkout_account_requests` records only that the customer asked (booking, e-mail from the booking, choice, locale) and is what settle reads; `checkout_account_consent` (notice_version NOT NULL for both choices) is written in the same call only when the owner's notice exists. Create an account works with a request row and no consent row while the notice is TBC.

## 5. The switch (owner decision at signature)

"Automatic guest accounts OFF until the owner's notice text exists in en/de/fr/ar; guests book and pay as today; consent never logged against the TBC placeholder."

Effective switch = **both**:
- DB: new column `public.settings.guest_accounts_live boolean not null default false` (flipped by the owner with one SQL line after the texts ship — a kill switch without deploy), read through a definer function;
- Code: `ACCOUNT_NOTICE_VERSION: string | null = null` in `apps/web/lib/checkout/account-notice.ts`, plus the message key `checkout.accountNotice` non-empty in all four `messages/*.json`. `accountNoticeReady()` is true only when all hold.

`pricing_live` is analogous but derived from the rate version; there is no generic flags table. A `settings` column is the smallest honest switch.
