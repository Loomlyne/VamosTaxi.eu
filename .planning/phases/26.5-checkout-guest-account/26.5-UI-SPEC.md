## Layout and Interaction Contract

Focal point is unchanged: section 1 class cards, then PAY. The panel is a quiet charcoal/white control, not a banner.

### Placement (D-01)

Inside the section 2 `SectionCard`, above the contact fields, DOM order:
1. Kicker `CHOOSE HOW TO CONTINUE` (it is the group's `legend` / `aria-labelledby`).
2. `AccountChoice` — three options: Continue as guest · Sign in · Create an account.
3. Expansion for the selected option (below the group, full width).
4. 1px hairline divider (24px gap).
5. Contact fields → flight → extras → disclosures (26.3, unchanged), except where a state below hides them.

The section header's inline-end link "Have an account? Sign in" is **removed** while the panel shows (the panel replaces it).
Signed-in customers keep the header text "Signed in as {email}".

### Grid per width

| Width | Options | Expansion |
|-------|---------|-----------|
| 1440 / ≥1081 | `repeat(auto-fit, minmax(200px, 1fr))` → 3 across in the main column; card = radio at inline-start, then icon + title (16/600), description below (13/400) | Sign-in form: email field (flex 1, `min-width:0`) + send button (auto width) on one row, 12px gap |
| 1024, 768 / 681–1080 | same rule → 3 across at 1024 and 768 (≈ 200–300px each; German descriptions wrap to 2 lines, cards stretch to the tallest) | same row; wraps to stacked if the button no longer fits (`flex-wrap`) |
| 390 / ≤680 | 1 column, full-width rows, 12px gap; description stays under the title | stacked: field, then full-width button |

Nothing scrolls sideways at 390. Logical properties only; in Arabic the radio sits at the right, order reads right to left.
Check en, de (+30%) and ar at all four widths.

### States — `AccountChoice`

| State | Look | Behaviour |
|-------|------|-----------|
| Default (on load, signed out) | **Continue as guest preselected** [discretion] — the fastest path; the other two unselected: 1px hairline border | The group is always visible; the choice is a visible question, not a hidden default |
| Hover | 1px `--vt-charcoal-700` border, `--vt-grey-50` fill (unselected only) | 140ms |
| Press | `translateY(1px)` | |
| Focus | `--vt-ring` on the card (keyboard focus lands on the checked radio; arrows move and select, per native radiogroup) | |
| Selected | 2px charcoal border, charcoal radio dot, `aria-checked="true"` | Changing option never clears typed contact values |
| Disabled | 42% opacity, `not-allowed` | While PAY is loading (existing fieldset `disabled`) and while a link is sending |
| Loading | not a separate look: signed-in status is resolved on the server render, so the panel never flashes. If it must resolve on the client, the panel renders signed-out and swaps in place when the session arrives |
| Error | red line with `circle-alert` directly under the group, `aria-describedby` on the group | Shown by the PAY rules below |
| Signed in | Panel not rendered | Header: "Signed in as {email}"; contact fields prefilled from the account (only empty fields; typed values are never overwritten) |

### Option 1 — Continue as guest (D-02, D-04, D-06)

- Expansion: one `Checkbox` row (44px, unticked on load). Label = owner legal text; until it lands the label is
  `<span data-tok>account creation notice</span>` → reads "account creation notice TBC". Placeholder label text stays
  English in all four languages (ADR-011). The owner's text will ship in en/de/fr/ar in `messages/*.json` and replace the pill.
- Contact fields show as today.
- PAY: consent unticked → error under the checkbox "Tick the box to continue as a guest", scroll + focus the checkbox.
  Ticked → PAY runs; the server logs the consent (choice `guest`, policy version, locale, time, truncated IP — the
  existing consent-log pattern) **before** the account is created. No consent is written from the browser alone.
- If the server finds the email already has an account → the known-email state (below). If not → Stripe as today;
  the account is created per the planner's decision; no extra screen.

### Option 2 — Sign in (D-03, D-07)

- Expansion = `CheckoutSignIn` stage `form`: `EMAIL` field (54px, icon `mail`, bound to the same email value as the
  contact field, hint "Use the email on your account") + `EMAIL ME A SIGN-IN LINK` (secondary, 54px). Under it the link
  "More ways to sign in" → existing `/sign-in?returnTo=…` with `stashForSignIn` (passkey and the shipped methods live
  there; this phase adds no password UI).
- While Sign in is selected and not yet signed in, the contact fields are hidden (they fill from the account after sign-in).
- Send: validates the email (existing "Enter an email address" / "Check the email address"), Turnstile, then
  button loading "Sending link", group disabled. The request uses the shipped magic-link/OTP action with
  `returnTo` = this checkout URL (trip, class, extras in the query) and **no account creation** on this path. The answer
  is always the `sent` stage, whether or not the email exists.
- Stage `sent` (same as the known-email state, below).

### Option 3 — Create an account (D-02, D-03)

- Expansion: one info line (13px, secondary) "We email you a link to finish your account. Your booking goes ahead now."
  plus the same `data-tok` account creation notice as a plain line (no checkbox — the customer asked for the account)
  [discretion: owner may want the tick here too].
- Contact fields show as today (first name, last name, email, mobile feed the account; no password field).
- PAY: server logs consent (choice `create`), runs the same known-email check; new email → account created, confirmation
  link sent to that email, Stripe as today. Known email → the known-email state.

### Known-email state and the `sent` stage (D-04, neutral)

One look for three triggers: Sign in → send; Guest PAY on a known email; Create account PAY on a known email.

- Replaces the expansion (options stay visible above it; contact fields stay as they were).
- Contents, in order:
  1. `Icon mail` + Body 16/600: **"Check your inbox — we sent a sign-in link"** (owner's wording).
  2. Label 13/400: "Sent to {email}" (email `.vt-dir-keep`).
  3. Body: "Open it on this device to come back here and pay."
  4. Kicker `OR USE THE CODE`; `6-digit code` field (54px, hint "It is in the same email as the link.") +
     `SIGN IN` (secondary, 54px; loading "Signing in"). Code sign-in keeps everything on this tab (voucher, company,
     note included) [discretion: code stays until the D-03 passwords-off job decides].
  5. `SEND ANOTHER LINK` (ghost 44px) → on success "Sent again just now." with `check` in `--vt-success`.
  6. Link "Use a different email" → back to the previous stage with the email field focused and selected.
  7. Hint 13px: "Nothing there? Check spam, then send another link."
- The copy never says an account exists or does not exist. Rate limit + Turnstile on every send and on the PAY-time check.
- Announce the heading in a polite live region; move focus to the heading. PAY returns to idle.
- Link path (D-07): link → `/api/auth/callback?next=<checkout returnTo>` → checkout with trip, class and extras from the
  URL, voucher/company/note from the per-tab stash (a link opened in a new tab restores URL data only — this is the
  shipped G1 behaviour; the code path is the in-place alternative).
- The original tab: on window focus it re-reads the session; if now signed in, the panel is replaced by the signed-in
  state without a reload [discretion].
- Success (link or code): panel removed, header "Signed in as {email}" (announced), empty contact fields prefilled,
  focus to the first empty required field or else to PAY.

### PAY rules added (26.3 order: class → section 2 → first name …)

Section 2 is now checked first in this order:
1. Sign in selected, not signed in, nothing sent → line under the group "Sign in first, or continue as a guest."
2. Sent stage showing, not signed in → line under the sent heading "Open the sign-in link we sent, then pay."
3. Guest selected, consent unticked → "Tick the box to continue as a guest".
Then the existing contact field rules. Each failure: scroll with header offset, focus, inline error, polite announce in
the rail/bar live region (as 26.3). PAY start failure keeps the existing "Payment did not start. Try PAY again."

### Errors inside the panel

| Case | Where | Copy |
|------|-------|------|
| Email empty / malformed | email field | existing "Enter an email address" / "Check the email address" |
| Code wrong or expired | code field | existing "Check the code. It is 6 digits and works for one hour." |
| Rate limited | line under the send/SIGN IN button | existing "Too many tries. Wait a minute and try again." |
| Send failed (network/server) | `Alert tone="danger"` above the send button | "The link did not send. Try again." |
| Turnstile failed | same alert | "The link did not send. Try again." |

Errors stay until the input changes. Send/SIGN IN return to idle after an error.

### Accessibility and motion

- Group: `role="radiogroup"` labelled by the kicker; native radio inputs; arrow keys move selection.
- Expansion swap: 140ms opacity only, `prefers-reduced-motion` instant; no height spring.
- Consent checkbox, code field, email field: `aria-invalid` + `aria-describedby` on error.
- Scroll owner: follow main at execution time (Lenis via `VamosScroll` or native if the Lenis-removal quick task has landed). No second Lenis, no `scroll-behavior:smooth`.

## Owner decisions at signature (2026-09-29, question form)
- Default: **"Continue as guest" is pre-selected** when section 2 opens.
- Create an account: **pay now, confirm later** — PAY is not blocked; an e-mail link finishes the account; bookings show only after it is clicked (D-05).
- Create an account consent: **plain notice line, no checkbox**; choosing the option is the agreement; consent still logged server-side (choice `create`).
- Before the owner's notice text exists in en/de/fr/ar: **automatic guest accounts are OFF** (a switch, like pricing_live); guests book and pay as today with no account made; consent is never logged against the TBC placeholder. The switch is flipped only after the four texts are in.

## Checker recommendations adopted as binding (UI checker, 2026-09-29)
1. Sign-in with an unknown e-mail looks identical to a known one (swallow "Signups not allowed for otp"; same response, status, similar timing; same for resend and wrong code).
2. Guest and create-account PAY never sign the customer in (no auth cookie/session); an unconfirmed e-mail can never open /account (D-05).
3. Every e-mail the site sends to an unverified address (create-account confirm, guest account mail) is rate-limited and behind Turnstile, and accounts are created **only after the Stripe payment succeeds** (settle/webhook), so abandoned checkouts create no accounts and send no mail.
4. Unknown-e-mail dead end hint: "Nothing there? Check spam, send another link, or continue as a guest." (four languages).
5. "Use a different email" resets the guest consent tick; the server log is tied to the e-mail actually paid with.
6. The checkout 6-digit code field is noted for removal by the later passwords-off job (D-03).
7. Icons `log-in.svg`, `user-plus.svg` copied unchanged from Lucide into assets/icons/ or dropped; never hand-drawn.
8. 12 px spacing is the token `--vt-space-3`.
