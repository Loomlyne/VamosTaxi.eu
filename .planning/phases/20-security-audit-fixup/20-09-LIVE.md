## F17 — Arabic font is blocked (seen on live by the control session, confirmed in code; no edit)

`app/vamos-locale.js:369` loads `https://fonts.googleapis.com/css2?family=Noto+Sans+Arabic…` when the
language is Arabic. The live CSP has `style-src 'self' 'unsafe-inline'` and no `font-src`, so the
stylesheet (and the font files on fonts.gstatic.com) are refused. Arabic pages fall back to the
device's own Arabic font. Not a security hole; a display fault and, if allowed instead, a privacy
point (the visitor's IP goes to Google).

Smallest fix: serve Noto Sans Arabic from our own host (`assets/`, like the other fonts) and drop
the Google link, so the CSP stays closed. Owner question; belongs with batch C.

### Lesson from the batch C part 2 deploy (control session finding)

The hand-over said the new gateway with the old `vamos` keeps the dashboard working. On live, between
the gateway deploy and the `vamos` deploy, dashboard `/login` and `/app/ops/ops.dc.html` answered 404
for one `vamos` build. The old `Dashboard` entrypoint did not serve `/app/ops/*` from assets (a named
entrypoint skips the asset layer; only the new code reads `env.ASSETS`). The claim was reasoned, not
tested: the two-Worker test only ran new + new and old-gateway + new-vamos. Rule for any two-Worker
ship: test every intermediate pair you will pass through, or make the new Worker fall back to the
old path when the other side is not deployed yet.
