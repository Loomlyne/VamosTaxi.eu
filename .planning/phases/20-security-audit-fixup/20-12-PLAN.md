# 20-12 — A pay link must not work for an erased booking (26.2 "Database notes", P5)

**Found by the 26.2 audit** (`gsd/phase-26.2-audit-2`, `975c3ab4`, `26.2-BP-B.md` line 21).

## What happens today

Staff e-mail a pay link for an unpaid booking. The booking is then erased (the customer asked for
their data to be removed, or staff erased it). The three pay-link functions
(`checkout_pay_link_by_hash`, `checkout_pay_link_state`, `checkout_pay_link_lines`; migrations
`20260928140000`, `20260930170000`) look only at the status (`pending` or `quote`), never at
`erased_at`. `checkout_payment_settle` never reads `erased_at` either. So the e-mailed link still
opens a new payment page for the erased booking until its 24-hour hold ends, and a payment would
be recorded on an erased booking. 26.2's fix `085c3102` only closes the payment pages already open.

Example: Mia asks on Monday to have her unpaid booking erased. The pay link in her inbox still
opens Stripe on Tuesday morning; she pays; the dashboard shows a payment on a booking with no data.

## Change (one migration, function replacements only, no row changed)

1. The three pay-link functions also require `erased_at is null`. An erased booking answers like
   an expired link (the pay page already has that screen; no new text).
2. Erasing a booking revokes its `pay` tokens in the same step (find the erase function; add the
   revoke there), so the link is dead at once, not only hidden.
3. `checkout_payment_settle`: a payment that arrives for an erased booking is not recorded as a
   booking payment; it takes the existing "no booking to settle" path, which refunds it
   automatically. Read that path first; do not invent a new one.

## Tests (pgTAP, fail before, pass after)

- Pay link of an erased pending booking: `by_hash` returns no row, `state` answers expired,
  `lines` returns nothing.
- Erase revokes the pay token.
- Settle for an erased booking does not mark it paid.
- A pay link of a normal pending booking still works (all three functions).

## Checks and ship

pgTAP full run on an isolated stack, from-zero replay, types identical, `check:db-fences`.
Safe on real paid bookings: functions only. Needs the owner's Ship. After the ship: read back
`md5(prosrc)` of the changed functions.
