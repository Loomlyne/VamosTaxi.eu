<objective>
Settle the Phase 4 / Phase 5 seam, and prove the engine's answers can be rendered before anyone
builds the page that renders them.

Phase 5's own D-16 leaves this open in writing: *"confirm the exact hand-off point (does Phase 5
render the widget's static shell that Phase 4's client logic mounts into, or does Phase 4 ship the
whole component) at Phase 5 planning time."* Two locked sources already answer it — 04-CONTEXT.md's
out-of-scope line and 04-UI-SPEC.md's checker-verified "Phase 4 introduces zero new components" —
so the answer is the first option, and this plan is what makes that answer safe to act on rather
than merely stated.

The risk it removes is specific. A contract nobody has rendered is a contract with a wrong field
name in it. `ineligible_reason: "route_off"` has to land somewhere in `VehicleCard`; a null
`total_rappen` has to read `CHF 000` without a branch; a 2:59 countdown has to fit a German string
in a narrow price column; and the whole board has to survive `dir="rtl"`. Discovering any of that
in Phase 5 means re-cutting the API in the phase that was supposed to consume it.

Purpose: hand Phase 5 a contract that has already been rendered in four languages.
Output: `lib/quote/client-contract.ts`, a fixture set, and a dev-gated harness at `/dev/quote`.
</objective>
