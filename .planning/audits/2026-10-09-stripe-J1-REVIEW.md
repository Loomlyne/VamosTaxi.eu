## Verdict: FIX FIRST

The change does what it claims on the live money paths, and most of the requirement list is met. Two things stop it shipping as is:
1. **J1-R01**: the regex rejects a key with leading or trailing whitespace, which `fetch` silently strips, so a key that works today could be refused everywhere after deploy (checkout, queue consumer, cron, refunds). Whether the bound key has such a character is unverifiable here. The fix is one line (trim and use the trimmed value).
2. **J1-R02**: the PR gate "Visual + integration tests" runs `webhook-replay.spec.ts`, whose fixture events carry no `livemode`. The new check refuses them, so that PR job goes red.

Neither is a live-money logic error in the diff. Everything else is Medium or below.

Answer to the question "can this break live payments or live refunds that work today, or fail open on mode safety":
- Break: only through J1-R01 (key shape stricter than what runs today). A real Stripe key (`sk_live_` or `rk_live_` plus base62 and underscore) passes the regex.
- Fail open on mode safety: no. The webhook check fails closed (`undefined !== false` is refused), the key factory refuses anything that is not a Stripe key, and the mode comparison is the only thing not covered by a unit test (J1-R05).

## Checked and clean

- **Key regex vs real keys (question 1)**: `^(?:sk|rk)_(live|test)_[A-Za-z0-9_]+$`. Real secret and restricted keys are `sk_`/`rk_` + mode + base62 and fit; `_` is also allowed. The only gap is whitespace (J1-R01). Publishable regex `^pk_(live|test)_[A-Za-z0-9_]+$` fits the `pk_live_51UIZmAQb…` value in `wrangler.jsonc:75`.
- **Other readers of the key (question 2)**: every call goes through `stripeFromEnv` (checkout, pay link, phone booking, settle, expire, purge, fee sweep, cancel, paid cancel, change, edit, refund, health). `worker.ts` does not read the key. `scripts/stripe-e2e.mjs` and `stripe-session-probe.mjs` already refuse anything but `sk_test_`; they are untouched. The e2e Worker config key `sk_test_e2e_fake_local_only` passes the regex. Behaviour differs only for a value that is not a Stripe key.
- **Dashboard Worker**: `wrangler.dashboard.jsonc` carries no Stripe vars; `vamos-dashboard` is a gateway (`dashboard-gateway.ts`), so refunds run in the `vamos` Worker with the same secrets (not read further).
- **Publishable placeholder** (`pk_test_placeholder`) names no mode, so the probe does not fail the undeployed production block.
- **Staff early check**: an unbound key passes the check (refund-due flows need no Stripe) and fails later at `stripeFromEnv`; a bound invalid key stops before anything is written in change, withdraw, paid edit and refund. Refund of a test-era booking is covered in J1-R04.
- **Handler order**: signature header, webhook secret, key mode, signature check, then livemode compare; `WebhookModeError` is tested before its parent class.
- **Health probe**: `Balance.livemode` is a boolean on the Stripe balance object; tests cover agree, mixed keys, account/key disagreement and test mode.
