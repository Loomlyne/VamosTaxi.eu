# Stripe review W3: browser side, return, confirmation

Reviewer W3, deep, report only. Date 2026-10-09. No source file was edited. Paths are under `apps/web/` unless they start with `app/` at the repo root (`/Users/koss/Developer/VamosTaxi.eu/app/`).

## How the payment path really works (traced)

1. `CheckoutForm.pay()` (`app/[locale]/checkout/CheckoutForm.tsx:725`) posts selections only (`buildIntentBody`, `lib/checkout/pay-flow.ts:46`, no amount) to `POST /api/checkout/intent`.
2. The server opens a Stripe **hosted page** Checkout Session (`ui_mode: "hosted_page"`, `lib/checkout/stripe.ts:131`). There is no Stripe.js, no Elements, no PaymentIntent `client_secret` in the browser. The browser does `window.location.assign(json.url)` only when the URL passes `isStripeCheckoutUrl` (https + origin `https://checkout.stripe.com`, `lib/checkout/pay-flow.ts:12`).
3. Stripe redirects to `success_url` = `<origin>/api/checkout/return?locale=<enum>&session_id={CHECKOUT_SESSION_ID}` (`lib/checkout/intent.ts:505`, `lib/checkout/return-url.ts:20`).
4. `GET /api/checkout/return` (`app/api/checkout/return/route.ts:29`) validates the session id by regex, rate limits per IP, retrieves the session from Stripe, settles only when `payment_status === "paid"` (`lib/checkout/return-settle.ts:92`), then 303s to a fixed path plus a regex-validated reference.
5. `/confirmation/<ref>` server-renders the booking only behind the `vt_manage` cookie or account claims, else a "processing" shell. `ConfirmationClient` polls `GET /api/checkout/status/<ref>` and decides "booked" from the server answer only.

Questions about Elements config, `client_secret` exposure and Stripe.js CSP are **not applicable**: nothing of ours loads Stripe (`lib/security/headers.ts:7-9`).

## Checked and clean

- Client never decides "paid". The browser sends only selections (`lib/checkout/pay-flow.ts:46-77`, no amount, no price). The return route reads paid from Stripe (`lib/checkout/return-settle.ts:77,92`) and settle re-reads the session (`lib/checkout/settle.ts:200-202,236`). The confirmation poll only reads server status (`ConfirmationClient.tsx:1-6,509-516`; `app/api/checkout/status/[ref]/route.ts:50-53`). "Booked" requires voucher status or captured payment from the server (`lib/checkout/confirmation-phase.ts:25`).
- No open redirect from the return route. Every target is a fixed path plus enum locale (`return/route.ts:15,34`), regex-validated session id (`return-settle.ts:13`) and regex-validated reference (`booking-status.ts:1`); `encodeURIComponent` on the rest (`return-settle.ts:146,173`). No reflected URL.
- Redirect to Stripe is allow-listed (`pay-flow.ts:9-20`: https and origin `https://checkout.stripe.com`), used at `CheckoutForm.tsx:823,872` (the pay-link page skips it: see note below).
- `return_url` host cannot come from a request header string: `publicSiteOrigin` accepts only listed hostnames, strict regex, no userinfo, no path (`lib/security/origin.ts:103-117`); `x-forwarded-host` ignored. Locale in `success_url` is a zod enum (`intent-schema.ts:98`) and re-checked in `return-url.ts:22`. `successUrl` must contain `session_id={CHECKOUT_SESSION_ID}` (`stripe.ts:119-121`).
- Session id handling: no `client_secret` anywhere in the browser; session id only in the return URL, regex-validated, never logged (the only log line in the return route has fixed fields, `return/route.ts:49`); `Referrer-Policy: strict-origin` (`headers.ts:49`)
- Return route abuse control: per-IP limit before the Stripe read (`return/route.ts:43-53`, F6) with the same soft redirect, `cache-control: private, no-store` on every redirect (`route.ts:17-22`), `force-dynamic`.
- 3DS and Twint redirect return: the manage cookie is `SameSite=Lax` precisely so it is sent on the top-level GET back from Stripe (`lib/checkout/manage-token.ts:23-37`); the confirmation page does not need the tab to survive (`ConfirmationClient.tsx:3-5`).
- Double submit: `pay()` returns early while loading (`CheckoutForm.tsx:726`), button disabled and `aria-busy` while loading (`components/checkout/PayBar.tsx:80-93`), fieldset disabled while paying (`PaymentSection.tsx:39`), one idempotency key per selection that is dropped after a failed answer (`lib/checkout/pay-idempotency.ts:19-26`), bfcache `pageshow` resets the state (`CheckoutForm.tsx:973-980`). Server side race handling is W2's.
- Pay-link page: open and PAY use the server's state, never the browser's (`PayClient.tsx:152-157,236-251`, `pay-client-states.ts:47-57`); refused states (paid, refunded duplicate, expired) are shown from server codes; the sessionStorage session id is a regex-checked display hint only (`pay-client-states.ts:65-70`).
- Amount integrity on the browser side: the only amounts the client holds are display values; charged rappen comes from the server quote (`SummaryRail.tsx:131`, `CheckoutForm.tsx:620,717`); intent body has no amount field. CHF is the only charge currency (`stripe.ts:159`, `CHARGE_CURRENCY`); display FX falls back to CHF when no rate (`lib/fx/format.ts:33-35`).
- i18n completeness: every key in `checkout` (335) exists in de, fr and ar (script comparison: 0 missing in each). Entries identical to English are brand or loan words (Total, Link, Apple Pay, class names), plus a few in fr (`tripDate`, `tripDistance`, `contactMobile`, `chooseClassAria`, `extras`) that read the same in French. Missing keys also fall back to English at runtime (`i18n/request.ts:42-61`) and are logged (`:74-89`). Payment error strings checked in all four languages (`payStartFailed` path, `quoteExpired`, `priceChanged`, `paymentWindowClosed`, `payLink*`, `confirming*`, `received*`).
- RTL in payment UI: `checkout.css`, `confirmation.css`, `checkout-parts.css`, `account-choice.css`, `pay-link.css` contain no physical `left/right`, `margin/padding/border-left/right`, `text-align:left/right`, `float` or `translateX`; amounts, references, phone and flight use `vt-dir-keep`.
- Brand rules in payment UI: no glow or coloured shadow, no tinted yellow found in the files read; Alerts use `info`/`danger` tones; icons come from `Icon`.
- Amount text: CHF mark through `formatAmount`/`PriceSummary` (`lib/currency.ts`), `000` placeholder only for null.

Note on the pay-link redirect: `PayClient.tsx:284` calls `window.location.assign(json.url)` on the open route's answer without `isStripeCheckoutUrl`. The URL comes from our own server and from Stripe, so this is not exploitable today, but it is the one place the allow-list is skipped. Counted here rather than as a finding because exploiting it needs a compromised server response; apply `isStripeCheckoutUrl` there when W3-01 and W3-05 are fixed.
