## Flow as traced

1. `POST /api/stripe/webhook`: `request.text()` raw (route.ts:26) then `constructEventAsync` with the Web Crypto provider and Stripe's default 300 s tolerance (webhook-verify.ts:34-40). A bad signature returns 400.
2. `stripe_event_record` (`insert ... on conflict (id) do nothing`), then `STRIPE_EVENTS.send({eventId,type,objectId,stripeCreated})`, then 200. Either step failing returns 500 so Stripe retries (webhook.ts:54-73). The enqueue happens even when the row is a duplicate.
3. Queue consumer (`max_batch_size 1`, `max_retries 8`, DLQ): `handleStripeMessage` re-reads the session, charge or dispute from Stripe, then `stripe_event_begin` (attempts+1, `already_processed`, `superseded`, `ok`), then `checkout_payment_settle` or `checkout_extra_payment_settle` (stamps `processed_at` in the same transaction), or `stripe_charge_refunded_record` / `stripe_dispute_upsert` and then `stripe_event_settle`.
4. After the settle commit, in TypeScript and without a transaction: refund (when `refund_required`), confirmation mail, account provisioning, other-session expiry. Each is best effort and never turns into a retry.
5. After 9 deliveries the message goes to `...-dlq`; the DLQ consumer mails info@ once and always acks.

## Handled versus subscribed

Code handles (`settle.ts:191-211`, `money-events.ts:32-77`):

| Event type | Result |
|---|---|
| `checkout.session.completed` | `succeeded` if the re-read session has `payment_status=paid`, else `failed` |
| `checkout.session.expired` | `failed` |
| `checkout.session.async_payment_failed` | `failed` |
| `payment_intent.canceled` | `canceled` |
| `charge.refunded` | recorded in `booking_refunds` |
| `charge.dispute.created`, `.updated`, `.closed` | upserted in `booking_disputes` |

Anything else is stamped processed with no effect (`settle.ts:356-359`): `checkout.session.async_payment_succeeded`, `payment_intent.succeeded`, `payment_intent.payment_failed`, `charge.refund.updated`, `charge.succeeded`.

Stripe must be subscribed to at least these 8: `checkout.session.completed`, `checkout.session.expired`, `checkout.session.async_payment_failed`, `payment_intent.canceled`, `charge.refunded`, `charge.dispute.created`, `charge.dispute.updated`, `charge.dispute.closed`. The only recorded read of the endpoint (`docs/audit/2026-vamos-audit.md:169`, 24 Sept) lists 4 events: `checkout.session.*` and `payment_intent.canceled`. Nothing in the repo records that the 4 charge events were added afterwards. `stripe-fee.ts:8` says the endpoint is not subscribed to `charge.updated`. **Unverified, needs the live Stripe read (plan check 4).**

## Open questions answered

- **Raw body kept:** yes, `route.ts:26`, passed unchanged to `constructEventAsync`.
- **Signature tolerance and rotation:** default 300 s; one `STRIPE_WEBHOOK_SECRET` per environment. Stripe's secret roll sends both signatures for 24 h, so updating the Worker secret inside that window is safe. Per-environment secret binding is W1.
- **Record then enqueue gap:** safe. 200 is returned only after both; either failure returns 500; duplicates re-enqueue and are absorbed (`already_processed`). Only a long enqueue outage past Stripe's retry window leaves a row stranded (W4-01).
- **Consumer retry, ack, DLQ:** 8 retries; transient DB errors retry at 5 s or 60 s; permanent errors on a succeeded payment write the SQLSTATE and retry at 300 s so the DLQ mail always fires; DLQ consumer always acks; alert result is discarded (W4-02).
- **Double settle (U15):** safe at the database. Both paths take `FOR UPDATE` on the payment then the booking; the second sees `succeeded` and returns `already_settled` without a second confirmation. The earlier gap (the second delivery left its own `stripe_events` row unprocessed) is fixed in code at `20261007310000:121-130` and `settle.ts:338-345`; `CLAUDE.local.md` says that migration is live (2026-10-05 16:25). Whether the 11 old unprocessed return rows were cleaned is unverified (live check 1).
- **Capture versus auto-capture:** hosted Checkout, automatic capture. A succeeded outcome always ends confirmed or refunded; the capture gate is no longer consulted (`settle.ts:10-14`).
- **Partial failure after state change before email:** mail failure never fails the settle; hourly sweep resends (W4-10, W4-13 for the edges).
- **Stale side effects on retry:** refund idempotent by key, confirmation by claim row.
- **Poison messages:** a body without `objectId` throws a TypeError at `settle.ts:277`, retries 8 times, and in the DLQ `dlq.ts:32` throws again; `worker.ts:227-229` logs and acks without a mail. Messages come only from our own route, so Low and not a separate finding.
