## Answer to the priority question (short)

1. **The code cannot tell what mode the secret key is in.** Nothing in `apps/web` reads the prefix of `STRIPE_SECRET_KEY` at the one place that builds the client (`stripe.ts:17-29`). Nothing compares it with the publishable key. Nothing checks `event.livemode` in the webhook.
2. **The commit says the live secret key is already on the Worker.** `6a5f274e` message: "Staging Worker (public vamostaxi.site) now pairs the live publishable key with the live secret key already uploaded via wrangler secret." So the intent of that commit is live mode on Worker `vamos`. This contradicts `CLAUDE.local.md` ("Stripe test account acct_1UIZmqHcNp9GZYjz", live key needs his word every time, never covered by the standing order), `.planning/ROADMAP.md` must-nots, `lib/env.d.ts:361,373`, `docs/runbooks/stripe-webhook.md:6`. Whether he gave his word in that session is **not recorded in the repo**. The commit is authored as Koussay (PR #70), so it may be deliberate. Needs his answer (W1-01).
3. **Guards that refuse live keys exist only on 5 staff functions, only for the `sk_live_` prefix, as a blocklist.** `rk_live_` is not refused (U3 confirmed, still open). The customer checkout, pay-link, settle auto-refund, expire, and fee sweep have no mode guard at all (W1-02).
4. **Side effect if the key is live:** the same guards now block the only app path that refunds real money (W1-03).
