Branch `pay/j2-settle-stuck` (worktree `.claude/worktrees/pay-j2-settle-stuck`). **Stacked: base is branch `pay/j1-mode-guard`** (head `862584ec`), so it contains J1. J3 (`pay/j3-amount-verify`) and J4 (`pay/j4-late-paylink`) are stacked on top of it. Findings are in `.planning/audits/2026-10-09-stripe-W4.md` and `-W5.md` of the main folder (untracked there). ## What changed, per finding

| Finding | Change |
|---|---|
| W4-01 | New hourly step in `worker.ts` `scheduled()` (hourly path, after `expire_unpaid`): `lib/checkout/stripe-events-sweep.ts` calls `public.stripe_events_sweep_claim` (not processed, idle 10 min since the last delivery or sweep, oldest first, batch 20, ignores events older than 30 days and events closed with a benign reason) and re-enqueues `{eventId,type,objectId,stripeCreated}` on `STRIPE_EVENTS`. At most 6 sweeps per event (`SWEEP_MAX_SWEEPS`). An event still open after that comes back once as `abandon`: info@ is mailed (stuck-payment mail, ids only) and only then `stripe_events_sweep_abandoned` marks it reported; a mail that fails is an error log and is tried again next hour. Counts only in the log line `stripe_events_sweep`. |
| W4-02 | Every `deliver*` function in `lib/ops/must-fix-mail.ts` now reads the `{ok:false}` of `sendOpsMustFix` and throws `MustFixMailError` (code `no_api_key` / `send_failed` / `trip_not_found`, never provider text). The DLQ consumer (`lib/checkout/dlq.ts`, `lib/checkout/queue-consumers.ts`) no longer acks a failed alert: error log `dlq_alert_failed`, `message.retry({delaySeconds: 600})`, 5 deliveries in all (`max_retries: 5`, `retry_delay: 600` on both DLQ consumers in `wrangler.jsonc`), then error log `dlq_alert_gave_up` and ack (no further queue exists). The durable second line is the W4-01 sweep: the event is still unprocessed, is re-enqueued, hits the DLQ again, and is reported as abandoned until a mail goes out. Every other alert path in `settle.ts` (stuck payment, paid-after-cancel, overlap) logs a failure at error level. |
| W4-03 | Refund-required branches (`duplicate_charge`, `test_booking`, `paid_after_cancel`, `requote_superseded`) no longer stamp `processed_at` in SQL. They write the marker `refund_required:<reason>` in `stripe_events.last_error` and leave the event open. The Worker closes it (`stripe_event_settle(id,null)`) only after the Stripe refund and `checkout_duplicate_refund_record` both succeeded. A failed refund returns `{retry:true}` (error log `refund_failed`, no per-retry mail); the redelivery reaches settle's already-settled branch, finds the marker and returns the refund order again (new branch in `checkout_payment_settle`). The idempotency key is unchanged (`refund:<booking>:<payment>:<reason>`, `refund:missing-booking:<session>`). `refundPaidSessionWithoutBooking` (no payment row) no longer closes on a failed refund or a failed mail. A null PaymentIntent closes only after the stuck-payment mail went out. Tests: a failed refund is retried with the same key, a successful one is not repeated. |
| W4-04 | `settle.ts` chooses the Stripe re-read by event type and checks the id shape: charge `ch_` or `py_`, dispute `du_` or `dp_`. Any other id (also an empty one) is an error: error log `stripe_event_unknown_object_id`, `last_error='unknown_object_id'` written, `{retry:true}`; never stamped processed. The old fall-through that stamped null charges/disputes as processed now retries. A poison body without `objectId` no longer throws a TypeError. |
| W4-06, W1-14 | `retry_delay: 30` on both stripe-events consumers (staging, production). `retryDelayForAttempt(message.attempts)` gives 30, 60, 120, 240, then 300 s (total about 27 min for 8 retries); `applyHandleResult` uses it for every retry that names no delay (explicit delays 5/30/60/300 s unchanged). The throw path of the consumer retries with the same delay. |
| W4-09 | New `stripe_event_close(id, reason)`: sets `processed_at` and keeps the reason in `last_error`. Used for `no_request`, `no_payment`, `booking_missing`, `non_chf_refund`, `refund_required_no_payment_intent` and for a permanent error with nothing captured (SQLSTATE as reason). A non-CHF refund now mails info@ (checked) before it is closed. The sweep also skips rows that an older Worker left open with those reasons. |
| W4-10 | **Documented, not closed** (see "Found, not fixed"). |
| W4-14 | `consumeStripeEventMessage` (new, `lib/checkout/queue-consumers.ts`, called from `worker.ts`): a thrown handler logs `queue_handler_threw` at error level with message id, event type and SQLSTATE and class (or the error name), never the message text or body; a message that can be neither retried nor acked is logged and rethrown so Cloudflare redelivers. |
| W4-17, W5-04 | `checkout_payment_settle`: a failed/canceled outcome for a payment that is `succeeded` or `duplicate` changes nothing, raises nothing, writes no `payment.failed` event and closes the event. Same in `checkout_extra_payment_settle`. |
| W5-12 | Both settle functions normalise the currency/FX tuple before any write: unusable values (GBP, CHF with a rate = the legacy `currency_conversion` shape, an incomplete EUR/USD/AED tuple) are dropped; the capture is recorded as CHF without FX detail, and the raw facts go in the `payment.succeeded` event payload (`fx_not_recorded`). No more CHECK violation after capture. A complete EUR/USD/AED tuple is stored as before. |
| W5-17 | `stripe_event_settle`: an unknown event id raises P0002 (`event_not_found`); an already processed row keeps its first `processed_at` and gets no `last_error`. The already-settled branches of both settle functions stamp only `where processed_at is null`. |

## Deviations

- W4-03: I took the "do not stamp processed until the refund succeeded" option (marker in `stripe_events.last_error`) instead of a reopen RPC: a reopen would still have hit the already-settled branch with no refund order. The marker reuses `last_error`, so no schema change for it.
- W4-02: no new durable alert channel (ticket row, WhatsApp). The owner signed e-mail to info@; the extra signals are error logs, the DLQ retries and the sweep's abandon report. If the owner wants a second channel it is a new decision.
- The per-retry stuck-payment mail on a failed refund was dropped (it sent up to 9 mails); the DLQ mail after about 27 minutes is the alert, the error log shows each failure.
- W4-10: documented only.
- `database.types.ts` hand-edited (see above).

## Found, not fixed

- **W4-10 (documented)**: verified in code: only the confirmation mail has a sweep (`sweepStuckNotifications`, hourly, 10-minute claim). Nothing resumes: account provisioning (`provisionCheckoutAccount`; it is idempotent), expiry of the booking's other open Checkout Sessions (a late second payer is then refunded by the duplicate path, which is now durable), the driver mail after an applied change (`afterExtraApplied`), the info@ mail `alertDifferenceNotApplied`, and the Meta Purchase (no claim row survives a lost invocation). Cause: settle stamps `processed_at` in its own transaction and these steps run after it; a redelivery then answers `already_processed`. Closing it needs a claim row per step plus a sweep (new schema), or a second queue message enqueued with the settle; both are bigger than J2.
- A refund that Stripe rejects for good (for example the charge was already refunded by hand in the dashboard) retries 8 times, reaches the DLQ mail and then the sweep abandons it after 6 hourly runs; there is no automatic "already refunded" recognition (Stripe's idempotency key also only lives 24 hours).
- `deliverOpsMustFix` now throws on a missing key; its other two callers (`app/[locale]/(ops)/api/staff/vehicles/[id]/route.ts`, `lib/ops/edit-request.ts`) still swallow the throw without a log (off-road and overlap mails, not payment paths).
- Order-dependence of two pre-existing `*.local.test.ts` files (above).
- W4-12 (which events the Stripe endpoint subscribes to) is unchanged and still needs the live read.
- J1 review items R04, R06, R09, R10 are not touched here.
