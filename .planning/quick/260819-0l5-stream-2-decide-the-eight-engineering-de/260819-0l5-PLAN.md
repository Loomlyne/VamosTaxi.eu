**`.planning/ADR-003-booking-reference-format.md` — Q9, booking reference format.**
Status Accepted. Phase 2.
Context: the mocks use `VT-4821`-style references throughout, and `cleanBooking` at
`app/vamos-ops-data.js:202` generates `'VT-' + Math.floor(1000 + Math.random() * 8999)` —
random four digits, collision-prone by construction, not merely by exhaustion. `CLAUDE.md`
cites `VT-4821` as an example of a code that must carry `.vt-dir-keep` so it stays LTR inside
Arabic.
Decision: `VT-YY-####`, e.g. `VT-26-4821`. Digits stay, because dispatchers read references
aloud on the phone and a base32 or alphanumeric code is materially worse for that. The year
prefix resets the numeric space annually, so the ceiling is 9999 bookings per year rather
than 9999 ever — comfortably above a Zurich transfer operation's near-term volume, and
extendable to five digits within a year without a format break. It also makes a reference
self-dating in ops search, which is free.
Cost of being wrong: the highest-friction of the cheap decisions. Changing it after launch
leaves two formats in circulation permanently — in emails already sent, in support threads,
in ops search and in the manage-booking lookup. That is why it is settled now and not later.
Consequence to state as a constraint, not a footnote: sequential references are enumerable,
so the manage-booking link must stay a signed token and must never be a lookup by reference
alone. That property is already in the design; this ADR records that the format depends on it.
Also note that references stay `.vt-dir-keep` in Arabic and that the generator is replaced,
not extended — random four digits do not become the last four digits of the new format.

**`.planning/ADR-004-currency-display-only.md` — Q12, per-currency pricing.**
Status Accepted. Phase 4.
Context: `app/vamos-ops-data.js` stores a figure per currency via `moneySet()` for fixed
routes, per-km rates and surcharges, with a comment claiming dispatch can genuinely price a
route differently in EUR than in CHF. `VamosLocale.money()` does the opposite — it swaps the
mark and never the number. `CLAUDE.md` states it as a binding rule: the currency switch

per route and per surcharge — no per-currency columns. The port drops `moneySet`'s extra

migration — a prices table keyed by currency, added later. Building four lists now and
collapsing them later throws work away instead. The cheap direction is the one taken.

**`.planning/ADR-006-return-trips-booking-legs.md` — Q20, return trips.**
Status Accepted. Phase 2. This is the schema decision Phase 2 depends on, so say so.
Context: the widget has a return tab; the shape is currently modelled as a single `bookings`
row with a `return_at` column.
Decision: one booking, two legs. A `bookings` row is the commercial record — customer,
payment, price, reference, refund. A `booking_legs` table carries one or two rows, each with
direction, pickup, dropoff, scheduled_at, flight, vehicle class, chauffeur and status.
Why, argued rather than asserted: a return leg needs its own driver, its own vehicle, its own
pickup time, its own status and possibly its own flight. A `return_at` column cannot carry any
of that, and it breaks the first time dispatch assigns a different driver to the return, or
the customer cancels only the return leg. Two separate one-way bookings would hand the
customer two references and two confirmation emails for one purchase, and would break "one
booking, one fixed price" — the product's core promise.
State explicitly that a discounted round trip is a pricing rule that sits on top of either
model and is not a schema choice, so it is not decided here. Do not name a discount
percentage — that belongs to the CHF matrix and stays open under Q11.
Cost of being wrong: the most expensive of the eight to reverse. Every ops screen, every
email template and the refund path key off this shape, and changing it after launch means
migrating live bookings mid-flight. That is precisely why it is settled in Phase 2 rather
than discovered in Phase 9.

**`.planning/ADR-007-edge-data-residency.md` — Q24, data residency of edge processing.**
This is the one ADR in the set that is a proposal rather than a settled decision. Its
`**Status:**` line reads exactly `Proposed, pending counsel, 2026-08-19`. Phase 8, noting
that `.planning/STATE.md` requires it resolved before Phase 10. Title it as a proposal.
Context: Supabase is pinned to eu-central (Frankfurt) per `.planning/PROJECT.md`; Cloudflare

Proposed engineering default: pin the data-touching routes near Frankfurt with Smart
Placement; leave public marketing routes at the edge.
State all three options with their real costs, because the point of this ADR is to give
counsel a costed choice rather than an abstract question:
— Pin everything. Easiest to defend to counsel. Costs edge latency on static marketing pages
— but those are cached at the edge anyway, so the true cost is small.
— Pin nothing. Fastest. Passenger data is then processed in whatever jurisdiction the request

also the same fix for the Hyperdrive round-trip cost, so it pays for itself operationally
regardless of what the legal answer turns out to be.

processing at a Cloudflare PoP with no persistence constitutes a transfer at all under nFADP
and GDPR. That is a legal question, and nothing in the repo answers it.

everything pinned, it is a configuration change to the remaining routes and a small latency
cost on cached pages; if counsel accepts edge processing, the recommendation still stands on
its operational merits and nothing is undone. The expensive failure is shipping Phase 10
monitoring before this is answered, since `.planning/STATE.md` already ties Sentry to a
working `consent_log`.
